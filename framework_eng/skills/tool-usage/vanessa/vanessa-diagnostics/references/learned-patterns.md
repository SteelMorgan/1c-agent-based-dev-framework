область: отладка падающих Vanessa-сценариев
приём: при разборе любого падения сценария пошагово делать скриншоты до/после каждого подозрительного действия (открытие формы, нажатие кнопки, выбор пункта меню) и проверять реальную видимость элементов глазами на снимке, а не доверять тексту шага. Скриншот — первичный источник правды о runtime-состоянии формы; ЖР и логи — вторичный.
антиприём: интерпретировать «элемент не найден» / «команда не сработала» только по тексту execution log + ЖР и сразу классифицировать как `implementation_error` или эскалировать пользователю. Текстовые сигналы не показывают реальный layout, скрытые/перекрытые элементы, фактический заголовок открытой формы, ошибки рендеринга — все эти случаи диагностируются только визуально.
почему: Vanessa и ЖР сообщают «нет элемента DSSL_X», но на скриншоте может быть видно, что (а) открыта НЕ та форма, которую ожидали (FullTextSearch вместо чата), (б) элемент есть, но не виден из-за условия Видимость, (в) элемент перекрыт модальным окном/предупреждением безопасности, (г) шаг попал не на тот контрол из-за похожего синонима. Без визуальной проверки агент строит догадки и сжигает итерации Developer-Code «вслепую» (прецедент OC-23400: 3 итерации фиксов кода/XML, реальная причина — `Видимость = ЗначениеЗаполнено(DSSL_ContextObject)`, обнаружено только пользователем в debugger).
шаги:
  1. На любом падении/прерывании Vanessa-сценария — ДО эскалации или классификации `implementation_error` — сделать скриншот текущего состояния через `mcp__chrome-devtools__take_screenshot` (если noVNC доступен) или `gui-control` toolset (xdotool + scrot/import).
  2. Если упало внутри сценария — повторить шаги вручную или одиночным сценарием с `--screenshots-on-step` (если поддерживается) или через инструментацию: после каждого критичного шага форсировать скриншот.
  3. Сверить визуальный layout с ожиданием из `.feature`: какой заголовок формы, какие элементы видны, какая команда подсвечена.
  4. Только после визуального подтверждения классифицировать: defect-в-тесте (не та форма / не тот контрол) → Scenario-Author; defect-в-коде → Developer-Code; admin (роль/права) → эскалация пользователю.
  5. Орхестратор обязан делегировать визуальную диагностику сабагенту (Tester / Explorer), а не эскалировать «непонятный сигнал» пользователю в обход скриншот-проверки.
источник: OC-23400 iter 4-8 (3 ложные итерации Developer-Code из-за отсутствия визуальной проверки причины «элемент не найден»); указание пользователя 2026-04-26.

область: визуальная проверка как ПЕРВЫЙ шаг диагностики (приоритет над grep/анализом кода)
приём: при любом непонятном сигнале от Vanessa ПЕРВЫМ действием — визуально воспроизвести обсуждаемый шаг через скриншот (gui-control/chrome-devtools/screenshot skill). ТОЛЬКО ПОТОМ — grep по дампу, анализ метаданных, гипотезы о ролях. Если пользователь уже один раз указал «проверь визуально» — это не разовое указание, а постоянное правило для всех последующих итераций той же задачи.
антиприём: получив непонятный сигнал, сразу прыгать в `grep`/чтение модулей/анализ метаданных и формировать гипотезы на основе только текстовых данных. Это создаёт правдоподобные, но непроверенные объяснения, которые потом тратят итерации сабагентов. «Я нашёл правдоподобное объяснение через grep» ≠ «я доказал причину».
почему: Vanessa описывает РУНТАЙМ-симптом, который не всегда совпадает с тем, как код **должен** работать. grep по дампу показывает декларативное имя/роль; скриншот показывает, что реально отрендерилось. Эти два слоя могут расходиться: подменю с Title="WhatsApp" может рендериться под видимым именем «WhatsApp», но техническое имя — `WhatsAppБСП`, и Vanessa-локатор по technical-name промахивается даже при видимой кнопке. Без скриншота все рассуждения о причине — спекуляция.
шаги:
  1. На любом «не нашёл / открылась не та форма / не сработало» — НЕМЕДЛЕННО визуальная проверка тем же шагом, что упал. Скриншот результирующего экрана.
  2. Сравнить с ожиданием из .feature: что реально на экране — та форма? тот контрол? с тем именем/Title?
  3. Только после визуального подтверждения — переходить к grep/анализу кода/гипотезам.
  4. Если пользователь дал указание «проверь визуально» в любой итерации задачи — оно действует на ВСЕ последующие итерации той же задачи без переподтверждения.
источник: OC-23400 iter 9 — пользователь дал указание «проверь сам по скриншотам» в начале iter 4-cycle, я запомнил его как разовое и в iter 9 опять прыгнул в grep вместо скриншота (нашёл правдоподобную гипотезу о mismatch `Чаты_epi_ПодменюWhatsApp` vs `WhatsAppБСП`, но без визуального подтверждения).
