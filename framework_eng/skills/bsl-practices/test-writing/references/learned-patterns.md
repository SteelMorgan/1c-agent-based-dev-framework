```
status: confirmed
область: серверные YaxUnit-тесты с записью в БД
приём: Пишущий серверный набор всегда регистрируется с .ВТранзакции() сразу после
       ДобавитьТестовыйНабор(). Рантайм ищет настройку по иерархии Тест→Набор→Модуль.
       Перед каждым тестом YaxUnit открывает транзакцию, после — откатывает.
       Справочники — только через ЮТест.Данные(); документы через Документы.X.СоздатьДокумент()
       не трекаются — требуют явного teardown в .После("...").
антиприём_1: НЕ создавать объекты через прямые конструкторы (Справочники.X.СоздатьЭлемент,
             Документы.X.СоздатьДокумент) без teardown — объекты не трекаются YaxUnit,
             копятся в базе, прогоны теряют идемпотентность.
антиприём_2: НЕ применять .ВТранзакции() к наборам с негативными тестами проведения
             (ожидаемый Отказ = Истина): упавшая вложенная транзакция отравляет внешнюю —
             «В данной транзакции уже происходили ошибки!» при последующих чтениях.
             Такие наборы: .УдалениеТестовыхДанных() + .После("Очистка").
исключения: (а) негативные тесты проведения — см. антиприём_2;
            (б) прод-код с гвардом ТранзакцияАктивна() — двухфазные фиксации, реальные API;
            (в) клиентский контекст — ДобавитьКлиентскийТест.
            Каждое исключение требует комментария-обоснования у набора + .После("Очистка").
почему: Без изоляции тесты не воспроизводимы, база деградирует, прогоны дают нестабильные
        результаты в зависимости от порядка выполнения и предыдущих запусков.
шаги: |
  1. ДобавитьТестовыйНабор("Имя") — сразу .ВТранзакции() если набор пишет в БД
  2. Справочники: ЮТест.Данные().СоздатьЭлемент() / КонструкторОбъекта().Записать()
  3. Документы: ЮТест.Данные().СоздатьДокумент() — трекается; иначе .После("Очистка")
  4. Негативные тесты: .УдалениеТестовыхДанных() + .После("Очистка"), без .ВТранзакции()
  5. Перепроведение: ДокОбъект = Ссылка.ПолучитьОбъект() перед каждой сменой режима
источник: task-165 GBIG PAM, два гейта ревью (2026-06-05); повторно подтверждено на TASK-165.6
```

```
status: confirmed
область: серверные модули расширений (YaxUnit)
приём: В серверных модулях (Server=true) использовать ПредопределенноеЗначение("Справочник.ИмяСправочника.ИмяЭлемента")
       для получения ссылки на предопределённый элемент.
антиприём: НЕ использовать ПредопределённыйЭлемент() — это клиентская функция,
           недоступная в серверном контексте. Ошибка компиляции, расширение не загружается.
почему: 1С выдаёт ошибку компиляции "Процедура или функция с указанным именем не определена",
        расширение TESTS не загружается, тесты зависают без результата.
        ЖР показывает event_presentation="30" (ошибка компиляции), но без явного указания на причину.
шаги: |
  1. В серверных модулях (Server=true, ExternalConnection=true): ПредопределенноеЗначение("...")
  2. В клиентских модулях (Client=true): допустим ПредопределённыйЭлемент(), но ПредопределенноеЗначение тоже работает
  3. При массовом исправлении: grep -r "ПредопределённыйЭлемент" → replace_all → ПредопределенноеЗначение
источник: task-103 GBIG PAM, ошибка компиляции в 4 тестовых модулях (2026-03-24)
```

```
status: confirmed
область: тестирование кода с УстановитьПривилегированныйРежим(Истина)
антиприём: НЕ писать тест, проверяющий, что код с УстановитьПривилегированныйРежим(Истина)
           «работает под пользователем без прав» (вернул данные / не упал с ОшибкаПравДоступа).
           Привилегированный режим платформенно и БЕЗУСЛОВНО отключает проверку прав —
           это гарантия платформы 1С, а не поведение твоего кода. Такой тест проверяет
           ФРЕЙМВОРК, а не функцию. Он зелёный независимо от логики и пройдёт, даже если
           убрать всю бизнес-логику — нулевая диагностическая ценность.
почему: тест-под-ограниченным-пользователем для верификации привилегированного режима = тест
        тестирует платформу. Дополнительная цена: требует спец-фикстуры (пользователь с урезанной
        ролью, снятое Чтение на справочник), двухсессионный сплит в Vanessa, ручное создание
        admin-юзера — всё ради проверки платформенного инварианта. Прецедент: TASK-165.2 SC-05 /
        unit T-17 (REQ-10) — застряли на отсутствии пользователя ОграниченныйПользовательТест;
        под полноправным AgentAI тест проходил «вхолостую» (полные права → результат тот же
        с привилегированным режимом и без). SC-05 заодно заражал соседний сценарий через
        битый TestClient в реестре VA.
приём (что РЕАЛЬНО проверять): не факт обхода прав, а ГРАНИЦЫ привилегированного режима —
       что УстановитьПривилегированныйРежим(Ложь) вызывается СРАЗУ после нужного запроса
       (точечно, не на всю процедуру), в т.ч. в ветке Исключение. Это поведение твоего кода,
       а не платформы. Стандарт «включил точечно → сразу выключил» уже в навыках по стандартам
       БСП (см. [[ssl-patterns]], [[error-handling]]) — отдельный тест на «обход прав» не нужен,
       достаточно ревью точечности границ.
исключения: если привилегированный режим НЕ безусловный (условная установка по флагу/роли —
            редко и обычно само по себе анти-паттерн) — тогда поведение зависит от твоего кода
            и проверка осмысленна. Но дефолт: безусловный УстановитьПривилегированныйРежим(Истина)
            → тест прав НЕ писать.
источник: TASK-165.2 GBIG PAM, директива пользователя (2026-06-09): «если стоит
          УстановитьПривилегированныйРежим=Истина, права 100% не проверяются — это платформенная
          фишка, перепроверять не нужно; главное чтобы режим сразу после вызова выключался —
          а это уже в навыках по стандартам БСП».
```

```
status: confirmed
область: обратный (LIFO) обход накопителя в teardown-коллекторе zero-residue
антиприём: НЕ писать обратный обход через `Для Сч = Накопитель.ВГраница() По 0 Цикл`.
           Цикл `Для` в 1С считает ТОЛЬКО вверх (шага вниз НЕТ): при непустом накопителе
           условие `ВГраница() <= 0` ложно сразу → тело НЕ исполняется НИ РАЗУ. Это
           МОЛЧАЛИВЫЙ no-op — компиляция чистая, LSP чист, тест зелёный, ЖР без ошибок,
           а коллектор не удаляет ничего и residue копится.
приём: обратный обход ТОЛЬКО через `Пока` с ручным декрементом, причём декремент — ДО
       любого `Продолжить`, иначе вечный цикл:
         Сч = Накопитель.ВГраница();
         Пока Сч >= 0 Цикл
             Ссылка = Накопитель[Сч];
             Сч = Сч - 1;
             ...
         КонецЦикла;
почему: зелёный тест при сломанном teardown — типовая маскировка. Симптом
        неотличим от «всё чисто», пока не измеришь ДЕЛЬТУ объектов до/после прогона.
        Поэтому приёмка коллектора — дельта-0 запросом КОЛИЧЕСТВО(*), а НЕ «тест зелёный».
        Диагностика этого класса требует full-rebuild (динамический build — no-op на BSL,
        грузит старый код → ложная картина) + лог `удалено=N` внутри ОчиститьВсё.
        Прецедент: TASK-165 GBIG PAM — `удалено=0` при 40 объектах в накопителе, residue
        в big_Markets/big_MarketAccounts/биг_Портфели; после фикса цикла удалено==на входе,
        дельта-0 на всех 7 модулях.
исключения: общий запрет на reverse-`Для` в 1С — исключений нет (конструкция языка).
источник: TASK-165 GBIG PAM (2026-06-15), рантайм-эксперимент с инструментом в ОчиститьВсё.
```
