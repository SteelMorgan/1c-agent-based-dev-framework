# Git Work Policy

> Goal: a transparent history (one commit = one logical unit of work), task-level rollback ability, and careful handling of generated 1С artifacts.

## Principles

1. **One task — one branch.** Task isolation on `task/TASK-XXX-<slug>`, branched from the parent branch (usually `main`).
2. **Commit = checkpoint.** Each approved full-cycle phase is recorded with a commit. This provides restore points if the next phase fails.
3. **Squash-merge into the parent.** The parent branch receives the task as a single commit. Phase history remains in the task branch for postmortem analysis.
4. **Subagents do not commit.** Only the orchestrator has the right to run `git commit` (within the task and for the final merge when the conditions in § “Final merge” are met) and the user.
5. **`//++agent` markers and git complement each other.** Markers provide a local audit trail in the source code (see `agent-code-marking`); git provides history over time. Markers in code are NOT removed before commit.
6. **No force-pushes or destructive operations in the parent branch.** Inside the task branch, rebase/amend are allowed while the branch is local.
7. **Deleting files from git is forbidden without explicit user permission.** This principle is critical — see the separate section “Prohibition on deleting files” below.

## Branch Strategy

### Creating a task branch

When a task is classified as **medium/complex** (full-cycle), the orchestrator:

1. Ensures the working tree is clean (`git status --porcelain` is empty). If not, this is either an unfinished previous task (escalate to user) or manual user edits (require separate discussion).
2. Starts from the current parent branch: `git fetch origin && git switch <parent>` (for example `main` or `master` — determined by the project).
3. Creates a task branch: `git switch -c task/TASK-XXX-<slug>`, where `<slug>` is a short kebab-case name (max 4-5 words).
4. Records the branch name and the parent SHA at the moment of branching in `orchestrator-context.md`.

### Quick-fix

For a **simple task** (see `quick-fix.md`: <20 lines, one file, no new artifacts) — a separate branch is NOT created. The commit goes directly into the current project branch as a single commit tagged `fix(TASK-XXX): ...`.

### Subtasks (TASK-XXX.Y)

If a task is split into numbered subtasks (TASK-103.1, TASK-103.2), each subtask has **its own branch** `task/TASK-103.1-<slug>`, merged into `main` independently. If the work is indivisible — one branch `task/TASK-103-<slug>`, with commits labeled `TASK-103.1`, `TASK-103.2`.

## What to Commit and What Not to Commit

### MUST commit

| Category | Paths |
|-----------|------|
| Source code | `src/xml/**`, `exts/<extension>/**` (except protected paths, see `protected-paths`) |
| Unit tests | `exts/TESTS/**` |
| BDD scenarios | `vanessa-tests/features/**/*.feature`, `vanessa-tests/support/**` |
| Task documentation | `tasks/<TASK-XXX>/**` in full — specification, technical design, task breakdown, agent contexts, final report, images |
| Configuration metadata | `ConfigDumpInfo.xml`, `Configuration.xml` — even if autogenerated, they are a valid part of the Designer format |
| Code `//++agent` markers | Markers inside BSL remain in commits — they are part of the source |

### MUST NOT commit (`.gitignore`)

| Category | Paths |
|-----------|------|
| Vanessa run artifacts | `vanessa-tests/reports/**`, `vanessa-tests/runs/**`, `vanessa-tests/allure/**` |
| Runner logs | `**/*.runner.log`, `**/runner.log`, `**/temp/**` |
| v8-runner artifacts | `workPath/**`, `v8project.local.yaml` |
| Local settings | `.install-session.json` (if it contains local state rather than project config) |
| Caches and temporary files | `*.cache`, `*.tmp`, IDE-local (`.idea/`, `.vscode/` — at project discretion) |

The concrete `.gitignore` is maintained in the project; this rule fixes the categories.

## When the Orchestrator Commits

The commit is made **after passing the approval gate / review** for each full-cycle phase.

| Phase | What goes into the commit | Message type |
|------|---------------------------|---------------|
| Phase 1 (Analyst) after user approval | `tasks/TASK-XXX/spec.md`, `.context/analyst-context.md`, `.context/reviewer-context-spec.md` | `spec(TASK-XXX)` |
| Phase 2 (Architect) after user approval | `tasks/TASK-XXX/technical-design.md`, `task-breakdown.json`, `.context/architect-context.md`, `.context/reviewer-context-arch.md` | `design(TASK-XXX)` |
| Phase 3a (Scenario-Author) after Reviewer | `vanessa-tests/features/**/*.feature`, `.context/scenario-author-context.md`, `.context/reviewer-context-bdd.md` | `bdd(TASK-XXX): scenarios` |
| Phase 3b (Developer-Tests) after Reviewer | unit tests in `exts/TESTS/**`, `.context/developer-tests-context.md`, `.context/reviewer-context-tests.md` | `test(TASK-XXX)` |
| Phase 3c (Scenario-Coder) after Reviewer | Vanessa step implementation in `vanessa-tests/features/steps/**`, `vanessa-tests/support/**`, `.context/scenario-coder-context.md` | `bdd(TASK-XXX): steps` |
| Phase 3d (Developer-Code) after Reviewer | implementation in `src/xml/**`, `exts/<ext>/**` (with `//++agent` markers), `.context/developer-code-context.md`, `.context/reviewer-context-code.md` | `feat(TASK-XXX)` / `fix` / `refactor` |
| Phase 4 (Tester) after Reviewer | additional tests, `.context/tester-context.md`, `.context/reviewer-context-tester.md` | `test(TASK-XXX): coverage` |
| Final report | `tasks/TASK-XXX/final-report.md` | `chore(TASK-XXX): final report` |

**If a phase did not pass review (BLOCK):** the phase authors make changes in the working tree, **without committing**, until the review is closed. Only the final approved version is committed.

**Bug report from Debugger:** a separate commit `fix(TASK-XXX/debug): <symptom>`. After acceptance of the Debugger fix.

## Commit Message Format

```
<type>(TASK-XXX[/phase]): <short description in Russian, up to 72 characters>

<optional extended explanation: how this phase differs from the previous one,
which important decisions were recorded. Single-line commits are acceptable for simple
cases.>

Phase: <name of the phase from full-cycle>
Agent: <subagent_type, for example developer-code>
Co-Authored-By: Claude <noreply@anthropic.com>
```

### Types

| Type | When |
|-----|-------|
| `spec` | Specification (Phase 1) |
| `design` | Technical design (Phase 2) |
| `bdd` | Vanessa scenarios and steps (Phase 3a / 3c) |
| `test` | Unit/integration tests (Phase 3b / 4) |
| `feat` | New functionality (Phase 3d) |
| `fix` | Bug fix (Phase 3d or quick-fix) |
| `refactor` | Refactoring without behavior changes |
| `perf` | Performance optimization |
| `chore` | Technical debt, marker cleanup, final report |
| `docs` | Documentation (CLAUDE.md, rules, skills) |

## Final Merge of a Task into the Parent Branch

### Conditions for orchestrator auto-merge

The orchestrator has the right to perform a squash-merge into the parent branch **only when ALL conditions are met**:

1. `cross-provider-review` in **gate mode** returned `verdict: PASS` (see orchestrator.md § 7.2).
2. `tasks/TASK-XXX/final-report.md` has been created and contains a `cross_provider_review` block with `review_id`.
3. All test runs (unit + Vanessa) in the final iteration completed with exit_code=0, raw stdout is attached to the final report.
4. `git status --porcelain` is clean — there are no unsaved files outside the task scope.
5. The parent branch has not moved too far ahead: if it has — the orchestrator first runs `git rebase <parent>` in the task branch and reruns the tests. If there are rebase conflicts — escalate to user.

If at least one condition is not met — the orchestrator does NOT merge, but informs the user and waits for their decision. User confirmation for the merge itself is NOT required when all conditions are met — the orchestrator merges automatically as many tasks as passed the gate.

### Squash-merge command

```bash
git switch <parent>
git merge --squash task/TASK-XXX-<slug>
git commit -m "TASK-XXX: <название задачи>

<краткое содержание изменений, 3-5 строк>

Phases completed: 1, 2, 3a, 3b, 3c, 3d, 4
Cross-provider-review: PASS (id=<review_id>)
Task branch: task/TASK-XXX-<slug>

Co-Authored-By: Claude <noreply@anthropic.com>"
```

### After merge

1. The task branch is **not deleted** for at least 2 weeks — in case of rollback or postmortem analysis.
2. The orchestrator writes to `orchestrator-context.md`: `MERGED: <merge_sha> → <parent>`.
3. If the project has a remote and push is configured — the orchestrator does NOT push automatically. Pushing to the remote is the user's decision.

## Prohibition on Deleting Files from Git

> The most critical protection against work loss. Applies to all agents — the orchestrator, subagents, debugger.

### PROHIBITED without explicit user permission

- `git rm <path>` — removing a file from tracking
- `git rm --cached <path>` — removing from tracking while keeping it in the working tree
- Physical deletion of a file that was under git control (that is, `git ls-files` shows it), followed by including the deletion in a commit
- `git reset --hard <commit>` outside the task branch or in a way that loses someone else’s changes
- Any operation that results in `git log -- <path>` in the parent after merge showing “file deleted”

### When deletion is allowed

1. **Explicit written permission from the user in the current dialogue.** Without confirmation “yes, delete this file” — do not delete. Saved permissions in memory or CLAUDE.md do NOT count as explicit permission for the current deletion.
2. **The file falls under `.gitignore`** and was previously committed by mistake. In this case, `git rm --cached` is allowed, but the orchestrator must explicitly tell the user: “this file is leaving git but remains local because it falls under `.gitignore`.”
3. **Atomic rename** (`git mv`). If a file is renamed / moved to another location — this is not deletion, but a move, and it is transparent to history.

### What to do instead of deletion

| Situation | What to do instead of deletion |
|----------|--------------------------------|
| Old code is no longer needed | Comment it out with the `//--agent` marker (see `agent-code-marking`). Do not physically cut out the file/lines |
| A phase artifact turned out to be wrong | Overwrite it with a new version. The old one will remain in commit history |
| A task folder seems obsolete | Do NOT delete `tasks/<TASK-XXX>/`. It is an audit trail of the work. If the task is canceled — leave it as is, you may add a note in `final-report.md` |
| It seems that the file is not needed in the repo at all | Escalate to the user with justification. Only the user performs deletion |

### Behavior when a violation is suspected

If the orchestrator detects a `D <path>` line in `git status` (deleted) OR an `R <old> -> <new>` line (rename) that was NOT explicitly initiated by the current phase:

1. Do NOT commit the change
2. Record in `orchestrator-context.md`: `SUSPECTED_DELETION: <path>`
3. Escalate to the user with the specific question “did you delete `<path>` or is it a side effect?”

## Rollback

| Scenario | Action |
|----------|--------|
| A phase did not pass review, ≥3 iterations | Right before BLOCK on the 3rd iteration: the phase commit is NOT made. Escalate to user. |
| A bug in the implementation is found after the Phase 3d commit | Separate commit `fix(TASK-XXX/debug): ...` on the same branch. |
| The task in the parent turned out to be bad | `git revert <squash-sha>` in the parent. One revert removes the task entirely. |
| The task was abandoned midway | The branch remains as is. Optionally rename it to `abandoned/TASK-XXX-<slug>`. |
| You need to redo Phase N from scratch | `git reset --hard <commit_phase_N-1>` in the task branch, then redo it. |

## Parallel Phases (3a and 3b)

Phase 3a (Scenario-Author) and Phase 3b (Developer-Tests) are performed in parallel. **The orchestrator commits the results sequentially:** first the one who finished first, then the second. If they touched shared files (which should not happen by design — 3a writes `.feature`, 3b writes `.bsl`) — that is a signal to investigate; someone stepped outside their phase scope.

## What NOT to Do (Anti-Patterns)

| Anti-pattern | Why it is bad |
|---------------|--------------|
| A subagent makes `git commit` on its own | The subagent does not see the entire phase scope and may commit junk. The right to commit belongs to the orchestrator. |
| A commit like “update ConfigDumpInfo” as a separate commit | `ConfigDumpInfo.xml` changes on every export and must be included in the commit of the phase that generated it. |
| Removing `//++agent` markers before commit | Markers are part of the source and provide context months later. They are removed only during the next major change (see `agent-code-marking`). |
| Force-push to the parent branch | Overwrites other people’s changes and breaks blame. |
| Committing `.context/` separately from phase artifacts | Contexts go into the commit of their own phase — they describe exactly that work. |
| Merge into `main` without `cross-provider-review` PASS | Violates the gate protocol in `orchestrator.md` § 7.3. |
| Deleting a file from git without explicit user permission | Loss of work and audit trail. See § “Prohibition on deleting files”. |
| `git rm` or `git rm --cached` on the agent’s initiative | Only the user has the right to remove files from tracking. |
| Deleting the `tasks/<TASK-XXX>/` folder of a canceled task | Task documentation is part of the audit trail. Mark it as canceled, but do not delete it. |

- `agent-code-marking` — markers inside commits; mandatory for BSL changes.
- `agent-context-protocol` — agent contexts go into the commit of their own phase.
