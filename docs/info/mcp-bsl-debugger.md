# MCP-отладчик BSL через debug server 1С

Этот документ можно **скормить агенту** как установочную инструкцию. Он описывает, что агенту нужно поднять на стороне сервера 1С и как проверить, что интерактивная отладка BSL доступна через MCP.

## Что это даёт

MCP-отладчик подключает агента к debug server 1С и даёт сценарий, близкий к обычной IDE-отладке:

- подключиться к инфобазе;
- увидеть доступные targets: клиентские сеансы, фоновые задания, WebSocket/HTTP-контексты;
- загрузить метаданные конфигурации и расширений;
- поставить breakpoint в модуле по строке;
- дождаться остановки;
- посмотреть стек, локальные переменные и выражения;
- выполнить `step_in`, `step_out`, `continue`;
- снять breakpoint и отключиться.

Основной проект MCP: [liga-1c-command/1c-debug-mcp](https://github.com/liga-1c-command/1c-debug-mcp).

## Архитектура

```
AI agent
  -> MCP server 1c-debug-mcp
    -> HTTP debug endpoint 1C debug server
      -> ragent/rphost с включённой HTTP-отладкой
```

Обычно debug server слушает порт `1550` на сервере 1С. Для удалённых серверов безопаснее не открывать порт наружу, а пробросить его SSH-туннелем:

```bash
ssh -i "<SSH_KEY>" \
  -L 127.0.0.1:<LOCAL_DEBUG_PORT>:127.0.0.1:<REMOTE_DEBUG_PORT> \
  -N -f <USER>@<HOST>
```

После этого MCP подключается к `http://127.0.0.1:<LOCAL_DEBUG_PORT>`.

## Включение HTTP-отладки 1С

Целевое состояние процесса 1С: `ragent` и рабочие процессы, которые будут отлаживаться, должны быть запущены с HTTP-отладкой. Для ручной проверки итоговый процесс обычно выглядит так:

```text
ragent ... -debug -http
rphost ... -debug -http
```

Если сервисный wrapper уже добавляет `-debug`, переменная окружения может задавать только добавочные флаги:

```bash
SRV1CV8_DEBUG=-http
```

Не принимай это на веру для конкретной версии платформы или конкретного entrypoint. Smoke-тест обязан проверить оба варианта:

1. Сначала `SRV1CV8_DEBUG=-http`.
2. Перезапустить сервис 1С.
3. Проверить фактические аргументы `ragent`/`rphost` через `ps`.
4. Если HTTP-отладка не поднялась, повторить с `SRV1CV8_DEBUG="-debug -http"`.
5. Зафиксировать, какой вариант реально работает в данном окружении.

На Linux-сервере дополнительно должен быть запущен `dbgs`:

```bash
/opt/1cv8/current/dbgs --addr=127.0.0.1 --port=1550
```

`--addr=0.0.0.0` допустим только как исключение: закрытый контур/VPN или firewall allow-list, временное окно отладки, пароль debug server (`ONEC_DEBUG_PASSWORD`) и явное выключение после проверки. Базовый вариант — loopback + SSH-туннель.

## Установка MCP

В этом workspace уже есть постоянная копия проверенной Node-сборки:

```bash
cd "/workspaces/work/repos/1C Framework/1c-debug-mcp"
npm run build
```

Используй этот каталог вместо `/tmp`: временные каталоги могут быть очищены.

Актуальный upstream-путь — Go-бинарь:

```bash
git clone https://github.com/liga-1c-command/1c-debug-mcp.git
cd 1c-debug-mcp/go
go build -o dist/1c-debug-mcp ./cmd/1c-debug-mcp/
```

Если агент работает с legacy-веткой, где MCP ещё собирается через Node.js, допустим запасной вариант:

```bash
cd 1c-debug-mcp
npm ci
npm run build
```

Минимальные параметры, которые агент должен получить из проекта:

```bash
ONEC_DEBUG_URL="http://127.0.0.1:<LOCAL_DEBUG_PORT>"
ONEC_INFOBASE_ALIAS="<INFOBASE_ALIAS>"
ONEC_CF_PATH="<ABS_PATH_TO_SRC_XML>"
ONEC_CFE_PATHS="<ABS_PATH_TO_EXTENSION_1>;<ABS_PATH_TO_EXTENSION_2>"
```

Если расширений нет, `ONEC_CFE_PATHS` можно не задавать.

## Smoke-тест

Smoke-тест должен быть явным и коротким:

1. Проверить, что SSH-туннель или прямой debug endpoint доступен.
2. Запустить MCP-сервер отладчика.
3. Выполнить `attach` к `ONEC_DEBUG_URL` и `ONEC_INFOBASE_ALIAS`.
4. Выполнить `get_targets`; должны вернуться хотя бы один клиентский/серверный target или фоновые задания.
5. Выполнить `reload_metadata`; конфигурация и нужные расширения должны загрузиться без ошибок.
6. Поставить breakpoint в безопасной процедуре тестового или служебного модуля.
7. Убедиться, что breakpoint принят и привязан к модулю.
8. Выполнить `clear_breakpoints`.
9. Выполнить `detach`.

Smoke-тест не обязан реально останавливать бизнес-сценарий. Реальная остановка проверяется уже в сценарии отладки конкретной процедуры.

## Инициирование остановки на breakpoint

Для реальной отладки порядок такой:

1. `attach` к debug server.
2. `get_targets` и выбор нужного target.
3. `reload_metadata`.
4. `set_breakpoints`.
5. Запуск сценария, который вызывает нужный код.
6. Сразу перейти в отладчик и опрашивать stop event: `wait_for_stop` каждые 5 секунд.
7. Для быстрого кода предел ожидания 30 секунд; для тяжёлой операции агент до запуска оценивает длительность и задаёт контрольный предел, чтобы не уйти в бесконечное ожидание.
8. После stop event управление через отладчик: `get_call_stack`, `get_variables`, `step_in` / `step_out` / `continue`.
9. `clear_breakpoints` и `detach`.
10. Если `detach` не сработал или возник `ibInDebug`, выполнить `force_detach` и повторно проверить targets.

Типовые способы вызвать код:

- Клиентский контекст: Vanessa-сценарий. Через `v8-session-manager` (`v8sm`) определить сеанс тест-агента и сопоставить его с target отладчика.
- Клиентский контекст: тестовый клиент + UI-tools MCP-витрины, если проще накликать форму/команду.
- Серверный контекст: минимальный YaxUnit-тест, который вызывает серверный метод или ближайшую публичную точку входа.
- Серверный контекст: временный tool в расширении `mcp_tools`, если тестом вызвать неудобно. После отладки удалить tool, регистрацию, временные экспортные методы и тестовые данные.

## Безопасность

- Не открывать debug-порт наружу без необходимости; предпочитать SSH-туннель.
- Не оставлять активные breakpoint после завершения.
- Не оставлять остановленный поток в транзакции, фоновой задаче или пользовательской сессии.
- Не выполнять `evaluate` для выражений с побочными эффектами: записи, проведения, вызовы HTTP, изменение глобального состояния.
- Не смотреть и не выводить секреты, токены, пароли, персональные данные.
- После работы всегда делать `clear_breakpoints` и `detach`.
- При зависшей debug-сессии использовать `force_detach`, затем проверить `get_targets`.
