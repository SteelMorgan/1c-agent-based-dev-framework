## Вывод

`dev-rules` - это не набор машинных `SKILL.md`, а Docusaurus-база соглашений. Считать навыками нужно тематические страницы: правила кода, запросы, формы, метаданные, роли, интеграции, CI/CD, Git/IDE и процессные регламенты.

Большая часть общих инженерных принципов избыточна: модель и так знает SOLID/KISS/DRY/YAGNI, Git flow, базовые RabbitMQ/Kafka-концепты, REST-коды и общие правила IDE. Для нашего фреймворка ценность дают не эти общие знания, а прикладные 1С-чек-листы, которые модель не обязана держать в весах в проектно-точной форме:

- какие свойства не забывать при создании конкретных объектов метаданных;
- какие БСП/RLS/даты запрета/варианты отчетов/версии объектов подключать;
- какие свойства управляемых форм важны для UX и корректности;
- какие локальные query-review правила стоит добавить к уже существующим навыкам;
- какие интеграционные соглашения по контрактам и брокерам можно оформить как проектные policy.

## P0: что стоит перенести

1. **Metadata object design checklist.**
   Добавить отдельный skill/reference для создания и review объектов метаданных. Это должно дополнять XML-спеки: спеки говорят "как устроен XML", а checklist говорит "что не забыть в рабочей 1С-конфигурации".

   Минимальный перенос:
   - справочник: длина наименования по умолчанию, код 0 если не нужен, представление объекта/списка, обязательный comment при новом объекте, заполнение/проверка заполнения, связи/параметры выбора, префиксация при распределенных сценариях;
   - документ: единственное/множественное представление, запрет оперативного проведения по умолчанию, каркас проведения, удаление движений, роли, подсистемы;
   - регистры: запрет незаполненных значений для обязательных измерений, порядок измерений по частоте отбора/соединения, дата запрета, RLS hooks;
   - отчет: БСП `ВариантыОтчетов`, хранилище вариантов, роль просмотра, не оставлять вариант "Основной", учитывать RLS, не использовать внешние отчеты как обход релизного цикла;
   - роли: убрать интерактивное удаление, роли подсистем, шаблоны именования, не использовать "установить все/снять все";
   - регламентные задания: thin entrypoint в одном модуле, логика в профильном модуле, `ОбщегоНазначения.ПриНачалеВыполненияРегламентногоЗадания`, `Использование` по умолчанию выключено.

2. **Form platform properties checklist.**
   Расширить форму не только визуальными требованиями, но и проверками XML/метаданных:
   - команда формы, меняющая сохраняемые данные, должна иметь `Изменяет сохраняемые данные`;
   - страница табличной части должна иметь `ПутьКДаннымЗаголовка`;
   - обязательность по возможности через свойство `Проверка заполнения`, а не только код;
   - для типовых форм добавлять программно и группировать в отдельную служебную вкладку/группу, если ТЗ не задает место;
   - видимость/доступность обновлять централизованной процедурой и последним действием после заполнения данных;
   - в форме списка добавлять `ГруппаПользовательскихНастроек`.

3. **Query style/safety delta.**
   Дополнить `query-patterns` не performance-правилами, а review-правилами:
   - имена вложенных запросов и временных таблиц должны быть осмысленными;
   - индекс ВТ только при evidence или очевидной многократной крупной связке;
   - не смешивать условия соединения (`ПО`) и отбора (`ГДЕ`);
   - `Запрос.Текст` устанавливать до параметров;
   - не делать отдельный `РезультатЗапроса.Пустой()` перед обычным обходом, если достаточно первого `Выборка.Следующий()`;
   - булевы поля в запросе выражать булевой алгеброй, а не `ВЫБОР ... ИНАЧЕ ЛОЖЬ`;
   - фиксировать особенность `АВТОНОМЕРЗАПИСИ` как warning, не как общее правило.

## Отклонено как избыточное

- SOLID/KISS/DRY/YAGNI и generic architecture basics: модель знает без инструкций; наши `code-quality`/developer rules уже задают практический стиль.
- Git/GitFlow/SSH/LFS/gitattributes/VS Code/EDT basics: модель и локальные `git-workflow`/инструкции покрывают; перенос создаст шум.
- Kafka overview: слишком общий и помечен как "в разработке".
- Docusaurus/website infrastructure, code of conduct, contributing сайта: не расширяет агентные знания по 1С-разработке.
- Пользовательские manuals: полезны как проектная документация, но не универсальный агентный skill.

## Методология повторной сверки

1. Обновить snapshot:

```bash
git -C /tmp/yellow-hammer-dev-rules pull --ff-only
git -C /tmp/yellow-hammer-dev-rules log --oneline -20
```

2. Смотреть изменения только в `docs/**/*.md`, не в сайте/зависимостях:

```bash
git -C /tmp/yellow-hammer-dev-rules diff --name-only <old>..HEAD -- docs
```

3. Классифицировать каждую новую страницу по четырем вопросам:

| Вопрос | Что означает |
|---|---|
| Модель знает это без инструкций? | Если да, не переносить, кроме проектно-точных 1С-нюансов |
| У нас уже есть skill/rule/reference? | Если да, переносить только дельту, не дублировать основу |
| Это универсально для 1С или доменно/проектно-специфично? | Универсальное идет в skill, доменное - в optional reference |
| Можно ли применить как checklist/review rule? | Если нет, оставить как watching/skip |

4. После переноса обновлять этот документ и сводную таблицу `external-skills-mapping.md`.
