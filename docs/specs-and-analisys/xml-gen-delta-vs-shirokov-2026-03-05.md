# Delta: `xml-gen` vs `cc-1c-skills` (Nikolay Shirokov)

Дата анализа: `2026-03-05`

Источник для сравнения:
- upstream repo: `https://github.com/Nikolay-Shirokov/cc-1c-skills`
- локальный модуль: `tools/xml-gen`
- локальные навыки: `framework/skills/tool-usage/xml-generation/*`

## 1. Краткий вывод

Текущий `xml-gen` в этом репозитории уже лучше upstream по качеству ядра:
- единый Java CLI, а не набор разрозненных PowerShell/Python-скриптов
- есть типизированное ядро, writers, editors, validators
- есть интеграция с `mdclasses` и `bsl-common-library`
- есть тестируемая архитектура, пригодная для дальнейшего расширения

Но upstream ушел шире по охвату предметной области:
- работает не только с EPF/Form/MXL/SKD/Role
- добавлены механизмы для `meta-*`, `cf-*`, `cfe-*`, `subsystem-*`, `interface-*`
- отдельно развиты `db-*`, `web-*`, `web-test`

Главный вывод: **переносить нужно не скрипты как есть, а предметную модель и покрытие объектов, встраивая их в ядро `xml-gen`**.

## 2. Вероятная точка расхождения

Наиболее вероятно, что за основу был взят upstream в состоянии примерно `2026-02-10`.

Признаки:
- к `2026-02-10` в upstream уже были `EPF`, `Form`, `MXL`, `Role`, `SKD`
- ваш `xml-gen` появился как отдельный Java-модуль `2026-02-12`
- предметный охват на старте практически совпадает с upstream-срезом на эту дату
- дальнейшее развитие пошло в другую сторону: у нас `ядро + валидация + editors`, у upstream `много skills + скрипты + новые домены`

Это не git-fork в точном смысле, а **функциональное ответвление с архитектурной переработкой**.

## 3. Что есть в upstream по XML и чего у нас пока нет

Ниже зафиксирована предметная дельта именно для XML/metadata-части.

### 3.1. Уже покрыто у нас

В текущем `xml-gen` покрыты:
- EPF
- Form
- MXL
- SKD
- Role
- edit-команды для части объектов
- validate-команды

Это достаточная база для точечных XML-объектов, внешних обработок и связанных артефактов.

### 3.2. XML/metadata-покрытие upstream, которого у нас нет

В upstream есть отдельные направления, которых в текущем `xml-gen` нет или нет как класса возможностей:

1. `meta-*`
- создание XML объектов конфигурации из DSL
- редактирование XML объектов конфигурации
- удаление объектов
- анализ структуры объекта
- валидация объектов конфигурации

Это ключевой пробел, если целевая модель должна работать **со всем деревом конфигурации**, а не только с отдельными файлами.

2. `cf-*`
- работа с корневыми файлами конфигурации
- создание пустой конфигурации
- редактирование `Configuration.xml` и связанных корневых структур
- валидация корневого дерева конфигурации

Это второй критичный пробел. Без этого невозможно сделать целостный XML-driven workflow по всей конфигурации.

3. `cfe-*`
- создание XML структуры расширения конфигурации
- заимствование объектов
- patch methods / interception
- валидация расширения
- сравнение изменений

Если планируется работа не только с конфигурацией, но и с расширениями, это отдельное важное направление.

4. `subsystem-*`
- создание/редактирование подсистем
- работа с XML подсистем
- валидация подсистем

5. `interface-*`
- редактирование `CommandInterface.xml`
- валидация командного интерфейса

Это отдельно важно, потому что интерфейс подсистемы часто ломается именно на XML-уровне, а агенты без инструмента слабо справляются с такими правками.

6. Дополнительные прикладные XML-объекты/операции в upstream
- `help-add`
- `template-add` / `template-remove`
- `form-remove`
- `mxl-decompile`
- `info`-режимы для ряда XML-объектов

Это не всегда ядро, но это полезные сервисные операции, которых сейчас не хватает для полного цикла.

## 4. Что именно нужно встраивать в ядро `xml-gen`

Ниже не "что скопировать", а **как правильно расширять ядро**, чтобы оно стало основой для всего дерева конфигурации.

### 4.1. Целевой принцип

`xml-gen` должен стать не просто "генератором 5 типов XML", а **единым metadata engine**:
- compile
- edit
- validate
- info
- decompile (где это оправдано)
- tree-aware operations

То есть целевая модель:

`DSL / CLI intent -> typed metadata core -> tree/layout resolver -> XML IO -> validation pipeline`

### 4.2. Что считать обязательной частью ядра

#### A. Единая модель дерева конфигурации

Нужно добавить в ядро представление:
- корня конфигурации
- дерева child objects
- типов объектов метаданных
- layout/path rules для каждого типа
- зависимостей между файлами

Минимально нужны:
- `Configuration.xml`
- `ConfigDumpInfo.xml`
- `Languages/*`
- `ChildObjects` и их регистрация
- привязка объекта к каталогу/файлу по типу

Без этого агент может сгенерировать корректный XML отдельного объекта, но не встроить его в конфигурацию безопасно.

#### B. Единый registry типов метаданных

Нужен registry уровня ядра:
- metadata type id
- xml namespace/schema expectations
- правила физического расположения
- правила регистрации в родительском узле
- правила валидации структуры

Практически это должен быть слой над `mdclasses`, а не россыпь ручных `if/switch`.

#### C. Tree-aware operations

Нужны не только `compile <obj>`, но и операции:
- `cf init`
- `cf validate`
- `cf add-object`
- `cf remove-object`
- `meta compile`
- `meta edit`
- `meta validate`
- `subsystem edit`
- `interface edit`
- `cfe init`

Смысл: команда должна знать не только про файл, но и про **место объекта в дереве**.

#### D. Обязательная двухуровневая валидация

Это критично.

Нужно закрепить как hard requirement:
1. `structure validation`
- обязательные элементы
- namespace
- порядок узлов
- базовые ограничения формата

2. `semantic validation`
- регистрация объекта в родителе
- корректность ссылок между XML-объектами
- допустимость типа/свойства для конкретного metadata object
- совместимость с layout дерева
- существование связанных файлов (`Ext`, forms, templates, rights, command interface, etc.)

Для агентного применения без этого механизм будет ломаться на "почти валидном XML".

#### E. Safe edit pipeline

Редактирование должно идти через pipeline:
- load
- parse
- normalize
- mutate
- revalidate
- write
- rollback on failure

Это уже частично есть в текущем editor/validator подходе и должно стать правилом для всех новых metadata-типа.

#### F. Info/read-mode

Агенты плохо понимают raw XML 1С. Значит ядру нужен безопасный режим чтения:
- `info` или `inspect`
- summary структуры объекта
- список child objects
- доступные свойства
- человекочитаемая сводка по связям

Это снизит потребность читать XML напрямую.

#### G. Decompile/reverse projection

Не для всех объектов, но полезно иметь там, где DSL реально удобен:
- MXL
- Form
- Role
- SKD
- в перспективе часть metadata objects

Это позволит round-trip и упростит работу агентов со сложным XML.

## 5. Предлагаемая программа расширения `xml-gen`

Ниже порядок, в котором имеет смысл развивать ядро.

### Этап 1. Привести в консистентность текущее ядро

Перед расширением нужно устранить внутренние расхождения:
- README и skills сейчас расходятся по `EDT` и по полноте `SKD`
- нужно зафиксировать один источник истины по supported features

### Этап 2. Добавить корневой уровень конфигурации

Новые команды:
- `xml-gen cf init`
- `xml-gen cf validate`
- `xml-gen cf info`
- `xml-gen cf add-object`
- `xml-gen cf remove-object`

Новые ядровые компоненты:
- `ConfigurationTree`
- `MetadataLayoutRegistry`
- `MetadataRegistrationService`

### Этап 3. Добавить generic metadata object engine

Новый модуль:
- `meta compile`
- `meta edit`
- `meta validate`
- `meta info`

Начать с самых частых типов:
- Catalog
- Document
- Enum
- CommonModule
- InformationRegister
- AccumulationRegister
- Constant

Важно: здесь нужно не копировать upstream-скрипты, а построить **единый generic framework для metadata objects**.

### Этап 4. Подсистемы и командный интерфейс

Добавить:
- `subsystem compile/edit/validate/info`
- `interface edit/validate`

Это закрывает важный практический сценарий: агент может добавить объект и сразу корректно встроить его в UI дерева конфигурации.

### Этап 5. Расширения конфигурации

Добавить:
- `cfe init`
- `cfe validate`
- `cfe borrow`
- `cfe patch-method`

Это отдельный слой, но лучше строить его уже поверх общего tree-aware ядра.

### Этап 6. Сервисные XML-операции

Добавить по мере приоритета:
- `help add`
- `template add/remove`
- `form remove`
- `mxl decompile`
- `role info`
- `form info`
- `skd info`

## 6. Что из upstream стоит перенести концептуально уже сейчас

### 6.1. Type synonym resolution

В upstream свежая полезная идея: более мягкое разрешение синонимов типов в form DSL.

Для нашего ядра это надо встраивать не в form-only код, а в общий `TypeResolver`:
- псевдонимы базовых типов
- более устойчивый парсинг shorthand
- нормализация composite types

### 6.2. Composite types

Это особенно важно для будущего `meta-*`.

Нужно заложить в общее ядро поддержку:
- составных типов
- канонизации composite notation
- нормальной сериализации ссылочных типов и namespace

### 6.3. Namespace discipline

Опыт upstream с `d5p1` показывает, что namespace-ошибки всплывают поздно и болезненно.

Нужно закрепить отдельный namespace layer:
- canonical namespace registry
- сериализация namespace по типу XML-документа
- validator на namespace consistency

## 7. Что фиксировать как отсутствующее у нас, но нужное

Ниже список нужно сохранить как backlog domain gaps.

### 7.1. Внешние обработки / отчеты / прикладные XML-операции

У нас уже есть часть EPF-сценариев, но дополнительно нужно учитывать:
- remove form/template/help operations
- сценарии полного жизненного цикла внешних отчетов
- decompile/info-сценарии для существующих XML

### 7.2. Полное дерево конфигурации

Сейчас отсутствуют как отдельный механизм:
- root configuration operations
- generic metadata object operations
- subsystem/interface operations
- extension operations

Это ключевой пробел относительно целевой модели.

### 7.3. Обязательная валидация на каждом шаге

Для агентного использования это не "nice to have", а базовое требование:
- validate before edit
- validate after edit
- rollback on invalid write
- отдельный machine-readable output

## 8. Отдельно: механизмы upstream, не относящиеся к `xml-gen`

Эти механизмы нужно изучать отдельно и не смешивать с развитием XML-ядра.

### 8.1. `db-*`

Что это:
- создание базы
- загрузка/выгрузка конфигурации
- обновление базы
- запуск 1С
- загрузка изменений из Git

Почему отдельно:
- это orchestration/runtime level
- это не XML engine
- зависит от платформы, окружения, CLI конфигуратора

### 8.2. `web-*`

Что это:
- публикация базы через Apache
- управление публикациями
- остановка/удаление публикаций

Почему отдельно:
- это deployment/infrastructure layer
- не относится к XML-ядру

### 8.3. `web-test`

Что это:
- Playwright automation для 1С web client
- чтение DOM и семантическое представление форм
- сценарии тестирования через браузер
- скриншоты, видео, TTS

Почему отдельно:
- это UI/runtime automation
- не связано с XML generation/validation напрямую
- может использоваться как downstream-проверка после XML-изменений, но не как часть `xml-gen`

### 8.4. `switch.py` и мультиплатформенные skills

Что это:
- перенос skills между `.claude`, `.codex`, `.agents`, `.cursor` и др.
- переключение runtime `PowerShell <-> Python`

Почему отдельно:
- это packaging/distribution layer
- не имеет отношения к ядру XML-обработки

## 9. Практическая стратегия для нашего проекта

### Не делать

- не переносить PowerShell/Python-скрипты upstream в `tools/xml-gen`
- не строить расширение через копирование отдельных навыков
- не добавлять новые metadata-типы без валидатора
- не смешивать XML-core и web/db automation в один модуль

### Делать

- расширять `xml-gen` как metadata engine
- сделать tree-aware ядро для всей конфигурации
- ввести обязательную структуру `compile/edit/validate/info`
- опираться на `mdclasses` как на ядро доменной типизации
- рассматривать upstream как источник domain coverage и сценариев, а не как готовую архитектуру

## 10. Решение по приоритетам

### Приоритет A

Критично для целевой архитектуры:
- `cf-*`
- `meta-*`
- mandatory validation pipeline
- registry/layout/tree core

### Приоритет B

Очень полезно:
- `subsystem-*`
- `interface-*`
- `cfe-*`
- `info`-режимы

### Приоритет C

Поддерживающие и сервисные вещи:
- `mxl-decompile`
- remove/help/template utility operations
- дополнительные UX-режимы

## 11. Финальная оценка

`cc-1c-skills` полезен для нас не как кодовая база для прямого переноса, а как:
- источник предметного покрытия XML объектов 1С
- источник сценариев CLI/skill usage
- источник списка недостающих возможностей

Текущее `xml-gen` уже лучше как основа продукта.

Следующий шаг должен быть не "догнать upstream по количеству навыков", а:

**превратить `xml-gen` в единое ядро работы со всем XML-деревом конфигурации 1С с обязательной валидацией на каждом шаге.**
