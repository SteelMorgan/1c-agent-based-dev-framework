# MXL DSL: наш парсер vs канон Широкова

**Дата:** 2026-05-21
**Цель:** определить стратегию миграции для §8 SPEC-xml-gen-backlog (hard cut vs back-compat vs гибрид).
**Гейт:** этот документ должен быть утверждён до старта Java-имплементации §8.

---

## 1. TL;DR

Два DSL описывают одну и ту же предметную область (SpreadsheetDocument 1С), но с **принципиально разными соглашениями**. Ни один нельзя считать надмножеством другого: у каждого есть уникальные возможности, которых нет у второго.

Ключевые расхождения затрагивают все три уровня: структуру верхнего уровня (`columnWidths`, `page`), модель строки (`rowStyle` с наследованием vs без) и модель ячейки (тип содержимого через имя поля vs через поле `type`). Имеющиеся 6 тестов в `MxlWriterTest.java` привязаны к текущему формату и **сломаются** при любом неаккуратном переносе на канон.

**Рекомендация:** стратегия «гибрид с конвертером» — добавить `MxlDslV2.java` (канон) рядом со старым, активируемый маркером `"$schema": "mxl-v2"` в JSON или флагом `--canon shirokov`. Существующие тесты остаются зелёными; навык уже документирует канон — консистентность восстанавливается без поломки потребителей. Подробное обоснование — §8 и §9.

## 3. Грамматические примеры — side-by-side

### 3.1. `columnWidths` — значения `"Nx"`

**Наш (`MxlDsl.java:29`, поддерживает только числа):**
```json
{
  "columns": 10,
  "defaultWidth": 12,
  "columnWidths": { "1": 5, "2-8": 40, "9-10": 50 }
}
```

**Канон Широкова (`dsl-spec.md §columnWidths`):**
```json
{
  "columns": 10,
  "page": "A4-landscape",
  "columnWidths": { "1": 5, "2-8": "1x", "9-10": "2x" }
}
```

**Разница:** Наш принимает `Map<String, Object>`, но в `MxlWriter.java` значения колонок не записываются вовсе (лишь `defaultWidth` в `<format><width>`). Канон: строка `"1x"` означает `1×defaultWidth`, `"2x"` — `2×defaultWidth`; `defaultWidth` вычисляется автоматически из `page` если все значения — `"Nx"`. Текущий `MxlWriter.java` не содержит ни одного вызова для записи индивидуальных ширин колонок в XML.

### 3.2. `page` — настройки страницы

**Наш:** Поле отсутствует. Ширина по умолчанию задаётся явно:
```json
{ "columns": 10, "defaultWidth": 10 }
```

**Канон:**
```json
{ "columns": 10, "page": "A4-landscape" }
```
Если добавить `"Nx"`-ширины — компилятор сам считает `defaultWidth` так, чтобы суммарная ширина вписалась в 780 у.е. (A4-landscape).

**Разница:** `MxlDsl.java` не имеет поля `page`. Это не просто пропуск — без `page` невозможно использовать `"Nx"`-пропорции (они привязаны к целевой ширине страницы).

### 3.3. `rowStyle` — автозаполнение строки

**Наш (поле парсится, но в компиляции молча игнорируется):**
```json
{ "rowStyle": "bordered", "cells": [
  { "col": 1, "param": "А" },
  { "col": 4, "param": "Б" }
]}
```
Результат: в XML будут только 2 ячейки — col=0 и col=3. Колонки 2-3 не будут иметь рамки.

**Канон (из `dsl-spec.md §rowStyle`):**
```json
{ "rowStyle": "bordered", "cells": [
  { "col": 1, "param": "А" },
  { "col": 4, "param": "Б" }
]}
```
Результат: компилятор создаст 4 ячейки: col=1 (param), col=2 (пустая, стиль `bordered`), col=3 (пустая, стиль `bordered`), col=4 (param). Все 4 с рамкой.

**Разница:** поведение при одинаковом DSL — разное. У нас `rowStyle` — «декларация намерения», которая теряется. В каноне — рабочий механизм. Это **самое критичное** поведенческое расхождение.

### 3.4. `height` строки — игнорирование

**Наш (`MxlDsl.java:145`, `MxlWriter.java` — не используется):**
```json
{ "height": 24, "cells": [{ "col": 1, "text": "Заголовок" }] }
```
Высота в XML **не записывается**. Каждая строка в XML будет иметь дефолтную высоту.

**Канон (`dsl-spec.md §rows`):**
```json
{ "height": 24, "cells": [{ "col": 1, "text": "Заголовок" }] }
```
Высота записывается в XML. Используется для строк заголовков с крупным шрифтом.

**Разница:** `height` принимается десериализатором, но до XML не доходит. Тихое игнорирование.

### 3.5. Validator — классификация ошибок

**Наш (MxlValidator.java:11):**
```
Level 1 (Structure): MXL-001..005
Level 2 (Semantic):  MXL-101..106
```
Коды: MXL-001 (namespace), MXL-002 (templateMode), MXL-003 (columns), MXL-004 (height mismatch), MXL-101 (horizontalAlignment), MXL-102 (verticalAlignment), MXL-103 (merge), MXL-106 (font height).

**Канон (`validate-classes.md`):**
Семь классов: `bad-column-index`, `bad-format-index`, `bad-height`, `palette-refs`, `area-ranges`, `merge-ranges`, + прочие структурные.

**Разница:** классификация разная, частичное семантическое перекрытие. `palette-refs` частично покрывается нашим MXL-101/102, `area-ranges` — не покрывается вовсе, `bad-column-index` — нет. `bad-format-index` — нет.

### 3.6. Decompile auto-naming стилей

**Наш (MxlDecompiler.java:68–99):**
Стили берут `id` из XML-элемента `<format><id>…</id>`. Если исходный MXL был собран сторонним инструментом без осмысленных имён — стили получат числовые ID.

**Канон (SKILL.md §Decompile):**
Автоматические осмысленные имена: `default`, `bold`, `header`, `bordered`, `bordered-right`, `bold-right`, `border-top` — вычисляются по комбинации свойств шрифта и рамки.

**Разница:** у нас нет логики автогенерации имён из свойств — только сохранение существующих ID.

## 4. Что есть только в каноне Широкова

Возможности, описанные в SKILL.md/dsl-spec.md, отсутствующие в `MxlDsl.java` и `MxlWriter.java`:

1. **`page`** — настройки страницы. Ни поля POJO, ни обработки в компиляторе (`MxlDsl.java` — отсутствует).

2. **`columnWidths` с `"Nx"` значениями** — пропорциональные ширины. `MxlWriter.java` не записывает индивидуальные ширины колонок вообще (только `defaultWidth` в `<format><width>`).

3. **`rowStyle` auto-fill** — при задании `rowStyle` у строки все незаполненные колонки получают пустые ячейки с этим стилем. В `MxlWriter.java` поле `rowStyle` принимается (`MxlDsl.java:147`), но компилятор его не использует при записи ячеек.

4. **`rowStyle` + `rowspan` взаимодействие** — при `rowspan > 1` последующие строки в той же области должны пропускать занятые колонки при автозаполнении. Логика не реализована.

5. **`height` строки в XML** — `MxlWriter.java` не записывает `<height>` в `<rowsItem>`. Поле парсится в POJO (`MxlDsl.java:145`), но теряется.

6. **Деление `columnWidths` на списки** (`"5,7,9"`) — в нашем коде ключ `"5,7,9"` не парсится; `MxlWriter.java` вообще не использует `columnWidths`.

7. **Автоосмысленные имена стилей при decompile** — логика `default`/`bold`/`bordered` по свойствам. Наш `MxlDecompiler.java` берёт имена из `<format><id>`.

8. **Validator `bad-column-index`** — проверка `col + span - 1 <= columns`. В `MxlValidator.java` отсутствует.

9. **Validator `bad-format-index`** — проверка, что style-reference существует в палитре форматов. Отсутствует.

10. **Validator `area-ranges`** — диапазоны именованных областей валидны (top <= bottom, не выходят за границы). Отсутствует.

11. **Validator `merge-ranges`** — объединения не пересекаются между собой. Отсутствует.

12. **Validator `palette-refs`** — целостность всех палитр (font/border/color/style). Частично перекрыто MXL-101/102, но не системно.

## 5. Что есть только у нас (риск потери при миграции)

Возможности текущего `MxlDsl.java` / `MxlWriter.java`, **не упомянутые** или упомянутые как «ограничение» в SKILL.md:

1. **`borderWidth` на уровне Style** — поле `borderWidth` (String: `"thin"` / `"thick"`) в `MxlDsl.Style` (`MxlDsl.java:100`). Записывается в `<width>1</width>` или `<width>2</width>` (`MxlWriter.java:381-383`). В dsl-spec.md это поле присутствует, так что риска нет — это совместимость.

2. **Валидация MXL-002 (`templateMode`)** — проверка наличия `<templateMode>true</templateMode>`. В канонических 7 классах не выделена как отдельный класс, но описана в «прочие структурные».

3. **Валидация MXL-004 (`height` vs rowsItem count)** — конкретная проверка на соответствие объявленной высоты и реального числа строк. В каноне входит в «прочие структурные».

4. **`detail` как `<detailParameter>` в XML** — в `MxlWriter.java:262` (decompiler) корректно читает `<detailParameter>`. Это нюанс реализации, канон описывает семантику `detail`, но не XML-тег — **риска нет** если сохранить тег.

5. **Семантика пустых ячеек без `cells`** (`MxlWriter.java:143–146`) — строка без `cells` инкрементирует счётчик строк. Это деталь поведения, которая должна сохраниться в каноне.

6. **Числовая ширина в `columnWidths` без `"Nx"`** — текущий формат допускает чисто числовые ширины без `page`. При миграции на канон поле `columnWidths` с числовыми значениями **должно остаться валидным** (канон тоже допускает числа — дополняет строками `"Nx"`).

- Все 6 тестов используют `new MxlDsl(...)` с позиционным конструктором. При переименовании или изменении сигнатуры классов тесты не скомпилируются.

- Нет ни одного теста на `rowStyle` (поле игнорируется) — при реализации `rowStyle` понадобятся новые тесты.
- Нет тестов на `height` строки.
- Нет тестов на `columnWidths` с `"Nx"`.

**Итого: 6 тестов; 0 тестов специфичны для канона Широкова.**

## 8. Стратегии миграции

### 8.1. Hard cut

**Суть:** удалить `MxlDsl.java` и `MxlWriter.java`, создать `MxlDslV2.java` и `MxlWriterV2.java` (или переименовать на месте). Старый формат JSON больше не поддерживается.

**Плюсы:**
- Чистая кодовая база без двойного кодекса.
- Навык `mxl-dsl/SKILL.md` уже описывает канон — код наконец совпадёт с документацией.
- Нет логики выбора парсера по версии.
- Bump major version (0.x → 1.0) сигнализирует о намеренном разрыве.

**Минусы:**
- Все 6 тестов `MxlWriterTest.java` нужно переписать (не только скомпилировать — семантика `rowStyle`, `height`, `columnWidths` изменится).
- Если у потребителей есть JSON-файлы в старом формате (проверить: на данный момент в codebase production-скриптов нет, но они могут быть в проектах пользователей).
- Нет пути ни для тех, кто начал использовать старый формат и сохранил JSON-файлы.

**Impact на потребителей:**
Все 7 subagent-промптов ссылаются на навык как документацию — они следуют SKILL.md, а не старому коду. После hard cut SKILL.md (уже описывающий канон) станет консистентен с реализацией. Потребители будут исправно генерировать DSL в каноническом формате.

### 8.2. Back-compat через `--canon shirokov` или `"$schema"` маркер

**Суть:** сохранить `MxlDsl.java` как устаревший парсер. Добавить `MxlDslV2.java`. Активация нового парсера — `"$schema": "mxl-v2"` в JSON или CLI-флаг `--canon shirokov`.

**Плюсы:**
- Существующие тесты остаются зелёными без изменений.
- Если у пользователей есть JSON-файлы в старом формате — они продолжают работать.
- Можно выпускать постепенно (patch/minor bump).

**Минусы:**
- Двойной кодекс: две версии POJO, два writer'а — неясно, какой вариант «правильный».
- Агенты могут путаться, в каком формате генерировать DSL (SKILL.md — канон, но CLI принимает оба).
- Технический долг: когда и как удалять старый парсер? Нужен явный deadline или условие (major bump).
- Тестовое покрытие нового формата не появится само — нужно написать параллельный набор.

**Технический долг:** по плану SPEC-xml-gen-backlog.md §8.2 — «полная миграция через 1 версию после релиза 0.3.0». Без явного коммита это рискует зависнуть.

### 8.3. Гибрид (конвертер старого формата в новый)

**Суть:** Написать `MxlDslMigrator.java` — при обнаружении старого формата (отсутствие `$schema`, наличие только числовых `columnWidths`) автоматически конвертировать в канон перед compile. Пользователю ничего делать не нужно — оба формата работают через один writer.

**Плюсы:**
- Максимально прозрачная миграция: старые JSON работают, новые JSON работают, writer один.
- Можно написать автоматический апгрейд инструментом (`xml-gen mxl upgrade <input.json>`).
- Нет двух независимых кодовых путей для сериализации XML.

**Минусы:**
- Конвертер сложнее, чем кажется: `"Nx"` нельзя автоматически вывести из числовых ширин без знания `page`. Конвертация может быть только «одностороннюю»: числа → числа (без `"Nx"`).
- `rowStyle` в старом формате молча игнорировался — при конвертации нельзя «достроить» пропущенные ячейки, если неизвестно поведение.
- Возможны неожиданные различия: отладка «почему поведение поменялось у старого JSON» — трудная задача.

## 9. Рекомендация

**Рекомендуемая стратегия: гибрид с маркером `"$schema"` (подход 8.2, без конвертера).**

Аргументация:

1. **Объём расхождений (§2):** из 22 концепций — 5 конфликтов (❌) и 4 частичных расхождения (🔶). Переписывание существенное, но изолированное: затрагивает только `MxlDsl.java`, `MxlWriter.java`, `MxlValidator.java`, `MxlDecompiler.java`. Остальные модули не затронуты.

2. **Использование (§7):** 0 production-скриптов. Все потребители — агентские промпты и документация. Риск «сломать чьи-то JSON-файлы» невысок, но не нулевой — если пользователь уже хранит JSON-макеты в старом формате.

3. **Риск потери функциональности (§5):** минимальный — в нашем парсере нет уникальных возможностей, которых нет в каноне. Всё, что мы умеем, канон тоже умеет (и шире).

4. **Тесты (§6):** 6 тестов, которые тестируют текущее поведение. При back-compat они остаются зелёными без изменений; при hard cut — нужна полная переработка. Разница в стоимости: несколько часов работы.

5. **Навык уже в каноне:** SKILL.md уже описывает канон Широкова. Это значит агенты уже сейчас генерируют DSL в каноническом формате — но компилятор не умеет его полностью выполнить (`rowStyle`, `page`, `"Nx"`). Это означает, что **сегодня есть реальное несоответствие** между документацией и поведением. Быстрое добавление нового парсера (по маркеру) это исправит без обязательного удаления старого.

**Конкретный план:**
- `MxlDslV2.java` — новый POJO с полями `page`, `columnWidths` (с `"Nx"`), `rowStyle` в `Row`, `height` в `Row`.
- `MxlWriterV2.java` — writer с реализацией `rowStyle`-автозаполнения и `height`.
- Активация: если JSON содержит `"$schema": "mxl-v2"` или CLI получает `--canon shirokov` — используется V2. Иначе — V1 (текущий).
- Existing тесты зелёные.
- Новые тесты для V2 — по каждому из расхождений §2 (класс ❌/🔶).
- SPEC-xml-gen-backlog.md §8.2 уже описывает именно этот подход.
- После 1 major-версии V1 можно удалить.

## 10. Открытые вопросы для пользователя

1. **Есть ли живые JSON-файлы в старом формате?** Если в проектах потребителей (DRIVE, UT, PAM) хранятся JSON-файлы MXL-макетов в текущем формате (без `$schema`) — насколько важна их работоспособность после миграции? Это влияет на выбор hard cut vs back-compat.

2. **Когда активировать канон по умолчанию?** Текущий план SPEC-xml-gen-backlog.md §8.2: «через 1 версию». Какая версия считается «следующей major»? `0.3.0 → 1.0.0` или другая схема?

3. **`"Nx"` без `page` — допустимо?** В каноне `"Nx"` значения имеют смысл только если задан `page` (иначе неизвестна база для умножения). Нужно ли добавить валидацию «`"Nx"` требует `page`», или оставить `"Nx"` без `page` как ошибку парсера?

4. **Validator: 7 классов vs текущие коды.** После §8 нужно ли сохранить совместимость с кодами `MXL-001`..`MXL-106` (например, в CI-правилах или документации проектов) или можно заменить на классы `bad-column-index` и т.д.?

5. **auto-naming при decompile.** Алгоритм генерации имён `default`/`bold`/`bordered` по комбинации свойств — нужен конкретный маппинг (что считается `bold`, как отличить `bordered` от `bordered-right`). Это часть имплементации §8 или отдельная задача?

6. **`columnWidths` в XML.** Текущий `MxlWriter.java` не записывает индивидуальные ширины колонок в `<columns>` (только `<size>`). Нужны ли они в XML для корректной работы 1С, или платформа игнорирует ширины из Template.xml и берёт из `ColumnGroup`? Требует уточнения по поведению платформы.
