## 1. TL;DR

**Происхождение.** MXL-парсер написан самостоятельно командой steelmorgan с нуля на Java, единственным автором во всех коммитах является `steelmorgan <steelmorgan33@gmail.com>`. Иными словами, DSL проектировался по документации Широкова, а не копировался из его кода.

**Что взять прямо сейчас инкрементально:** (1) реализация `rowStyle`-автозаполнения в `MxlWriter` — DSL-поле уже есть в `MxlDsl.Row`, но `MxlWriter` его игнорирует; (2) генерация `namedItem`-блоков в XML для поддержки именованных областей через `ПолучитьОбласть()`; (3) расчёт `columnWidths` с поддержкой диапазонов (`"2-8": 40`) и пропорционального `"Nx"` синтаксиса плюс параметра `page`.

## 3. Аудит кода на следы Широкова

### 3.1. Имена сущностей

Широков использует те же термины `columns`, `fonts`, `styles`, `areas`, `rows`, `cells`, `col`, `span`, `param`, `text` потому что они соответствуют терминологии платформы 1С и объекту `SpreadsheetDocument`. Проверка grep по всем пяти MXL-файлам на ключевые слова `Широков`, `Shirokov`, `shirokov`, `cc-1c-skills`, `borrowed`, `ported from` дала **0 совпадений**.

Из 12 публичных имён верхнего уровня в `MxlDsl.java` (поля класса + поля вложенных POJO):
- 0 совпадений дословно с именами переменных из Python/PowerShell Широкова (код Широкова — скрипт с локальными переменными, у нас — типизированные POJO)
- 12 из 12 совпадают **концептуально** с JSON-DSL спецификацией (`mxl-dsl-spec.md`), сохранённой в `docs/reference/cc-1c-skills/`
- Это явное архитектурное решение: DSL формировался по спецификации Широкова как документу, не по его коду

Ключевое расхождение между нашим DSL и каноном Широкова (зафиксировано в `external-skills-mapping.md §3.1`):
- `columnWidths` у нас: `Map<String, Object>` — ключ-строка с диапазоном, значение Object (число или строка `"Nx"`)
- У Широкова: тот же формат в JSON-спецификации, но реализация поддерживает расчёт `defaultWidth` из `page` + `"Nx"` пропорций
- Разрыв: в нашем `MxlWriter.java` поле `columnWidths` объявлено в DSL (строки 27–29), но в теле `createDesigner()` оно **не используется** — компилятор его игнорирует

Итоговый счёт по именам публичного API: из 25 публичных полей `MxlDsl` (включая вложенные POJO):
- 0 полей совпадают с именами переменных из скриптов Широкова (PowerShell/Python) дословно в смысле заимствованного кода
- 25 из 25 совпадают концептуально с JSON-DSL спецификацией Широкова, поскольку DSL проектировался по этой спецификации
- 3 поля (`Row.rowStyle`, `Cell.detail`, `columnWidths`) — аддитивные расширения, декларированные в POJO но не реализованные в `MxlWriter` (см. §6а)

### 3.2. Структуры данных

`MxlDsl.java` использует `Map<String, Font>` и `Map<String, Style>` для именованных шрифтов и стилей — идентичная структура есть в спецификации Широкова. Архитектурное решение оправдано: именованные шрифты/стили — это предметная концепция (JSON DSL позволяет переиспользовать стили), а не изобретение Широкова.

`MxlDsl.Row.rowStyle: String` (строка 146) и `MxlDsl.Cell.detail: String` (строка 173) — поля, присутствующие в DSL-спецификации Широкова и перенесённые в POJO. Оба существуют в `MxlDsl.java`, но `MxlWriter.java` их не обрабатывает (`rowStyle` и `detail` нигде в теле `writeCell()` или `writeArea()` не упоминаются — `grep` по `MxlWriter.java` возвращает 0 вхождений).

### 3.3. Комментарии и докстринги

Все Javadoc-комментарии в MXL-файлах написаны на русском языке, описывают реализацию, не содержат ссылок на Широкова и не используют его терминологию за пределами общепринятой 1С-документации. Единственная внешняя ссылка в MXL-коде — `MxlDecompiler.java:19` описывает класс как «Обратная операция к MxlWriter.create()» — это внутренняя перекрёстная ссылка.

Явная ссылка на Широкова есть только в SKILL.md (не Java-код): `framework/skills/.../mxl-dsl/SKILL.md` строка 10: «Канон взят из спецификации Широкова (cc-1c-skills)».

### 3.4. Паттерны XML-генерации

Namespace-набор в `MxlWriter.java` строки 22–28:

```java
MXL_NAMESPACES.put("", "http://v8.1c.ru/8.2/data/spreadsheet");
MXL_NAMESPACES.put("style", "http://v8.1c.ru/8.1/data/ui/style");
MXL_NAMESPACES.put("v8", "http://v8.1c.ru/8.1/data/core");
MXL_NAMESPACES.put("v8ui", "http://v8.1c.ru/8.1/data/ui");
MXL_NAMESPACES.put("xs", "http://www.w3.org/2001/XMLSchema");
MXL_NAMESPACES.put("xsi", "http://www.w3.org/2001/XMLSchema-instance");
```

Этот набор полностью совпадает с namespace-шапкой из `docs/reference/cc-1c-skills/1c-spreadsheet-spec.md` строки 9–14. Совпадение объяснимо: namespace-шапка диктуется форматом 1С платформы, а не выбором разработчика. Проверить по реальному `Template.xml` из UT-проекта (упоминается в тестах `MxlValidatorTest`) — любой MXL с платформы 8.3.20–8.3.27 будет иметь идентичный набор namespace.

Порядок элементов в XML (`languageSettings` → fonts → styles → `columns` → `rowsItem` → `templateMode` → `defaultFormatIndex` → `height`) совпадает с порядком, описанным в спецификации `1c-spreadsheet-spec.md`, но **не соответствует каноническому порядку** из той же спецификации (`languageSettings` → `columns` → `rowsItem` → ... → `font` → `format`). Это означает, что MxlWriter следовал не строгому порядку из спецификации, а логическому порядку, удобному для генерации. Широков в Python тоже генерирует font/format до rowsItem — полного совпадения нет ни с кем.

**Именование XML-элементов** — MxlWriter использует стандартные 1С-имена тегов: `<rowsItem>`, `<c>`, `<i>`, `<f>`, `<tl>`, `<parameter>`, `<templateText>`, `<merge>`, `<rowMerge>`. Эти имена диктуются форматом платформы (зафиксированы в `1c-spreadsheet-spec.md`) и не являются изобретением Широкова. Аудит `MxlWriter.java` показывает полное соответствие спецификации без отклонений.

**Стиль кода** — MxlWriter написан в стиле проекта xml-gen: extends `XmlWriter`, использует `startElement`/`endElement`/`writeElement`-хелперы базового класса, `indentLevel` для форматирования. Этот стиль уникален для xml-gen и не имеет аналогов в Python-скриптах Широкова.

Использование вложенного `<c><c>...</c></c>` (cell group → cell content, строки 181–217 `MxlWriter.java`) соответствует структуре из `1c-spreadsheet-spec.md`. Именно этот паттерн описан в спецификации как «cell group → cell content».

## 4. Что у нас есть, чего нет у Широкова

Эти возможности **уникальны для нашей реализации** и будут потеряны при полной миграции на DSL Широкова без адаптации:

1. **EDT-формат в compile** (`--format designer|edt`, `MxlWriter.java:42–47`). У Широкова только Designer. Параметр уже реализован; EDT-ветка сейчас вызывает тот же `createDesigner`, но CLI-флаг сохранён для будущей полной реализации.

2. **Деструктуризация областей в decompile** (`MxlDecompiler.java:103–183`). Логика `_Before`/`_After` для строк вне именованных областей — наше расширение. У Широкова `mxl-decompile.py` (705 строк) имеет более богатую auto-naming логику (§3.5 ниже), но структурная обработка pre/post-областей оригинальна.

3. **Режим info с пагинацией** (`MxlInfoPrinter.java:355–373`). `--limit` / `--offset` параметры для длинных макетов — нашего изобретения, у Широкова нет.

4. **Интеграция в единый JAR** со всеми другими командами. Широков — отдельные скрипты. Наш `xml-gen mxl ...` вызывается единообразно с `xml-gen form ...`, `xml-gen meta ...` и т.д.

## 5. Что у Широкова есть, чего у нас нет — и можно взять СЕЙЧАС

Перечислены только фичи, **не требующие переписывания DSL**. Каждая реализуется как дополнение к существующему `MxlWriter`/`MxlDecompiler`/`MxlValidator`.

### 5.1. rowStyle-автозаполнение в MxlWriter

**Что:** когда строка задаёт `rowStyle`, компилятор должен автоматически создавать ячейки для всех колонок строки, заполняя «пустоты» ячейками с указанным стилем. Это обеспечивает сплошные рамки в табличных строках без явного перечисления каждой ячейки.

**Почему не требует изменения DSL:** поле `rowStyle` уже объявлено в `MxlDsl.Row.java:146`. Нужно только реализовать логику в `MxlWriter.writeArea()`.

**Затронутые файлы:** `MxlWriter.java` (метод `writeArea`, строки 136–174), `MxlWriterTest.java`.

**Сложность интеграции:** M. Нужно знать, какие колонки уже заняты ячейками (включая rowspan-перенос), и заполнить оставшиеся.

### 5.2. Генерация namedItem-блоков в MxlWriter

**Что:** именованные области (`ПолучитьОбласть("Заголовок")`) определяются через `<namedItem xsi:type="NamedItemCells">` в конце XML-файла. Сейчас `MxlWriter` не генерирует `namedItem`-блоки. Это означает, что сгенерированный Template.xml не содержит именованных областей на XML-уровне, хотя DSL задаёт `areas[].name`.

**Связь с DSL:** `MxlDsl.Area.name` уже существует. Нужно генерировать соответствующий `<namedItem>` после `<rowsItem>` блоков с правильными `beginRow`/`endRow`.

**Затронутые файлы:** `MxlWriter.java` (добавить метод `writeNamedItems`).

**Сложность интеграции:** S–M. Нужно отслеживать строковые индексы областей в процессе генерации (уже вычисляется в `writeArea`).

### 5.3. columnWidths с диапазонами и page/Nx

**Что:** DSL-спецификация поддерживает ключи вида `"2-8": 40`, `"5,7,9": 30` и значения `"Nx"` (пропорции). Параметр `page: "A4-landscape"` задаёт суммарную ширину, из которой `defaultWidth` вычисляется автоматически.

**Почему не требует изменения DSL:** поле `columnWidths: Map<String, Object>` уже объявлено в `MxlDsl.java:29`. Нужно добавить поле `page` в `MxlDsl` и реализовать обработку в `MxlWriter.createDesigner()`.

**Затронутые файлы:** `MxlDsl.java` (новое поле `page`), `MxlWriter.java` (обработка `columnWidths` и расчёт `defaultWidth`).

**Сложность интеграции:** M. Парсинг ключей диапазонов прямолинеен; логика `"Nx"` — несколько строк арифметики.

### 5.4. Auto-naming стилей в MxlDecompiler

**Что:** при decompile из XML в JSON Широков присваивает стилям осмысленные имена (`default`, `bold`, `header`, `bordered`, `bordered-right`, `bold-right`, `border-top`) на основе комбинации свойств — вместо числовых индексов. Текущий `MxlDecompiler` использует числовые id шрифтов/стилей как есть.

Соответствующий паттерн зафиксирован в `framework/skills/.../mxl-dsl/SKILL.md:163`: «Шрифты и стили получают автоматические осмысленные имена».

**Сложность интеграции:** M. Нужно пост-обработать собранные `fonts`/`styles` Map и переименовать ключи по хешу свойств.

### 5.5. rowStyle-компрессия в MxlDecompiler

**Что:** если все пустые ячейки строки имеют одинаковый стиль, он сворачивается в `rowStyle`, а пустые ячейки убираются из вывода. Зафиксировано в SKILL.md:164.

**Сложность интеграции:** S–M. Детектировать шаблон в `decompileRows()` и трансформировать выходной объект строки.

### 5.6. format-строки в MxlValidator

**Что:** Широков проверяет формат-строки ячеек (например, `"ЧЦ=15; ЧДЦ=2"`) на синтаксис. Текущий `MxlValidator` проверяет выравнивание (MXL-101, MXL-102), merge (MXL-103), font height (MXL-106), но не проверяет корректность `<format>` строк.

**Сложность интеграции:** S. Добавить проверку MXL-107 в `validateSemantic()`.

## 6. Что требует полной миграции (НЕ берётся сейчас)

Фичи канона Широкова, принципиально несовместимые с текущим DSL без миграции. Детальное сравнение — в `mxl-canon-comparison.md`.

- **Индексация колонок**: `col` 1-based у нас, 0-based у Широкова в XML (мы конвертируем в `MxlWriter.java:184`: `cell.getCol() - 1`; Широков в DSL тоже использует 1-based)
- **Positional cell без col**: у Широкова `<i>` в XML необязателен, позиция = предыдущая + 1; у нас `col` в DSL обязателен; `MxlDecompiler.java:232–234` уже восстанавливает 1-based при decompile, но `MxlWriter` не поддерживает positional без `col`
- **Дополнительные наборы колонок** (`columnsID`): у Широкова есть поддержка нескольких независимых grid-ов (для сложных УПД). В нашем DSL это поле `MxlDsl.java` не описано, в `MxlWriter` нет логики. Это не аддитивная фича — требует расширения DSL
- **Область типа Columns / Rectangle**: наш `MxlDecompiler` парсит только `Rows`-области (строки 115–116), Rectangle/Columns игнорируются. `MxlWriter` не генерирует `namedItem` вообще (см. §5.2)
- **Фон ячеек, рисунки (Drawing), штрихкоды**: зафиксированы как ограничения в mxl-dsl-spec.md строка 158

## 6а. Детальный разрыв между MxlWriter и каноном: что в DSL есть, но не реализовано

Это не про DSL-расхождения (которые в mxl-canon-comparison.md), а про **внутренний долг в MxlWriter**: поля объявлены в `MxlDsl.java`, JSON их принимает, но компилятор их молча игнорирует.

| Поле в MxlDsl | Строки в MxlDsl.java | Обработка в MxlWriter.java | Статус |
|---------------|---------------------|---------------------------|--------|
| `columnWidths` | 27–29 | Не используется нигде | ❌ Игнорируется |
| `Row.rowStyle` | 146 | Не упоминается в writeArea/writeCell | ❌ Игнорируется |
| `Cell.detail` | 173 | Не упоминается в writeCell | ❌ Игнорируется |
| `Cell.span` | 169 | `writeElement("merge", span-1)` в строках 207–209 | ✅ Реализовано |
| `Cell.rowspan` | 170 | `writeElement("rowMerge", rowspan-1)` в строках 212–214 | ✅ Реализовано |
| `Cell.template` | 175 | `writeCellTemplate()` строки 244–248 | ✅ Реализовано |
| `Font.underline` | (строка в Font inner class) | `writeElement("underline", "true")` строки 301–303 | ✅ Реализовано |
| `Font.strikeout` | (строка в Font inner class) | `writeElement("strikeout", "true")` строки 305–307 | ✅ Реализовано |
| `Style.format` | 103 | `writeElement("format", ...)` строки 366–369 | ✅ Реализовано |
| `defaultWidth` | 21 | `writeElement("width", ...)` строки 96–99 | ✅ Реализовано |

Также полностью отсутствует генерация:
- `<namedItem>` блоков (именованных областей) — `MxlWriter.java` не содержит ни одного вызова `writeElement("namedItem", ...)`
- `<height>` для строк (задаётся через `<format>` в XML, но `Row.height` из DSL не транслируется)
- `<merge>` глобальных объединений (используется для `<r>-1</r>` сплошных объединений колонок)

Сверка по `MxlWriterTest.java`: тест `testMinimalMxl` проверяет наличие `<templateMode>true</templateMode>`, `<height>1</height>` (общее число строк), `<index>0</index>`, `<tl>` — но ни один тест не проверяет наличие `<namedItem>` блоков. Это означает, что отсутствие `namedItem` не детектируется автоматически.

## 8. Открытые вопросы

1. **namedItem без MxlWriter**: можно ли использовать `xml-gen mxl compile` с текущей реализацией для реальной печатной формы, у которой BSL обращается к `ПолучитьОбласть()`? Предположительно нет — платформа не найдёт именованных областей. Нужна проверка на UT-проекте. Если подтвердится, что `namedItem` обязателен — это баг P0, не enhancement.

2. **rowStyle в decompile**: `MxlDecompiler` при decompile не сворачивает одинаковые стили в `rowStyle`. Если круговой тест (compile → decompile → compile) даёт разный JSON — это потенциальный источник drift. Нет golden-теста для roundtrip.

3. **Статус EDT-ветки**: `MxlWriter.java:46` — EDT вызывает тот же `createDesigner`. Формат EDT для MXL (`.mxlx`) отличается от Designer или нет? Нет тестов и нет подтверждённой спецификации в `1c-spreadsheet-spec.md`. Широков только Designer-формат поддерживает, EDT-ветка — наше расширение, статус которого не проверен.

4. **Высота строки**: `MxlDsl.Row.height` объявлен (строка 145 `MxlDsl.java`), но `MxlWriter.writeArea()` его не использует. Высота строки в XML задаётся через `<formatIndex>` строки на элемент `<format><height>N</height></format>`. Реализация требует добавления в палитру форматов на лету.

5. **Провенанс decompile.py Широкова**: `xml-gen-expansion-plan-2026-03-09.md §Phase 1` указывает 705 строк Python как референс для нашего декомпилятора. Не ясно, были ли конкретные алгоритмические решения взяты оттуда или реализованы независимо. Автор коммита `117c331` — steelmorgan (Claude Opus 4.6). Прямое изучение Python-исходника возможно через `WebFetch` на `github.com/Nikolay-Shirokov/cc-1c-skills`.
