# Манифест ретиринга правил и навыков 1С-агентного фреймворка

> Планирование. Цель — перевести always-on правила из «всё всем каждый запрос» в модель
> «guardrails + маленькие триггеры → ленивые навыки». Принцип конструктора: каждая пара
> «правило-триггер + навык» — отдельная сущность, ставится по необходимости.

## Главный критерий (по нему классифицировано всё)

По каждому правилу/навыку один вопрос:
**«Нужно ли его ВСЕГДА видеть целиком — или достаточно инструкции „прочитай, если сработал триггер"?»**

| Категория | Что значит | Always-on? |
|---|---|---|
| **GUARD** | guardrail / мета / диспетчер — видеть всегда целиком | да, правило целиком |
| **TRIG** | маленькое правило-триггер «событие → навык X» + ленивый навык-тело | да (только триггер) |
| **SKILL** | тело-процедура | нет (ленивый навык) |
| **GOAL** | навык, вызываемый по очевидному намерению | нет, без правила |
| **WF** | запуск предписан фазой full-cycle/orchestrator | нет (триггер в workflow) |

Решения по итогам обсуждения:
- `globs` НЕ используем (нет правил, привязанных к пути).
- Триггеры НЕ сливаем в одно правило (модульность; каждая пара отдельно).
- Маркер размещения — frontmatter `alwaysApply` (true → в always-on каталог; иначе → только component_map).
- Хуки-проверки (enforcement) — отдельный следующий этап, в этот манифест не входят.
- Кросс-харнес: целимся на Claude CLI + Codex CLI (похожая структура), тяжёлый контракт не нужен.

## §6. Обоснование п.3 (по принципам)

Критерий «видеть всегда целиком или читать по триггеру» + «кто использует» + «durability через компакт, не раздувая других»:

- **quick-fix** — короткая разовая процедура для простого таска, применяется один раз, компакт переживёт редко → **read-on-trigger = SKILL**. Триггер — framework-bootstrap.
- **full-cycle + orchestrator** — это НЕПРЕРЫВНЫЙ операционный манинг оркестратора: он опирается на него каждый ход весь сложный таск, который заведомо пересекает несколько компактов. Ленивый навык, загруженный раз, сожмётся → оркестратор теряет собственный манинг посреди задачи. → нужен **durable** канал. Но это **main-only** (сабагенты orchestrator.md не используют) → нельзя класть в always-on (раздуем всех сабагентов — ровно проблема, которую решаем).
  - **Ограничение харнеса:** оркестратор ОБЯЗАН быть ГЛАВНЫМ агентом — сабагент не может стартовать сабагентов (prompt.ts:282). Поэтому это НЕ субагентный профиль, а **профиль главного потока** (`--agent orchestrator` / `mainThreadAgentDefinition`).
  - Профиль главного потока: durable every-request, главный поток сохраняет право спавнить сабагентов, и при этом сабагенты его НЕ наследуют (runAgent.ts:508 — у сабагента свой `agentDefinition`, не главного потока). Это и есть искомый durable-канал «main-only».
  - Требует: запускать главную сессию под `--agent orchestrator` (определение агента с операционным манингом в systemPrompt). Сейчас оркестратор = главный агент без явного профиля, управляется CLAUDE.md.
  - Варианты, если `--agent` не используем: (A) держать манинг в CLAUDE.md — durable для main, но сабагенты наследуют (раздувание этого одного большого документа); (B) SKILL + якорь framework-bootstrap — invoked_skills даёт per-agent ≤25k восстановление (лучше file-restore top-5 у read-правила), сабагенты не наследуют, но риск частичной потери на компакте у огромного документа (критичное — в голову ≤25k, детали в references/).
  - В мультиагентном фреймворке, где суб-оркестратор может спавнить, сработал бы и субагентный профиль — но не в этом харнесе.

## §6.1. Оркестратор как профиль: два варианта оформления

Манинг оркестратора (orchestrator + full-cycle) кладём в **системный промпт главного потока**. Сборка системного промпта (проверено `QueryEngine.ts:321-325`):

```
systemPrompt = [ customPrompt ?? defaultSystemPrompt , memoryMechanics? , appendSystemPrompt? ]
```

Отсюда ровно два способа доставить манинг durable-каналом. CLAUDE.md (канал `getUserContext`) в обоих случаях работает поверх — он отдельный и тоже durable.

| | **Вариант A — `--agent orchestrator`** | **Вариант B — `--append-system-prompt`** |
|---|---|---|
| Что делает | `customPrompt` **ЗАМЕНЯЕТ** `defaultSystemPrompt` (`buildEffectiveSystemPrompt`: `agentSystemPrompt ? [agentSystemPrompt] : … : defaultSystemPrompt`) | манинг **ДОБАВЛЯЕТСЯ** строкой поверх базового `defaultSystemPrompt` (`QueryEngine.ts:324`) |
| Базовый промпт Claude Code | теряется (кроме proactive/KAIROS-режима, где append) | сохраняется целиком |
| Профиль должен быть | **самодостаточным** (вся идентичность + инструменты + поведение оркестратора внутри) | **дельтой** (только надстройка «ты оркестратор», базовое поведение даёт дефолт) |
| Наследование сабагентами | НЕ наследуется (у сабагента свой `agentDefinition`, runAgent.ts:508) | НЕ наследуется (`appendSystemPrompt` пробрасывается, но сабагент собирает свой системный промпт; в этом харнесе сабагенты orchestrator.md не используют) |
| Право спавнить сабагентов | есть (главный поток) | есть (главный поток) |
| Durability через компакт | every-request, переживает | every-request, переживает |
| Риск | профиль обязан переписать/воспроизвести нужные части базового промпта — иначе потеря дефолтного поведения | манинг не может переопределить базовое поведение, только дополнить |
| Когда выбирать | нужна полная кастомная идентичность оркестратора, базовый промпт мешает | базовый промпт нужен как есть, оркестратор — тонкая надстройка (рекомендуемый дефолт: проще, меньше риск) |

Третий путь (для полноты): **proactive/KAIROS-режим** — там agent-профиль не заменяет, а добавляется к базовому. Это частный случай варианта A с семантикой «append» и в обычном запуске не используется.

**Рекомендация:** по умолчанию — **вариант B** (`--append-system-prompt` с дельта-манингом оркестратора): сохраняет базовое поведение Claude Code, требует минимум сопровождения, durable, main-only. Вариант A — когда понадобится жёстко кастомная идентичность оркестратора без базового промпта.

## §7. Смысловая связанность: bootstrap ↔ orchestrator ↔ quick-fix/full-cycle

Перепроверка маршрутизации после переразметки (по факту ссылок в файлах).

**Текущие ссылки (как есть):**
- `framework-bootstrap` (always-on): таблица «когда что грузить» → простая задача = `quick-fix.md`, сложная = `orchestrator.md`; «если сомневаешься — грузи orchestrator.md» (framework-bootstrap.md:15-22).
- `quick-fix` → эскалация: «зафиксировать состояние → передать оркестратору → full-cycle» (quick-fix.md:33).
- `orchestrator` использует `full-cycle` как фазовый манинг.

**Целевые места жительства:**
- `framework-bootstrap` = **always-on правило** (GUARD/диспетчер) — нужен любой сессии, чтобы классифицировать.
- `orchestrator` + `full-cycle` = **профиль главного потока** (§6.1) — НЕ загружаемый документ, а идентичность сессии на старте.
- `quick-fix` = **SKILL** (ленивый, грузится по триггеру из bootstrap).

**Найденная нестыковка (root cause, не симптом):**
Bootstrap и quick-fix ссылаются на orchestrator/full-cycle как на **загружаемые `.md`-документы** («загружай `orchestrator.md`»). В целевой модели это **профиль launch-time**, а не документ, который можно «подгрузить» посреди сессии. Если сессия НЕ запущена как оркестратор (обычная ad-hoc-сессия), она физически не может «загрузить orchestrator.md» и стать оркестратором — профиль ставится только на старте (`--agent` / `--append-system-prompt`).

**Разрешение (модель «ты либо оркестратор-сессия, либо лёгкая сессия»):**
1. **framework-bootstrap** остаётся диспетчером для любой сессии, но текст маршрутизации переписать:
   - простая задача → подгрузи навык `quick-fix` (Skill-тул) и иди по нему;
   - сложная задача → **это работа оркестратора**. Если ты УЖЕ оркестратор (профиль загружен — манинг orchestrator/full-cycle в системном промпте) → иди по нему. Если ты НЕ оркестратор → эскалация: переоткрыть/запустить сессию под профилем оркестратора (`--agent orchestrator` или `--append-system-prompt`). Не «загружать orchestrator.md» в текущую не-оркестраторную сессию.
2. **Типовой режим работы** в этом проекте: главная сессия по умолчанию ЗАПУСКАЕТСЯ как оркестратор (профиль есть на старте). Тогда:
   - bootstrap-классификация = первый шаг самого оркестратора;
   - full-cycle уже в его системном промпте (профиль) — для сложного таска ничего «грузить» не нужно;
   - quick-fix оркестратор подгружает навыком для простого таска;
   - «эскалация quick-fix → full-cycle» = оркестратор у себя же поднимает фазовый манинг (он уже в профиле), не «передаёт» во внешний документ.
3. **Якорность сохранена:** framework-bootstrap always-on и переживает компакт → ссылка на профиль оркестратора и навык quick-fix достижима после любого сжатия. Профиль (orchestrator+full-cycle) durable сам по себе (системный промпт). quick-fix восстановим через каталог навыков (хук SessionStart compact) + триггер в bootstrap.

**Связанность после правок — когерентна:**
- bootstrap (always-on, router) → quick-fix (skill, lazy) ✓ достижимо;
- bootstrap (router) → orchestrator (профиль) ✓ через «ты уже оркестратор / иначе старт под профилем», не через загрузку документа;
- orchestrator → full-cycle ✓ оба в одном профиле, всегда вместе;
- quick-fix → эскалация во full-cycle ✓ как поднятие фазового манинга внутри оркестратора, не как передача во внешний `.md`.

**Что переписать при реализации (фиксируется как долг §3):**
- `framework-bootstrap`: убрать «загружай orchestrator.md», заменить на «сложная → работа оркестратора (профиль); не-оркестратор → эскалация на запуск под профилем».
- `quick-fix` (будущий навык): «эскалация → передать оркестратору» уточнить: оркестратор поднимает full-cycle из своего профиля, а не из внешнего документа.
- `depends_on` у bootstrap (`framework/workflows/orchestrator.md`, `quick-fix.md`) — пометить, что orchestrator/full-cycle теперь профиль (component_map), а не загружаемое правило.

## §7.1. Пересмотр: вариант B (append) как УНИВЕРСАЛЬНЫЙ старт

Допущение: главная сессия **всегда** запускается профилем оркестратора в режиме `--append-system-prompt` (вариант B, §6.1). Тогда манинг orchestrator+full-cycle всегда в системном промпте main-потока (durable, каждый запрос, поверх базового промпта Claude Code). Это меняет роли инструкций.

**Главное следствие:** главная сессия = ВСЕГДА оркестратор. Дихотомия §7 «оркестратор-сессия / лёгкая сессия» **схлопывается** — штатной не-оркестраторной main-сессии нет.

**Перераспределение ответственности:**

| Инструкция | Роль при B-старте | Кто видит |
|---|---|---|
| Классификация/роутинг (ex-bootstrap) | первый шаг оркестратора → **в профиле** (durable) | main (профиль) |
| orchestrator + full-cycle (манинг) | **в профиле** (append поверх базы) | main (профиль), НЕ сабагенты |
| quick-fix | ленивый навык, профиль вызывает по классификации | main по требованию |
| GUARD (db/xml/protected/capability) | always-on правило | main + сабагенты (канал A) |
| TRIG (триггеры навыков) | always-on правило | main + сабагенты (канал A) |
| framework-bootstrap (как always-on правило) | **тонкий стаб** (ориентация + fallback + кросс-харнес), детальный роутинг ушёл в профиль | main + сабагенты (минимально) |

**Почему `framework-bootstrap` низводится до стаба, а не остаётся тяжёлым GUARD:**
- для main роутинг уже durable в профиле → тяжёлое always-on правило дублирует;
- для сабагентов диспетчер бесполезен (они исполняют делегированную фазу, не маршрутизируют) → его наследование через канал A = ровно то раздувание, которое убираем.
- → детальный роутинг и манинг в профиль; в always-on остаётся ~5-строчный стаб: «это 1С-фреймворк; если у тебя нет манинга оркестратора в системном промпте — ты неверно сконфигурирован / лёгкая сессия: простая задача → навык quick-fix, сложная → нужен профиль оркестратора». Стаб = safety-net на случай запуска без профиля + ориентир.

**Профиль оркестратора = единый durable-якорь (вместо bootstrap-правила):**
- quick-fix достижим: профиль → Skill-тул;
- WF-навыки достижимы: фазы full-cycle в профиле называют их при делегировании;
- резолв Codex F-04 (reachability WF-навыков) переезжает с «always-on bootstrap» на «профиль оркестратора» — остаётся закрытым.

**Чистая цель always-on канала A при B-старте:** GUARD + TRIG + тонкий стаб bootstrap. Манинга оркестрации и детального роутинга в канале A нет → сабагенты их не наследуют. Это итог леннее, чем в §4 (минус тело диспетчера из наследуемого канала).

**Картина сабагента:** системный промпт = свой ролевой профиль (analyst/developer/…); канал A = CLAUDE.md + GUARD + TRIG + стаб. Манинг оркестратора и роутинг — не видит. Корректно.

**Открытый вопрос (кросс-харнес):** `--append-system-prompt` — механизм Claude CLI. Codex CLI грузит инструкции через config.toml / AGENTS.md. На Codex манинг оркестратора нужен другой носитель. Тонкий портативный `framework-bootstrap`-документ (или секция AGENTS.md) сохраняет роль кросс-харсенного носителя роутинга. Решение: bootstrap-стаб остаётся портативным (component_map + always-on тонко), детальный манинг дублируется в харсенный носитель каждой среды. **Требует решения пользователя:** держать ли один портативный bootstrap для обеих сред или раздельные носители.

## §7.2. Lead vs Оркестратор: расщепление идентичности main-потока

Уточнение §7.1. Нельзя грузить в профиль ВЕСЬ `orchestrator.md` (с абсолютным запретом «NOT an executor») и одновременно разрешать main делать quick-fix руками — агент станет самопротиворечив. Главный агент — это **Lead**, надевающий одну из шляп, а не «всегда оркестратор».

**Коллизия:** `orchestrator.md` запрещает оркестратору исполнять что-либо («Writing code… Replacing any subagent yourself — even if it seems faster»). Если этот манинг always-on и при этом Lead «выбирает self для short-цикла» — прямое противоречие. Без guard это скользкий склон: «тривиальное» раздувается, дисциплина разделения (TDD, кросс-ревью) сгнивает.

**Три слоя манинга:**

| Слой | Содержание | Где | Durability |
|---|---|---|---|
| **1. Lead/диспетчер** | классификация; выбор цикла short/full; для short — self vs delegate; границы выбора | профиль (always) | durable, каждый запрос |
| **2. Дисциплина оркестрации** | «не исполняю — делегирую», routing, gates, review-cycle, BUG-routing, фильтр эскалации | профиль (always) | durable; **активна только в full-режиме** |
| **3. Детальные процедуры** | quick-fix (шаги), full-cycle (фазовая механика, artifact handover) | по ссылке, read-on-choice | лениво; форма фаз + дисциплина уже durable в слое 2 |

**Ключевое уточнение к §7.1:** в профиль идёт НЕ тело `full-cycle.md` целиком, а слой 2 (дисциплина) + форма фаз. Сама фазовая механика (слой 3) читается лениво по входу в фазу. Это **леннее**, чем «orchestrator+full-cycle телами в профиль» (§1, §6) — тело full-cycle деградирует до read-on-choice, durable остаётся только дисциплина.

**Запрет «не исполнять сам» scoped к full-режиму, НЕ ко всему main.** В режиме Lead/quick-fix main исполняет сам или делегирует одного сабагента — это НЕ нарушение, потому что он в этот момент не «оркестратор full-цикла».

**Guard на self-путь (MUST, иначе склон):**
- self-исполнение разрешено ТОЛЬКО в границах quick-fix: `<20 строк, 1 файл, без новых объектов метаданных, без архитектурных решений` (критерии уже зафиксированы в quick-fix.md/bootstrap);
- превышение любого критерия → принудительный переход в full-цикл (делегирование), self запрещён;
- verify-шаг (диагностика/синтаксис/тесты, quick-fix step 3) **обязателен даже для self** — единственная компенсация отсутствия кросс-ревью в quick-fix.

**Итог:** «оркестратор выбирает self vs delegate» (предложение пользователя) принято как **решение Lead-слоя под жёстким лимитом quick-fix**, а не как право оркестратора нарушать свой запрет на исполнение. bootstrap → растворяется в слое 1.

## §7.3. Портативный само-промотирующий bootstrap (кросс-харнес мост) — ЗАКРЫВАЕТ открытый вопрос §7.1

Закрывает кросс-харнес-развилку §7.1 («один портативный bootstrap vs раздельные носители»): выбран **один портативный**. Профиль становится **необязательным** — это эмуляция профиля через само-промотирующее always-on правило-триггер.

**Идея:** тонкое always-on правило (канал A на Claude / AGENTS.md на Codex / rules на Cursor) с условной веткой: главный поток, у которого манинга оркестратора нет в контексте, **сам вытягивает** его чтением. Триггер = «я главный и манинга нет», payload = манинг оркестратора (слои 1-2 §7.2). Сабагенты ветку пропускают.

**Две точки доставки, одно правило:**
- харнес С профилем (Claude, запуск под флагом `--append-system-prompt` / `--agent` — пользователь делает так) → манинг пред-загружен в системный промпт → правило no-op (тело уже в контексте);
- харнес БЕЗ профиля (Codex/Cursor) → правило само читает манинг; durability — через ре-триггер (стаб переживает компакт, тело перечитывается при потере).

**Критический риск и исправленное условие (НЕ ключевать на убеждении):**
после компакта «верю, что я оркестратор» (состояние задачи) **выживает в сводке**, а **тело манинга — вытесняется**. Условие «не идентифицируешь себя оркестратором → читай» даст ложный пропуск: агент по сводке скажет «я оркестратор» → пропустит чтение → тела нет. Поэтому ключуем на **фактическом наличии тела манинга в текущем контексте**, с ре-срабатыванием в точках потери:

```
- Если ты сабагент (системный промпт называет роль: analyst/developer/…) → правило не для тебя, выход.
- Если тело манинга оркестратора СЕЙЧАС в контексте (профиль ИЛИ прочитан в этой сессии после последнего компакта) → действуй как Lead/оркестратор.
- Иначе (главный поток, тела манинга в контексте НЕТ — старт ИЛИ потеряли после компакта) → прочитай <манинг-оркестратора> сейчас, затем действуй.
```

Точки срабатывания: старт сессии, **после компакта**, возобновление из `orchestrator-context.md`.

**Подстраховка само-ID:**
- Claude CLI — мягкую модель-само-ID подкрепить жёстким хук-guard по `agent_id` (сабагент/main различаются кодом: agent_id присутствует у сабагента; см. tools/hooks/claude-inject-skill-catalog.sh);
- профиль-харнесы — только суждение модели по своему системному промпту (мягко, но работает: у сабагента профиль явно называет роль).

**Решение пользователя (зафиксировано):** делаем портативный само-промотирующий bootstrap (работает везде); на Claude дополнительно запуск под флагом, подгружающим роль оркестратора в системный промпт главного агента → там правило вырождается в no-op. Кросс-харнес-вопрос §7.1 — **закрыт**.
