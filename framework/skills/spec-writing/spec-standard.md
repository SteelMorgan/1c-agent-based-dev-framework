# Навык написания спецификаций (SDD)

---
name: spec-writing
description: Обучает LLM-агента писать спецификации для задач разработки 1С в формате SDD (Spec-Driven Development). Использовать при создании спек, технических заданий, ревью требований или когда пользователь просит описать задачу перед реализацией.
---

## 1. Назначение

Этот навык учит агента писать структурированные спецификации для задач разработки на 1С в формате **SDD (Spec-Driven Development)** — спецификация до разработки.

**Зачем нужны спеки в агентной разработке:**

- **Разделение ответственности**: аналитик/пользователь формулирует ЧТО, агент реализует КАК. Спека — контракт между ними.
- **Снижение ошибок**: явные требования и критерии приёмки уменьшают недопонимание и переделки.
- **Ревью**: спека позволяет проверить решение до написания кода.
- **Документация**: спека становится основой для ADR и истории решений.

---

## 2. Когда нужна спека

| Тип задачи | Нужна спека | Обоснование |
|------------|-------------|-------------|
| **Новая функциональность** | **MUST** | Всегда. Фиксирует scope, требования, альтернативы и решение. |
| **Исправление бага с архитектурным влиянием** | **MUST** | Изменение структуры данных, интерфейсов или поведения требует обоснования. |
| **Простое исправление бага** | **MAY** | Можно ограничиться описанием в коммите, если изменение локально и понятно. |
| **Рефакторинг** | **SHOULD** | Рекомендуется для крупного рефакторинга; мелкий — без спеки. |

---

## 3. Шаблон спецификации

### Заголовок и метаданные

```markdown
# SPEC-NNN: [Краткое название]
Status: Draft | Review | Approved | Implemented
Date: YYYY-MM-DD
```

- **SPEC-NNN**: уникальный идентификатор (например, SPEC-001).
- **Status**: Draft — в работе; Review — на ревью; Approved — одобрена; Implemented — реализована.
- **Date**: дата последнего значимого изменения.

---

### Context and Problem Statement

**Что писать:** Контекст и формулировка проблемы.

**Как заполнять:**
- Опишите, **КТО** сталкивается с проблемой (роль, пользователь).
- Опишите, **ЧТО** не работает или чего не хватает.
- Кратко — зачем это нужно бизнесу.

**Типичные ошибки:**
- Слишком общее ("нужно улучшить систему").
- Сразу решение вместо проблемы ("нужно добавить документ" — это решение, а не проблема).
- Отсутствие контекста (кто, когда, при каких условиях).

---

### Requirements (RFC 2119)

**Что писать:** Формальные требования с использованием ключевых слов MUST, SHOULD, MAY, MUST NOT.

**Как заполнять:**
- Разбейте на подразделы: MUST / SHOULD / MAY / MUST NOT.
- Каждое требование — одна чёткая фраза.
- Избегайте "должен" без ключевого слова — используйте RFC 2119.

**Типичные ошибки:**
- Смешение уровней обязательности.
- Размытые формулировки ("система должна быть удобной").
- Отсутствие MUST для критичных требований.

---

### Scope (In scope / Out of scope)

**Что писать:** Явная граница задачи.

**Как заполнять:**
- **In scope**: что входит в задачу.
- **Out of scope**: что НЕ входит (защита от scope creep).

**Типичные ошибки:**
- Пустой Out of scope (риск поползновения границ).
- Неявные допущения ("очевидно, что...") — выносите в Out of scope.

---

### Considered Options

**Что писать:** Рассмотренные варианты решения.

**Как заполнять:**
- Минимум **2 альтернативы** (часто 3–4).
- Для каждой: краткое описание, плюсы, минусы.
- Таблица сравнения при необходимости.

**Типичные ошибки:**
- Только один вариант (нет анализа).
- Необъективное сравнение (рекомендуемый вариант идеален, остальные — плохие).

---

### Decision Outcome

**Что писать:** Выбранное решение и его последствия.

**Как заполнять:**
- Таблица: вариант → выбран (да/нет).
- **Consequences Good**: положительные последствия.
- **Consequences Bad**: отрицательные последствия и риски.

**Типичные ошибки:**
- Обоснование в стиле "потому что лучше" без аргументов.
- Игнорирование негативных последствий.

---

### Technical Design

**Что писать:** Техническая реализация.

**Подразделы:**

**Metadata Objects (создаёт пользователь):**
- Справочники, документы, отчёты, обработки — что нужно создать в конфигураторе.
- Реквизиты, табличные части, формы.

**Modules (пишет агент):**
- Какие модули реализует агент: модуль объекта, модуль менеджера, модуль формы и т.д.
- Основные алгоритмы, вызовы API.

**Data Flow:**
- Схема данных: откуда данные приходят, куда уходят.
- Интеграции, обмены.

**Типичные ошибки:**
- Смешение задачи пользователя (метаданные) и задачи агента (код).
- Отсутствие связи с требованиями (Requirements).

---

### Test Plan (TDD)

**Что писать:** План тестирования, ориентированный на TDD.

**Как заполнять:**
- Для каждого **MUST** — минимум один тест/сценарий.
- Учтены граничные случаи (пустые значения, нули, ошибки).
- Positive и negative тесты.

**Типичные ошибки:**
- Тесты только для "счастливого пути".
- Нет соответствия MUST ↔ тест.

---

### Open Questions

**Что писать:** Открытые вопросы, требующие решения перед реализацией.

**Как заполнять:**
- Вопрос + кто должен ответить (аналитик, заказчик, архитектор).
- Закрытые вопросы переносятся в Decision Log.

---

### Decision Log (ADR)

**Что писать:** Лог решений в формате ADR.

**Как заполнять:**
- Дата, краткое описание решения, обоснование.
- Хронологический порядок.

---

## 4. Правила использования RFC 2119

| Ключевое слово | Значение | Пример в контексте 1С |
|----------------|----------|------------------------|
| **MUST** | Обязательно. Без этого задача не считается решённой. | «Документ MUST содержать реквизит Организация.» |
| **SHOULD** | Настоятельно рекомендуется. Значительно улучшает результат. | «Форма SHOULD отображать остатки при выборе номенклатуры.» |
| **MAY** | Допустимо. Nice to have. | «Отчёт MAY поддерживать экспорт в Excel.» |
| **MUST NOT** | Запрещено. Явное ограничение. | «Обработка MUST NOT изменять данные без подтверждения пользователя.» |

### Примеры в контексте 1С

**MUST:**
- Документ поступления MUST формировать движения по регистру остатков.
- При проведении document MUST проверять заполнение всех обязательных реквизитов.

**SHOULD:**
- Форма документа SHOULD показывать предупреждение при изменении уже проведённого документа.
- Отчёт SHOULD использовать параметры сессии при формировании.

**MAY:**
- Справочник MAY поддерживать иерархию.
- Форма MAY иметь дополнительную панель инструментов.

**MUST NOT:**
- Модуль MUST NOT содержать прямых обращений к таблицам СУБД в обход API платформы.
- Обработка MUST NOT выполнять длительные операции в основном потоке без индикации прогресса.

---

## 5. Критерии качества спеки (для ревьюера)

Чеклист для оценки качества спецификации:

- [ ] **Context** описывает КТО имеет проблему и ЧТО не работает.
- [ ] Каждое **MUST** имеет соответствующий тест в **Test Plan**.
- [ ] **Scope** явно указывает, что НЕ входит (Out of scope).
- [ ] **Considered Options** содержит минимум 2 альтернативы.
- [ ] **Decision** имеет чёткое обоснование (не "потому что лучше").
- [ ] **Technical Design** разделяет задачи пользователя (метаданные) и агента (код).
- [ ] Нет противоречий между разделами.
- [ ] Нет неоднозначных требований — использованы ключевые слова RFC 2119.

## 6. Примеры

### Пример 1: Простая спека (новый отчёт)

```markdown
# SPEC-001: Отчёт «Остатки по складам»
Status: Approved
Date: 2025-02-11

## Context and Problem Statement

Менеджер склада не может быстро увидеть текущие остатки номенклатуры по складам 
в разрезе периодов. Сейчас данные приходится собирать из нескольких отчётов вручную.

**Кто:** Менеджер склада.  
**Проблема:** Отсутствует единый отчёт по остаткам.  
**Цель:** Дать быстрый доступ к остаткам по складам за выбранный период.

## Requirements (RFC 2119)

### MUST
- Отчёт MUST отображать остатки номенклатуры по складам на выбранную дату.
- Отчёт MUST иметь отбор по складу и дате.
- Отчёт MUST использовать только стандартные регистры (остатков).

### SHOULD
- Отчёт SHOULD формироваться за время не более 5 секунд при объёме до 10 000 позиций.

### MAY
- Отчёт MAY поддерживать экспорт в Excel.

### MUST NOT
- Отчёт MUST NOT изменять данные в базе.

## Scope

**In scope:** Отчёт в виде внешней обработки или отчёта конфигурации.  
**Out of scope:** История движения, резервирование, прогнозирование — не входят.

## Considered Options

| Вариант | Описание | Плюсы | Минусы |
|---------|----------|-------|--------|
| A | Внешняя обработка | Быстро, не требует обновления конфигурации | Нет в меню, раздача пользователям |
| B | Отчёт в конфигурации | Единообразие, меню | Требует обновления |

## Decision Outcome

Выбран вариант B — отчёт в конфигурации.

**Consequences Good:** Централизованное размещение, версионность.  
**Consequences Bad:** Необходимо обновление конфигурации при доработке.

## Technical Design

### Metadata Objects (создаёт пользователь)
- Отчёт «ОстаткиПоСкладам».
- Реквизиты: Склад, ДатаОстатков.
- Схема компоновки данных.

### Modules (пишет агент)
- Модуль отчёта: формирование запроса, настройка СКД.

### Data Flow
Запрос к регистру остатков → СКД → вывод на форму.

## Test Plan
- [ ] Остатки совпадают с регистром на выбранную дату.
- [ ] Пустой склад — пустой результат.
- [ ] Дата в будущем — корректная обработка (пустой или 0).
```

### Пример 2: Сложная спека (документ с проведением)

```markdown
# SPEC-002: Документ «Перемещение товаров»
Status: Review
Date: 2025-02-11

## Context and Problem Statement

Необходимо оформить перемещение товаров между складами. Сейчас перемещения 
оформляются двумя документами (списание и поступление), что создаёт риски 
несогласованных данных и усложняет учёт.

**Кто:** Кладовщик, бухгалтер.  
**Проблема:** Нет единого документа для перемещения.  
**Цель:** Один документ — одна операция перемещения с движениями по обоим складам.

## Requirements (RFC 2119)

### MUST
- Документ MUST иметь реквизиты: СкладИсточник, СкладНазначение, Дата, Организация.
- Документ MUST содержать ТЧ «Товары» (Номенклатура, Количество).
- При проведении документ MUST формировать движения: списание со склада-источника, 
  поступление на склад-назначения в одной транзакции.
- Документ MUST проверять наличие остатков на складе-источнике до проведения.

### SHOULD
- Форма документа SHOULD показывать остатки по выбранной номенклатуре на складе-источнике.
- Документ SHOULD поддерживать печатную форму «Накладная».

### MUST NOT
- Документ MUST NOT проводиться при отрицательных остатках на складе-источнике.

## Scope

**In scope:** Документ, проведение, печатная форма.  
**Out of scope:** Резервирование при перемещении, маршрутизация — в будущих задачах.

## Considered Options

| Вариант | Описание | Плюсы | Минусы |
|---------|----------|-------|--------|
| A | Два документа (списание + поступление) | Уже есть | Два документа, риск рассинхронизации |
| B | Один документ с двумя наборами движений | Одна транзакция, атомарность | Новый объект |
| C | Документ + подчинённые | Гибкость | Сложность, избыточность |

## Decision Outcome

Выбран вариант B — один документ с двумя наборами движений в одном проведении.

**Consequences Good:** Атомарность, простота для пользователя.  
**Consequences Bad:** Нужна настройка регистров, тестирование граничных случаев.

## Technical Design

### Metadata Objects (создаёт пользователь)
- Документ «ПеремещениеТоваров».
- Реквизиты: СкладИсточник, СкладНазначение, Организация.
- ТЧ «Товары»: Номенклатура, Количество.
- Регистры: остатки, партии (если используются).

### Modules (пишет агент)
- Модуль объекта: ОбработкаПроведения, проверка остатков, формирование движений.
- Модуль формы: отображение остатков, подбор номенклатуры.
- Модуль печатной формы.

### Data Flow
Ввод документа → Проверка остатков → Формирование движений списания и поступления 
→ Запись в регистры.

## Test Plan
- [ ] Проведение при достаточных остатках — успешно.
- [ ] Проведение при недостаточных остатках — отказ с сообщением.
- [ ] Отмена проведения — откат движений.
- [ ] Пустая ТЧ — документ не проводится.
- [ ] Склад-источник = склад-назначение — отказ или предупреждение.
```

## 7. Антипаттерны спек

| Антипаттерн | Проблема | Решение |
|-------------|----------|---------|
| **Спека без альтернатив** | Только один вариант = нет анализа. | Минимум 2 варианта в Considered Options. |
| **Размытые требования** | «Система должна быть удобной», «продуктивность должна вырасти». | Конкретные MUST/SHOULD с измеримыми критериями. |
| **Пустой Out of Scope** | Риск scope creep, бесконечные доработки. | Явно перечислить, что НЕ входит. |
| **Test Plan без граничных случаев** | Только «счастливый путь» — баги в проде. | Добавить пустые значения, нули, ошибки, отмены. |
| **Копипаст из бизнес-ТЗ** | Бизнес-требования без анализа и технической интерпретации. | Анализировать, декомпозировать, переформулировать в RFC 2119. |
| **Противоречия между разделами** | Requirements и Technical Design расходятся. | Сверить все разделы на согласованность. |
| **Решение без обоснования** | «Выбираем вариант A» без аргументов. | Обязательное обоснование в Decision Outcome. |
