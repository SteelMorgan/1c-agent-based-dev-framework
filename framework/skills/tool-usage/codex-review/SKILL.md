# Ревью через внешние LLM (Codex Review)

## Назначение

Навык учит агента получать **независимое ревью** артефактов от альтернативных LLM, запуская их через CLI-инструменты. Ревьювер работает в read-only sandbox, читает файлы проекта и навыки фреймворка, и возвращает структурированный отзыв.

**Принцип:** Claude Code — оркестратор. Он формирует задачу, передаёт артефакт и критерии (навыки), а внешний агент самостоятельно анализирует и отвечает.

---

## Когда применять

| Триггер | Действие |
|---------|----------|
| Пользователь вызывает `/review-gpt` | Запустить ревью через Codex CLI |
| Пользователь вызывает `/review-all` | Запустить GPT + Opus параллельно (см. `opus-review`) |
| Пользователь просит «второе мнение» | Предложить `/review-gpt` или `/review-all` |
| Сложная архитектура, > 5 файлов | Рекомендовать ревью |
| Перед реализацией спецификации | Предложить ревью плана |

---

## Формирование промпта

Промпт для ревьювера состоит из трёх обязательных блоков. Подробный шаблон: [references/prompt-template.md](references/prompt-template.md).

### Блок 1: Задача

Что нужно проверить и в каком контексте. Пример:

> Проведи ревью плана реализации интеграции с внешней системой.
> Контекст: доработка типовой конфигурации УТ, задача #42.

### Блок 2: Артефакт

Конкретный объект проверки. **Всегда передавать пути к файлам — ревьювер читает их самостоятельно. Никогда не вставлять содержимое файлов в промпт.**

Правила по типу:

- **Спецификация** — путь к файлу спецификации + пути к исходным материалам (задача, анализ)
- **Код** — основание изменений (спека или задача) + подсказка использовать `git diff --name-only HEAD~1` + ключевые файлы
- **Тесты** — путь к файлам/каталогу тестов + тестируемый модуль + основание (спека)
- **Форма** — путь к модулю формы + основание изменений
- **Архитектура** — путь к архитектурному документу + ключевые файлы реализации
- **Если файлов нет** (артефакт только в чате) — передать текстом как исключение

### Блок 3: Навыки (критерии ревью)

Ссылки на файлы `SKILL.md`, которые ревьювер **прочитает сам** и использует как критерии. Выбор навыков зависит от типа артефакта:

| Тип артефакта | Навыки |
|---------------|--------|
| Код BSL | `coding-standards`, `error-handling`, `query-patterns`, `ssl-patterns`, `form-patterns` |
| Спецификация / план | `spec-standard` |
| Форма (UI) | `form-patterns`, `form-visual-requirements` |
| Архитектура | `ssl-patterns`, `query-patterns`, `coding-standards` |
| Тесты | `coding-standards`, `error-handling` |

Пути к навыкам — относительно корня проекта:
```
framework/skills/bsl-practices/<name>/SKILL.md
framework/skills/spec-writing/<name>/SKILL.md
```

При смешанном артефакте (код + форма) — объединить навыки обеих групп.

## Вызов Codex CLI

### Команда

```bash
codex exec \
  -p cx_gpt-5_3-codex-high \
  --sandbox read-only \
  --ephemeral \
  -o /tmp/codex-review-$(date +%s).txt \
  "<промпт>"
```

### Передача длинного промпта

Промпты для ревью почти всегда многострочные и содержат спецсимволы.
**Всегда** записывать промпт во временный файл и передавать через stdin:

```bash
# 1. Записать промпт во временный файл
cat <<'EOF' > /tmp/codex-prompt-$(date +%s).txt
<текст промпта — любой длины, с кавычками, markdown и т.д.>
EOF

# 2. Передать через stdin
codex exec \
  -p cx_gpt-5_3-codex-high \
  --sandbox read-only \
  --ephemeral \
  -o /tmp/codex-review-$(date +%s).txt \
  - < /tmp/codex-prompt-*.txt
```

**Не использовать** `echo "<промпт>"` — ломается на кавычках и спецсимволах.

### Запуск в фоне

Использовать Bash tool с `run_in_background: true`. Это позволяет мониторить прогресс без блокировки основного разговора.

**Важно:** запомнить путь к файлу `-o` — это основной способ получения результата.

## Мониторинг и сбор результата

### Шаг 1: Запуск

Записать промпт во временный файл, затем запустить Codex:

```
REVIEW_TS=$(date +%s)
PROMPT_FILE=/tmp/codex-prompt-${REVIEW_TS}.txt
RESULT_FILE=/tmp/codex-review-${REVIEW_TS}.txt

# Записать промпт (через Bash или Write tool)
cat <<'EOF' > $PROMPT_FILE
<промпт>
EOF

# Запустить в фоне (через Bash с run_in_background: true)
codex exec -p cx_gpt-5_3-codex-high --sandbox read-only --ephemeral \
  -o $RESULT_FILE - < $PROMPT_FILE
```

Получить task_id из результата. Запомнить путь `RESULT_FILE`.

### Шаг 2: Мониторинг прогресса

Использовать **два способа параллельно**:

**Способ A — TaskOutput (основной):**
```
TaskOutput(task_id, block=false)  — проверить статус
```
Если TaskOutput возвращает данные — определять статус по ключевым словам:
- `exec` — Codex выполняет shell-команды (читает файлы)
- `codex` — Codex формулирует ответ
- `tokens used` — завершение

**Способ B — проверка файла `-o` (fallback):**
```
Read(RESULT_FILE)  — если файл существует → Codex завершился
```

> ⚠️ **Важно:** TaskOutput может потерять задачу (вернуть "no task found").
> В этом случае **не ждать** — сразу проверять файл `-o` через Read.
> Файл `-o` создаётся **атомарно при завершении** процесса Codex —
> он не существует пока Codex работает, и появляется только когда процесс
> полностью завершён. Если файл существует — Codex гарантированно отработал.

Сообщать пользователю краткий статус:
- «GPT читает файлы проекта...»
- «GPT анализирует артефакт...»
- «GPT формирует отзыв...»

### Шаг 3: Получение результата

```
Read(RESULT_FILE)  — прочитать чистый результат
```

Файл `-o` содержит **только финальный ответ** ревьювера, без хедеров и логов Codex.

Если файл `-o` пуст или не создан — прочитать последнее сообщение из stdout
через `TaskOutput(task_id, block=true)`.

### Шаг 4: Представление пользователю

- Показать отзыв ревьювера
- Если есть критические замечания — предложить скорректировать артефакт
- Отзыв — это **мнение**, финальное решение за пользователем

## Обработка ошибок

| Ситуация | Действие |
|----------|----------|
| Codex CLI не установлен | Сообщить: `npm install -g @openai/codex` |
| Таймаут (процесс не завершился) | Показать частичный результат из stdout |
| Ошибка API (exit code ≠ 0) | Показать stderr, предложить повторить |
| Файл `-o` пуст | Взять последнее сообщение из stdout |
| Промпт слишком длинный | Передать через stdin с `-` |

---

## Типичные ошибки

| Ошибка | Последствие | Как избежать |
|--------|------------|--------------|
| Не передать навыки в промпт | Ревьювер даёт общий отзыв без привязки к стандартам проекта | Всегда включать блок «Навыки» с путями к SKILL.md |
| Передать содержимое навыков вместо путей | Раздувание промпта, лимит токенов | Передавать только пути — Codex прочитает файлы сам |
| Запустить без `--sandbox read-only` | Ревьювер может попытаться изменить файлы | Всегда указывать `--sandbox read-only` |
| Забыть `--ephemeral` | Засорение диска сессиями | Всегда указывать `--ephemeral` |
| Не использовать `-o` | Придётся парсить stdout с шумом | Всегда указывать `-o` для чистого результата |
| Передать артефакт без задачи | Ревьювер не понимает контекст | Всегда начинать промпт с блока «Задача» |
