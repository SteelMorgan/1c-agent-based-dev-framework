# Навигация по коду (Code Navigation)

Не угадывать расположение кода — использовать LSP. Точные результаты по индексу проекта.

## Когда применять

| Триггер | Действие |
|---------|----------|
| Поиск определений процедуры/функции | `navigate_symbol` operation `definition` |
| Все вызовы функции X | `navigate_symbol` `search` или `get_call_graph` `incoming` |
| Кого вызывает функция | `get_call_graph` `outgoing` |
| Переименование по проекту | `rename_symbol` (сначала `preview: true`) |
| Quick Fixes | `get_code_actions` |
| Диагностика файла | `get_diagnostics` |
| Исследование неизвестного кода | `navigate_symbol` → `get_call_graph` → hover |
| Ошибка «метод не найден» на типе платформы | `getMembers` / `getMember` / `getConstructors` |
| Состав объекта/ТЧ/реквизиты, значения перечисления, предопределённые | `get_completion` после точки (см. «Discovery метаданных») |
| Где используется объект метаданных в коде | `search_ssl_functions` references на `Документы.X` + grep (см. ниже) |
| Оценить, кого заденет правка процедуры/функции | `get_symbol_impact` (входящие + ссылки + классификация) |
| Подсказки параметров при написании вызова | `signature_help` — курсор ВНУТРИ скобок вызова (см. «Подсказки параметров») |

## Алгоритмы

### Найти все вызовы функции

1. `navigate_symbol(query: "ИмяФункции", operation: "search")` → получить `uri`, `line`, `character`
2. `get_call_graph(uri, line, character, direction: "incoming")`

### Переименование по проекту

1. `navigate_symbol` → `uri`, `line`, `character`
2. `rename_symbol(..., preview: true)` → проверить `changes`
3. `rename_symbol(..., preview: false)`
4. `get_diagnostics` по затронутым файлам

### Quick Fixes

1. `get_diagnostics(uri)` → список диагностик
2. `get_code_actions(uri, range, diagnostic)` → применить

### Верификация API платформы после ошибки

**Триггер:** ошибка «Метод объекта не обнаружен» / «Неверное количество параметров» на типе платформы. Не угадывать повторно — верифицировать.

1. `search_syntax_reference(query: "ТипОбъекта")` → подтвердить имя, получить `id`
2. `getMembers(typeId)` → точный список методов/свойств
3. `getMember(typeId, member)` → сигнатура конкретного метода
4. `getConstructors(typeId)` → если ошибка про параметры `Новый`

**Важно:** Только реакция на ошибку, не превентивный поиск.

### Discovery метаданных через `get_completion`

BSL LS Type System v2 отдаёт метаданные конфигурации через автодополнение. Один tool отвечает на разные вопросы — меняется только позиция курсора (после точки). В `detail` каждого пункта — сигнатура и возвращаемый тип.

| Вопрос | Где поставить курсор | Что вернётся |
|--------|----------------------|--------------|
| Реквизиты / ТЧ / колонки объекта | после `Объект.` (типизированная переменная) | реквизиты, табличные части, их колонки, методы — с типами |
| Значения перечисления | после `Перечисления.ИмяПеречисления.` | значения перечисления |
| Предопределённые элементы | после `Справочники.Имя.` / `ПланыСчетов.Имя.` | предопределённые + методы менеджера |
| Состав ОпределяемогоТипа | курсор на реквизите типа ОпределяемыйТип | `get_completion` + `get_hover_info` раскрывают составляющие типы |

**Инверсный сигнал:** если после `перем.` `get_completion` возвращает пусто или нет ожидаемого члена — тип переменной выведен неверно/неизвестен. Отсутствие автодополнения здесь = индикатор ошибки типа (частый баг 1С), а не «нет данных».

### Найти использования объекта метаданных в коде

Картина гибридная (как сам объект используется в BSL):

1. `search_ssl_functions` (режим references) на символе менеджера `Документы.ИмяОбъекта` → **семантически точные** места обращения через менеджер. references исключают совпадения в комментариях/строках/текстах запросов.
2. **Дополнить grep'ом** то, что не является символом и потому references не видит: строковые литералы типа (`"ДокументСсылка.ИмяОбъекта"`, `Тип("ДокументСсылка.…")`) и пути метаданных внутри текста запроса (`ИЗ Документ.ИмяОбъекта`).

> Для «где используется» предпочитать references, а не голый grep по имени: грэп даёт ложные срабатывания в комментариях и строках. grep — только добор строковых/запросных использований.

### Импакт-анализ правки: `get_symbol_impact`

Перед переименованием/изменением процедуры — оценить радиус поражения одним вызовом:

1. `navigate_symbol` → `uri`, `line`, `character` символа.
2. `get_symbol_impact(uri, line, character)` → входящие вызывающие (call hierarchy) + все ссылки + **классификация вызывающих по типу модуля** (CommonModule / FormModule / ManagerModule / ObjectModule / …) — видно, откуда тянется правка: UI, сервер или фон.

**Два слепых пятна (заложены в вывод, держать в голове):**
- **Триггеры.** call hierarchy показывает только прямые вызовы. Метод достигается ещё и через подписки на события, обработчики форм, регл.задания, расширения `&Вместо/&Перед/&После` — этого здесь НЕ видно (декларативно; добирать через 1c-mcp/XML).
- **Однофамильцы.** Для общих объектных методов (`ОбработкаПроведения`, `ПередЗаписью`, есть в сотнях модулей) привязывать call hierarchy к конкретному модулю — иначе в результат попадут ложные звенья от одноимённых методов других объектов.

### Подсказки параметров на месте вызова: `signature_help`

Возвращает список параметров вызываемого метода и то, на каком аргументе стоит курсор. Контракт строгий — ошибка в позиции даёт пустой результат, который выглядит как «не поддерживается», а на деле это неверная позиция.

**ОБЯЗАТЕЛЬНО передавать `line`/`character` 0-based, курсор ВНУТРИ скобок вызова** — между `(` и `)`, НЕ на имени метода и НЕ перед `(`. Провайдер находит охватывающий вызов (`doCall`), резолвит вызываемый метод и только тогда возвращает сигнатуры.

```
// Строка (1-based 8):  Аккаунт = ПолучитьАккаунт(ДокументОперации, ПараметрыОперации);
signature_help(uri, line=7, character=29)   // сразу после "(" → param 0
//   → ПолучитьАккаунт(ДокументОперации?, ПараметрыОперации?), Active parameter: 0
signature_help(uri, line=7, character=47)   // после запятой   → Active parameter: 1
```

**Пустой результат ≠ tool сломан.** `signature_help` возвращает сигнатуры только когда вызываемый метод резолвится в метод с известным списком параметров. Надёжно работает для **методов того же модуля** (резолв из разобранного исходника). Возвращает пусто для:
- курсор НЕ внутри скобок (на имени / перед `(`) — самая частая ошибка;
- межмодульный вызов (`Модуль.Метод(`) — нужен индекс типов конфигурации, исправен только когда BSL LS нацелен на единый корень конфигурации (см. «Типичные ошибки»: межмодульный резолв);
- глобальные методы платформы (`СтрШаблон(`, `ЗначениеЗаполнено(`) и методы объектов платформы (`Запрос.УстановитьПараметр(`) — нужен загруженный **контекст платформы 1С** (синтакс-помощник `.hbk`). Контейнер mcp-lsp лёгкий — платформа НЕ зашита в образ, провижинится в рантайме. Run-скрипт `bsl-ls` генерирует глобальный конфиг и передаёт его через `-Dapp.globalConfiguration.path`: когда задан `BSL_PLATFORM_BIN` (compose `docker-compose.platform.yml` монтирует каталог `.hbk` read-only) — используется явный `v8platform.binPath` с приоритетом; когда не задан — BSL LS автоопределяет установленную платформу (включая Windows). Без того и другого в стартовом логе `Failed to load platform contexts: No 1C platform installations found`, и hover/completion/сигнатуры по платформе пустые. С загруженным (`Loaded N platform contexts from 1C syntax helper`) — резолвятся с полными доками параметров (на русском при `language:ru`).

Для подтверждённого списка параметров независимо от места вызова — `getMember(typeId, member)` (типы платформы) или `navigate_symbol`→hover (собственное объявление метода).

## Типичные ошибки

| Ошибка | Обходной путь |
|--------|---------------|
| LSP не подключён | Проверить `lsp_status`; запустить BSL Language Server |
| Символ не найден | Проверить имя (регистр, язык); `ask_ai_assistant` (шаблон SEARCH_DOCS из `buddy-prompting`) по имени метода/типа |
| `get_call_graph` таймаут | Уменьшить `depth` |
| `rename_symbol` не применим | Проверить позицию курсора; защищённая область → ручное редактирование |
| Файл не индексирован | Дождаться индексации LSP |
| `signature_help` возвращает пусто | Курсор должен быть ВНУТРИ скобок вызова (0-based), не на имени метода; надёжно для методов того же модуля. Для межмодульных/глобальных вызовов см. строку ниже |
| Межмодульный `Модуль.Метод()` не резолвится (пустой `signature_help`, межмодульный call hierarchy теряет звенья, ложный `QueryToMissingMetadata`) | BSL LS должен индексировать ЕДИНЫЙ главный корень конфигурации `src/xml`, а не корень проекта с 9 `Configuration.xml` (основная + расширения). Session-manager автоопределяет главный корень конфигурации под переданным workspace (`detectConfigurationRoot`), так что это должно быть исправлено. Если регрессирует — проверить стартовый лог bsl-ls на `Detected 1C configuration root: …/src/xml`; отсутствие = детект не сработал (например, в workspace нет главного `Configuration.xml` или бинарь старее фикса) → реиндексация смотрит не на то дерево |
