# Измерение производительности BSL через debugger

Использовать измерение debugger для одного воспроизводимого и безопасного запуска. Считать его одновременно профилем времени и доказательством того, какой модуль и какие строки действительно исполнились в выбранном target.

Не заменять этим навыком интерактивную остановку на breakpoint, техжурнал, анализ плана СУБД или мониторинг ресурсов контейнера: измерение локализует BSL-путь, но само по себе не доказывает причину в СУБД, блокировках или внешнем сервисе.

## Записать scenario fingerprint до измерения

До включения measure записать fingerprint сценария:

- ожидаемую точку входа: модуль, процедуру и строку или иной однозначный source locator;
- точный класс trigger и класс его аргументов;
- время старта и окончания запуска;
- известные targetID, session/seance и ключ измерения, если их можно захватить в момент trigger.

Fingerprint — критерий корреляции, а не описание «похожей бизнес-операции». Не заменять его длительностью target, числом модулей или первым handler-ом с бизнес-похожим именем.

## Выбрать область и контрольный запуск

До подключения зафиксировать:

- один бизнес-триггер и его входные данные; цель — исполнить его ровно один раз;
- ожидаемый target: клиент, серверный вызов, фоновое задание или другой сеанс;
- исходный код и ревизию, с которыми сопоставляются moduleData и lineInfo;
- предел времени для запуска и способ безопасной остановки;
- критерий сравнения: тот же триггер, те же данные, та же конфигурация и одинаковый прогрев для варианта «до» и «после».

Не измерять пользовательский продуктивный сеанс и не профилировать широкий, недетерминированный сценарий. Если воспроизводимого триггера нет, сначала сделать его минимальным; без него профиль неинтерпретируем.

## Подключить debugger и включить измерение

1. Подключиться (`attach`) к HTTP debug server и получить targets.
2. Сопоставить target с подготовленным сеансом по типу, времени запуска, пользователю и номеру сеанса. При необходимости обновить metadata до запуска.
3. Включить режим измерения штатным RDBG-запросом `setMeasureMode` / `RDBGSetMeasureModeRequest`. Передавать `measureModeSeanceID`, когда он доступен: сохранить это значение как ключ корреляции.
4. Зафиксировать время старта, targetID, ключ сеанса измерения и границу запуска.
5. Только после успешного ответа включить ровно один заранее выбранный триггер. Не нажимать повторно и не допускать параллельных фоновых запусков того же пути.
6. Дождаться завершения триггера в пределах заранее установленного таймаута, затем выключить измерение тем же штатным механизмом.
7. Получить асинхронный результат, сохранить исходный event/payload как evidence до интерпретации.

На платформе 8.3.27 результат приходит асинхронным событием с `xsi:type=DBGUIExtCmdInfoMeasure`; фактический `cmdID` — `measureResultProcessing`. Не ожидать синхронный ответ с профилем от команды включения или выключения.

## Не потерять асинхронный результат

Извлекать и сохранять payload `PerformanceInfoMain`. Проверить как минимум:

| Поле | Использовать для |
|---|---|
| `targetID` | Сопоставить результат с измеренным target. |
| `totalDurability` | Получить общую длительность измерения. |
| `totalIndepServerWorkTime` | Отделить независимое серверное рабочее время, если его предоставляет платформа. |
| `performanceFrequency` | Нормализовать значения частоты и длительности. |
| `moduleData` | Найти исполненные модули. |
| `lineInfo` | Разобрать строки: `lineNo`, `frequency`, `durability`, `pureDurability`, `serverCallSignal`. |

Проверить, что `targetID` совпадает с сохранённым target, а при нескольких одновременных измерениях также совпадает `measureModeSeanceID` или другой сохранённый ключ сеанса. Не приписывать профиль нужному запуску только по близкому времени.

Считать target eligible только в одном из двух случаев:

1. targetID был захвачен при trigger и совпал с payload;
2. `moduleData`/`lineInfo` содержат ожидаемый модуль, процедуру и строку из scenario fingerprint.

Одна общая business-цепочка не заменяет этого доказательства. Если fingerprint отсутствует в candidate target, это доказывает, что ожидаемый путь в нём не был достигнут; не объяснять отсутствие «неизвестным moduleID» или вероятной конкуренцией.

Если candidates несколько либо ожидаемая точка входа не найдена, установить статус `target_correlation_failed`, сохранить список кандидатов и fingerprint, выполнить cleanup и не ранжировать hotspots. Никогда не выбирать target по длительности, по количеству модулей или по первому business-looking handler.

Адаптер debugger обязан сохранять необработанное async-событие до возврата вызывающему коду. Не вызывать обычный `ping` как единственный способ ожидания, если он может прочитать и отбросить очередь событий: следующий poll тогда уже не увидит результат. Явно распознавать псевдоним события `measureResultProcessing`, а не выдумывать иной cmdID.

Если typed API профилирования отсутствует, работать raw-протоколом только по официально установленной XSD/RDBG-спецификации соответствующей платформы. Не конструировать типы, поля или XML «по аналогии». Адаптер обязан передать `measureModeSeanceID`, если он предусмотрен, и сохранить асинхронный event без потери.

Если event не найден до контрольного таймаута, не объявлять hotspot и не подменять evidence догадками. Зафиксировать потерянный/неполученный результат, снять режим измерения, очистить подключение и проверить адаптер, очередь событий и корреляцию перед новым запуском.

## Прочитать профиль как call trace

Сопоставить `moduleData` с исходниками точной ревизии, затем сопоставить каждый `lineNo` с исходной строкой. Построить таблицу строк или поддеревьев: модуль, процедура, строка, частота, inclusive, self, признак серверного вызова и роль в бизнес-операции.

| Метрика | Интерпретация |
|---|---|
| `frequency` | Частота исполнения строки; обычно основа для оценки числа вызовов/итераций после нормализации. |
| `durability` | Полная (inclusive) длительность: строка вместе со вложенной работой. |
| `pureDurability` | Собственная (self) длительность: работа строки без вложенных вызовов. |
| `serverCallSignal` | Граница/сигнал серверного вызова; использовать для объяснения клиент-серверной кратности, а не как самостоятельное время. |

Нормализовать счётчики `frequency`, `durability` и `pureDurability` по `performanceFrequency`, если значения платформы заданы в ticks. В отчёте указывать формулу и единицы; не сравнивать сырые ticks разных измерений как миллисекунды.

Считать `durability` inclusive-временем, а `pureDurability` self-временем. Не суммировать inclusive-времена родителя и потомков: вложенная работа окажется учтена несколько раз.

## Сначала коррелировать target, затем выбрать denominator

Соблюдать порядок для каждого измерения: **correlate target → choose business boundary → rank**. Не переходить к business-denominator и hotspot, пока target не стал eligible по scenario fingerprint.

## Выбрать business-denominator по вложенной цепочке

Не принимать `totalDurability` target по умолчанию за business-denominator. Сначала восстановить вложенную цепочку handler-ов по inclusive-линиям, частоте, `moduleData`, исходникам и соседним строкам: внешний transport/polling handler → первый handler бизнес-сообщения → его дочерние вызовы.

Для каждой нераскрытой линии с moduleID:

1. Сопоставить её с `moduleData`, исходной ревизией и строкой источника.
2. Если прямого сопоставления нет, посмотреть соседние линии, вложенные inclusive-вызовы, частоту и границы handler-а.
3. Не считать неизвестный moduleID доказательством отсутствия idle/polling: его роль устанавливается по цепочке и арифметике, а не по имени.

Применять следующее решение:

```text
Есть первый handler бизнес-сообщения с inclusive B?
├─ нет → оставить target total единственным предварительным denominator и явно назвать неоднозначность.
└─ да → target total T примерно равен B + self внешней transport/polling-обёртки W?
   ├─ да → классифицировать W как idle/polling; business-denominator = B.
   └─ нет → проверить оставшееся время и цепочку; использовать два denominator только пока неоднозначность не снята.
```

Показывать уравнение с нормализованными единицами: `T ≈ B + W + residual`. Если `B` — первый бизнес-handler, а `residual` мал относительно погрешности/служебных строк, не ранжировать `W` как бизнес-hotspot даже при высоком self. Для бизнес-линий пересчитать долю как `нормализированная метрика / B`, а не как `/ T`; явно подписать выбранный denominator в каждой таблице и в сравнении до/после.

Использовать `moduleData` и `lineInfo` как фактический trace:

- строка с ненулевой частотой доказывает исполнение на измеренном пути;
- строка с высокой частотой показывает цикл, повторный вызов или fan-out;
- `serverCallSignal` помогает отделить пересечения клиентского и серверного контекстов;
- отсутствие строки в результате не доказывает, что она никогда не вызывается: она не попала в этот target и этот единичный запуск.

## Найти существенную причину, а не длинную строку

Сначала исключить из ранжирования ожидания UI, polling, sleep, блокирующие ожидания, простои внешнего ответа и строки за пределами выбранного business-denominator. Самая длинная wall-time строка может быть idle, а не полезной точкой оптимизации.

Затем ранжировать кандидаты двумя разными способами:

1. По высокому `pureDurability`: это собственная тяжёлая работа строки или небольшого поддерева.
2. По `frequency × нормализированный pureDurability`: это накопленный эффект частого вызова, даже если одна итерация недорога.

Различать:

- **high self** — дорогая собственная операция; исследовать её алгоритм, данные, запрос или внешнюю границу;
- **call amplifier** — строка сама недорога, но множит тяжёлый дочерний вызов; искать цикл `N`, внутреннюю кратность `K` и эффект `N × K`;
- **inclusive wrapper** — большая inclusive-длительность при малом self; не оптимизировать обёртку, пока не найден дорогой потомок;
- **failed resolver / пробный путь** — частые неуспешные разрешения, проверки или retries; не называть их бизнес-профилем без подтверждения успешного бизнес-результата.

Для каждой гипотезы выписать evidence: строка источника, нормализированные значения, доля от выбранного деноминатора, роль в call trace и исключённые ожидания. Не делать вывод «медленная база» или «медленный HTTP» только из BSL-профиля: собрать профильный артефакт соответствующего уровня.

## Сравнить варианты и параллельные цели

Сравнивать «до» и «после» только при идентичном единичном триггере, данных, target, прогреве, границе измерения и выбранном business-denominator. Сопоставлять не только total, но и:

- частоту конкретных линий и серверных границ;
- self-время и accumulated self-время;
- состав фактического call trace;
- изменение `N × K` для амплификатора;
- наличие новых ожиданий или исчезнувшего профиля.

При нескольких concurrent targets вести отдельную запись на каждый target и сеанс измерения. Не объединять их строки и totals, пока нет явной связи через targetID, ключ сеанса и причинную цепочку trigger → server call → result.

## Завершить измерение без хвостов

Перед выводом или передачей результата:

1. Убедиться, что режим измерения выключен даже после ошибки или таймаута.
2. Сохранить raw async event и нормализованную сводку с targetID, ключом сеанса, временем, trigger и исходной ревизией.
3. Отпустить остановленный target, если в том же сеансе применялись breakpoints; снять все breakpoints.
4. Выполнить `detach`; при зависшем debug-состоянии — штатный `force_detach` и повторную проверку targets.
5. Удалить временные триггеры, тестовые данные и средства запуска, если они были созданы только для замера.

Сообщать результат в форме: «сценарий и target → доказанный trace → нормализированные метрики и деноминатор → исключённые ожидания → гипотеза причины → сравнение до/после или следующий профильный инструмент → подтверждение cleanup».

## Контрольный список против ложных выводов

- Не принимать target total за бизнес-знаменатель без восстановления вложенной handler-цепочки и уравнения `T ≈ B + W + residual`.
- Не считать неизвестный moduleID доказательством отсутствия idle/polling.
- Не выбирать hotspot только по максимальному wall/inclusive времени: это может быть idle или ожидание.
- Не суммировать рекурсивно inclusive-время родителя и потомков.
- Не игнорировать частоту: modest self при большом `frequency` может доминировать.
- Не пропускать вложенную кратность `N × K`.
- Не считать неуспешные resolver-вызовы бизнес-профилем.
- Не объявлять hotspot, если async event потерян, target не совпал или payload неполон.
- Не ждать бесконечно: задать hard timeout, выключить measure и очистить debug-сеанс.
