# Сценарные приёмы анализа ТЖ

Справочник прикладных приёмов диагностики по записям технологического журнала.
Основной процесс работы с ТЖ — в `SKILL.md`.

---

## 1. Классификация записи ТЖ по типу инцидента

| Тип инцидента | Минимальный набор событий ТЖ | Что искать в первую очередь |
|---------------|-----------------------------|-----------------------------|
| **startup** | `EXCP`, `CONN` | Версия платформы, режим клиента, тип ИБ, порт, путь к source-set |
| **HTTP** | `EXCP`, `CALL`, `SCALL` | Путь запроса (`HTTPPath`), обработчик, метаданные сервиса |
| **web-client** | `EXCP`, `CALL` | URL клиента, идентификатор сессии, имя модуля/формы |
| **background job** | `EXCP`, `TLOCK`, `CALL` | Имя задания, параметры, пользовательский контекст, счётчик повторов |
| **auth/session** | `CONN`, `EXCP` | Имя пользователя, роль, признак аутентификации, завершение сеанса |
| **DBMS** | `DBMSSQL` / `DBPOSTGRS`, `SDBL` | Текст запроса, `elapsed`, `table`/`index`, идентификатор транзакции |
| **lock/deadlock** | `TLOCK`, `TDEADLOCK`, `TTIMEOUT` | Держатель/ожидающий блокировки, объект блокировки, время ожидания |
| **long call** | `CALL`, `SCALL` | `Duration`, имя метода/процедуры, стек вызовов, транзакционный контекст |

---

## 2. Обязательные идентификаторы

При разборе любой записи ТЖ фиксировать и сохранять в рабочем контексте:

| Идентификатор | Поле ТЖ | Зачем нужен |
|--------------|---------|-------------|
| `timestamp + TZ` | `DateTime` | Основа timeline; без TZ сшивка файлов ненадёжна |
| `infobase` | `IB` | Разграничение инфобаз в кластере |
| `user` | `Usr` | Аудит, связь с ЖР |
| `session` | `Session` | Цепочка событий одного сеанса |
| `connection` | `Con` | Привязка к каналу клиент–сервер |
| `process id` | `process` (имя файла ТЖ) | Идентификация рабочего процесса |
| `transaction id` | `Trans` | Границы транзакции, rollback |
| `background job id` | `JobID` | Повторные запуски, retry |
| `HTTP path` | `HTTPPath` | Маршрутизация HTTP-запроса |
| `correlation id` | `CorrID` / `ClientID` | Сшивка с ЖР и между процессами |

Если идентификатор отсутствует в записи — явно отметить это в выводе; не подставлять предположение.

## 3. Timeline и источник времени

**Правило:**

- При анализе нескольких файлов ТЖ в начале работы зафиксировать источник времени и часовой пояс каждого файла.
- Если часовые пояса расходятся — привести всё к UTC перед построением timeline.
- Первая причинная запись (`EXCP`, начало `TLOCK`, первый `DBMSSQL` с превышением threshold) приоритетнее последующих следствий: rollback, retry, `TTIMEOUT`, завершение сеанса.
- Повторяющиеся однотипные записи после первой ошибки — следствие, не причина.
- При отсутствии записей до момента сбоя — явно запросить предшествующий интервал вместо интерпретации неполного окна.

## 4. Сценарий: startup-сбой

**Цель:** установить причину до того, как предлагать правки кода.

Порядок проверки:

1. Версия платформы (из имени файла/процесса ТЖ или `EXCP.descr`).
2. Режим клиента: файловый / клиент-серверный / веб-сервер.
3. Тип ИБ: файловая / SQL-сервер; для SQL — имя СУБД и версия.
4. Режим запуска: кластер (менеджер кластера) или standalone.
5. Сетевые параметры: порт агента кластера, веб-сервер, IP-привязка.
6. Учётные данные: аутентификация ОС / 1С; права на папку ИБ или BD.
7. Путь к source-set (конфигурация из хранилища или файлов) — наличие, доступность, корректность.

Предложение правки кода допустимо только после того, как пункты 1–7 подтверждены или исключены.

## 5. Сценарий: HTTP / web-client

**Цель:** связать входящий запрос с конкретным модулем/процедурой ДО интерпретации сообщения об ошибке.

Порядок:

1. Из события ТЖ извлечь `HTTPPath` (HTTP) или идентификатор формы/сессии (web-client).
2. Найти обработчик: HTTP-сервис или веб-обработчик по пути → объект метаданных.
3. Перейти к коду обработчика (`navigate_symbol`).
4. Только после установления контекста интерпретировать текст `EXCP.descr` или `CALL.descr`.
5. Зафиксировать в выводе: `HTTPPath` → имя сервиса → модуль → процедура/функция.

---

## 6. Сценарий: фоновое задание

**Цель:** собрать полный контекст задания перед анализом ошибки.

Фиксировать обязательно:

| Атрибут | Источник |
|---------|---------|
| Имя задания | `JobID`, описание в метаданных |
| Расписание (если регламентное) | Метаданные конфигурации |
| Параметры запуска | `EXCP.descr` / `CALL.descr` |
| Пользовательский контекст | `Usr` в записи ТЖ |
| Счётчик повторов | количество `JobID`-записей с одинаковым именем |
| Состояние блокировок | наличие `TLOCK`/`TTIMEOUT` с тем же `Session`/`Trans` |

Если задание завершилось с ошибкой после нескольких повторов — первый запуск содержит первичную причину; последующие — последствия или маскировку.

## 7. DBMS-улики единым блоком

При наличии событий `DBMSSQL` / `DBPOSTGRS` / `TLOCK` / `TDEADLOCK` хранить все улики вместе:

```
query_text:       <полный текст SQL-запроса>
lock_holder:      session=..., trans=..., process=...
lock_waiter:      session=..., trans=..., process=...
wait_event:       <тип ожидания>
table_index:      <таблица> / <индекс>
trans_boundary:   begin=..., end=... (или "не завершена")
elapsed_ms:       <длительность в мс>
process_session:  process=..., session=..., connection=...
```

Никогда не разрывать этот блок: потеря любого из полей может привести к неверной интерпретации причины блокировки или тормозящего запроса.

При наличии `SDBL`-записи рядом с `DBMSSQL` — сопоставить: `SDBL` содержит исходный запрос на языке запросов 1С, `DBMSSQL` — его SQL-трансляцию.

## 8. Шаблон вывода

Использовать для любого результата анализа ТЖ:

```
### Timeline
<только ключевые события в хронологическом порядке; источник времени и TZ>

### Гипотеза первопричины
<конкретная запись ТЖ → формулировка причины>

### Затронутые метаданные / модули
<объект метаданных → модуль → процедура/функция (или "не установлено")>

### Шаг верификации
<конкретное действие, которое подтверждает или опровергает гипотезу>

### Недостающие улики
<явный список: какие данные отсутствуют и какой интервал/событие нужно запросить>
```

Раздел «Недостающие улики» обязателен. Если фрагмент ТЖ не позволяет сделать надёжный вывод — указать это явно и запросить предшествующий интервал вместо предположения.
