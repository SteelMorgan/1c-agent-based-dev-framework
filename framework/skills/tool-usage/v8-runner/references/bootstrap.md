# Инициализация `v8project.yaml`

Используй этот reference, когда начинаешь работу с `v8-runner` в 1С-репозитории, в котором ещё нет `v8project.yaml`. Цель — задавать пользователю **только те вопросы, на которые ты не можешь ответить сам, изучив репозиторий**.

`v8-runner config init` уже автоматически определяет:
- существующие source-set'ы (Designer и EDT) под корнем проекта,
- выбранный формат при `--format=auto` (по умолчанию), на основе того, что нашлось,
- версию платформы, если её можно определить из исходников.

Поэтому в большинстве проектов правильная команда — это просто:

```bash
v8-runner config init
```

После этого изучи сгенерированный `v8project.yaml` и перезапускай с явными флагами только если автоопределение ошиблось или у пользователя есть ограничения, не видимые из файловой системы.

## Дерево решений (выполняй ДО того, как задавать вопросы пользователю)

### 1. Проверь, не настроен ли проект уже

Если `v8project.yaml` существует — **не** запускай `config init` без `--force`. Вместо этого изучи его и сообщи, что настроено. Использование `--force` требует явного согласия пользователя, потому что это перезапишет любые его локальные правки.

### 2. Определи формат исходников по файловой системе

Посмотри на корень проекта и его непосредственные подкаталоги.

| Признак в файловой системе | Вероятный формат |
|---|---|
| `src/cf/Configuration.xml`, `src/cfe/<ext>/Configuration.xml`, сырое Designer-XML-дерево | `DESIGNER` |
| `src/cf/.project`, `src/cf/Configuration/Configuration.mdo`, `*.mdo`, `DT-INF/` | `EDT` |
| Оба вида деревьев рядом (смешанный моно-репо) | `auto` (по умолчанию) — пусть `config init` зарегистрирует оба source-set'а |
| Ничего из вышеперечисленного | репозиторий не является деревом исходников 1С — остановись и спроси у пользователя, что он ожидает там найти |

Если формат однозначно один из двух, можешь передать `--format=designer` или `--format=edt` для ясности, но не обязан — `auto` выберет то же самое.

### 3. Реши, какой builder backend использовать

По умолчанию `DESIGNER`. Переключайся на `IBCMD` только когда:

- проект — `EDT`, и команда работает на версии платформы, где `ibcmd` поддерживается и быстрее (≥ 8.3.20); **и**
- на критическом пути нет фич, доступных только в Designer (некоторые legacy-задачи всё ещё требуют GUI Конфигуратора).

Спрашивай пользователя только если выбор неоднозначен и ты не можешь определить его из `tools.platform.version`. В сомнительных случаях используй `DESIGNER` — это более безопасный baseline.

### 4. Реши, какое подключение к ИБ использовать

`--connection` — это строка подключения, записываемая в `tools.connection`. Три типичные формы:

| Форма | Пример | Когда использовать |
|---|---|---|
| Файловая ИБ, управляемая `v8-runner` | `--connection "File=build/ib"` | большинство локальных циклов разработки. Путь создаётся при первом `v8-runner init`. Безопасный default. |
| Файловая ИБ, уже существующая на диске | `--connection "File=/abs/path/to/ib"` | у пользователя есть существующий baseline, на который он хочет указать |
| Серверная ИБ | `--connection "Srvr=cluster:1541;Ref=ibname"` | центральная dev-база, общая ИБ, CI-runner, привязанный к кластеру |
|

Для серверных подключений автоматического создания нет (требуются операции уровня DBA). Пользователь должен подтвердить, что база существует, а учётные данные хранятся отдельно (`v8project.local.yaml` держит секреты вне git).

Если README проекта, `docker-compose.yml` или `.env` уже описывают подключение, **используй его** без повторного вопроса. Если нигде ничего не задокументировано, спроси у пользователя **один раз** с тремя опциями выше и дефолтом `File=build/ib`.

### 5. Реши, куда писать вывод

По умолчанию `./v8project.yaml`. Переопределяй через `--output` только когда проект — это поддерево внутри большего репозитория и пользователь явно хочет конфиг не в корне. Не выдумывай значения для `--output`.

## Когда спрашивать пользователя (и как)

Спрашивай только если выполнено хотя бы одно из условий:

1. **Репозиторий выглядит неоднозначно или пустым** — нет признаков Designer/EDT и других зацепок. Спроси: «Я не вижу дерева исходников Designer или EDT под `<root>`. Где живут исходники 1С, или мне создать пустой конфиг?»
2. **Есть намёк на серверную ИБ, но строка подключения нигде не задокументирована.** Спроси: «Похоже на серверный проект. Какие cluster:port и имя ИБ? Или использовать локальный `File=build/ib` по умолчанию?»
3. **Обнаружены смешанные Designer + EDT исходники** и пользователь явно работает только с одним из них. Спроси: «Я обнаружил оба дерева — Designer и EDT. Зарегистрировать оба как отдельные source-set'ы или только один? Какой основной?»
4. **`tools.platform.version` не удаётся определить**, а у пользователя установлено несколько версий. Спроси один раз.

Формулируй вопросы одним заходом, давай default и продолжай, если пользователь хочет оставить дефолты.

## Примеры взаимодействия

### Типовой проект с File-базой и Designer-исходниками

```bash
v8-runner config init --connection "File=build/ib"
v8-runner init       # создаёт файловую ИБ
v8-runner build      # применяет исходники
```

Никаких вопросов к пользователю.

### EDT-проект на платформе 8.3.20+

```bash
v8-runner config init --format edt --builder IBCMD
v8-runner init
v8-runner build
```

Без вопросов, если версия платформы определена.

### Смешанный Designer + EDT моно-репо

```bash
v8-runner config init       # регистрирует оба source-set'а через auto
```

Спрашивай только если пользователь хочет, чтобы был активен только один из них.

### Серверный проект

```bash
# После подтверждения от пользователя:
v8-runner config init --connection "Srvr=10.0.0.10:1541;Ref=dssl_drive_ai"
# v8-runner init НЕ запускается — база управляется внешне
v8-runner build       # применяет локальные исходники к существующей ИБ
```

Спрашивай один раз про `Srvr=...;Ref=...` и политику учётных данных (где они хранятся). Серверная конфигурация обычно живёт вне git, через `v8project.local.yaml`.

## После `config init`

Всегда изучай сгенерированный `v8project.yaml` до запуска изменяющих команд. Покажи пользователю:

- выбранные format и builder (`format`, `builder`),
- обнаруженные source-set'ы (`source-sets[*].name`, `path`),
- строку подключения,
- заполнен ли `tools.platform.version`,
- любые предупреждения, выведенные `config init` (часто это намёки на отсутствующие инструменты или необычные раскладки).

Если что-то выглядит не так, обращайся к явным `--format`, `--builder` или `--connection`, а не правь YAML руками — это сохраняет workflow воспроизводимым.
