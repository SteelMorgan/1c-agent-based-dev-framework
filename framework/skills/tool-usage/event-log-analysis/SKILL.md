# Анализ журнала регистрации (Event Log)

## Назначение

Навык учит агента **искать и анализировать события в журнале регистрации 1С** (ЖР). ЖР фиксирует все значимые события платформы: ошибки, действия пользователей, изменения данных, запуск/остановку сеансов.

**Принцип:** ЖР — read-only источник. Сырые записи не включать в вывод без маскирования персональных данных. По умолчанию использовать `mode: "minimal"`.

Для анализа производительности и технических событий (запросы СУБД, блокировки, исключения) — отдельный навык [`tech-log-analysis`](../tech-log-analysis/SKILL.md).

---

## Когда применять

| Триггер | Действие |
|---------|----------|
| Пользователь сообщает об ошибке | `search_event_log` с `level: "Error"` и узким окном времени |
| Нужно найти ошибку за конкретный период | `search_event_log` с `from`/`to` |
| Аудит действий пользователя | `search_event_log` с фильтром по пользователю |
| Проверка изменений конкретного объекта | `search_event_log` с фильтром по метаданным |
| Запущены тесты — нужно понять, работает ли база | `search_event_log` с `from: test_start_time`, `limit: 20` |

## Сценарии использования

### Сценарий 1: Поиск ошибок за период

**Шаги:**

1. Получить `cluster_guid` и `infobase_guid` из `cluster_map.yaml`.
2. Определить период: `from`/`to` в формате ISO 8601.
3. `search_event_log` с `level: "Error"`.
4. Анализ `records`: `event_time`, `event_presentation`, `comment`, `metadata_presentation`.
5. При упоминании объекта метаданных — `navigate_symbol` для перехода к коду.

```
search_event_log(
  cluster_guid: "...",
  infobase_guid: "...",
  from: "2025-02-11T13:00:00Z",
  to:   "2025-02-11T14:00:00Z",
  level: "Error",
  mode: "minimal",
  limit: 100
)
```

### Сценарий 2: Аудит действий пользователя

**Шаги:**

1. Получить GUID-ы из `cluster_map.yaml`.
2. `search_event_log` с фильтром по пользователю и/или событию (например `_$Data$.Write`).
3. Анализ последовательности событий — выявить подозрительные или аномальные действия.

### Сценарий 3: Оценка состояния базы после запуска тестов

**Цель:** понять, работает ли база после запуска тестов — идут ли события, есть ли ошибки.

**Шаги:**

1. **До запуска тестов** — запомнить текущее время (`test_start_time` в ISO 8601).
2. После запуска — `search_event_log` с `from: test_start_time`, `limit: 20`, без фильтра по уровню.
3. Оценить результат:
   - **Нет событий вообще** → база не запустилась или ЖР недоступен.
   - **Есть события, нет `Error`** → база работает, тесты идут.
   - **Есть `Error`-записи** → перейти к шагу 4.
4. При наличии ошибок — повторить с `level: "Error"` для фокусного анализа причин.

```
# Шаг 2: общая картина (последние 20 событий с момента старта)
search_event_log(
  cluster_guid: "...",
  infobase_guid: "...",
  from: "2025-03-01T10:00:00Z",   # test_start_time
  mode: "minimal",
  limit: 20
)

# Шаг 4: только ошибки (если нужно)
search_event_log(
  cluster_guid: "...",
  infobase_guid: "...",
  from: "2025-03-01T10:00:00Z",
  level: "Error",
  mode: "minimal",
  limit: 20
)
```

**Интерпретация последних 20 записей:**

| Картина | Вывод |
|---------|-------|
| Записей нет | База не запустилась / ЖР недоступен |
| Есть события, `Error` отсутствует | База живая, тесты выполняются |
| Последнее событие — завершение сеанса без ошибок | Тесты завершились успешно |
| Есть `Error` в `event_presentation` / `comment` | Тесты упали — анализировать `comment` и `metadata_presentation` |

### Сценарий 4: Ошибка «в 15:00 вчера»

**Шаги:**

1. Сузить окно до ±15 минут от указанного времени.
2. `search_event_log` с `level: "Error"` или без фильтра по уровню.
3. Если ошибок нет — расширить окно или проверить ТЖ через `tech-log-analysis`.

## Безопасность и персональные данные

| Правило | Описание |
|---------|----------|
| **Маскирование** | ЖР содержит ФИО пользователей, ИНН, контактные данные. Не включать сырые записи в вывод без маскирования. |
| **mode: minimal** | По умолчанию `mode: "minimal"` — меньше данных, меньше риск. |
| **Узкое окно** | Сужать `from`/`to` до минимально необходимого периода. |
| **limit** | Не запрашивать более 1000 записей за раз при первичном поиске. |

## Типичные ошибки

| Ошибка | Обходной путь |
|--------|---------------|
| GUID-ы не из `cluster_map.yaml` | Прочитать конфиг-файл; при отсутствии — запросить у пользователя |
| ClickHouse недоступен | Зафиксировать причину; предложить альтернативу через ТЖ |
| Слишком широкий диапазон — timeout | Сузить окно до 15–30 минут; уменьшить `limit` |
| Нет ошибок в ЖР | ЖР фиксирует только платформенные события; технические проблемы (СУБД, блокировки) — в ТЖ |
