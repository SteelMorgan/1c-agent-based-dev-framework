# Поверхностная диагностика

Топ-5 типовых отказов. Глубокие сценарии (разбор WS-фреймов, конфликты `schema_hash` на уровне реализации, метрики) — в `docs/architecture/` и `docs/decisions/`, при необходимости подключать отдельной задачей.

Где смотреть всегда:
- лог менеджера (stdout / journalctl, уровень `--log-level info`);
- `tools/call session_list` — состояние реестра;
- Prometheus `:9100/metrics` (если включены метрики) — `mcp_session_register`, `mcp_session_call`, `mcp_session_queue_depth`.

## 1. Менеджер не стартует

**Симптом:** `cargo run` / бинарь падает сразу.

**Проверка:**
- В логе `Address already in use` → порт `:4000` или `:4001` занят. `ss -lntp | grep -E '4000|4001'` — найти держателя.
- `workPath does not exist` / `permission denied` → каталог из `v8project.yaml` не создан или нет прав. Создать вручную, выставить владельца.
- `failed to parse config` → синтаксис YAML.

**Решение:** освободить порт (или сменить `bind_address` в конфиге), создать каталог, поправить YAML.

## 2. Менеджер запущен, клиент не появляется в `session_list`

**Симптом:** клиент 1С стартовал, но `session_list` пуст или не содержит его записи.

**Проверка:**
- В логе менеджера нет записи `accepting WebSocket connection` → клиент не дошёл до WS. Причины: неверный `manager_url`, недоступная сеть, `mcpMode` не равен `ws`.
- В логе менеджера есть `accepting WebSocket connection`, но нет `session.register` → handshake не дошёл до регистрации. Смотреть лог расширения `client_mcp` на стороне 1С: проблема в addin `session_y8` или devkit.
- В логе ошибка `register rejected: client_uid collision (Active)` → другая активная сессия уже использует этот `client_uid`. Сменить uid или дождаться её закрытия.

**Решение:** проверить параметры `/C` запуска клиента (`bootstrap.md`), уровень транспортного слоя.

## 3. Клиент в `session_list`, но tool не появился в `tools/list`

**Симптом:** `session_list` показывает клиента, но `<kind>__<ожидаемый_tool>` отсутствует на витрине.

**Проверка:**
- В записи `session_list` поле `tools` пустое → клиент не отправил `tools/publish`. Это работа расширения 1С, не менеджера.
- В записи `tools` есть имя, но на витрине его нет → проверить лог менеджера на `proxy_tool_hidden{reason:"schema_conflict"}` (см. кейс 4).
- На стороне 1С расширение, ответственное за этот tool, не загружено или его регистрация падает молча — смотреть лог расширения.

**Решение:** проверить, что в проекте есть нужное расширение и оно публикует tool; правильно ли указан `kind` при запуске клиента.

## 4. Tool скрыт с витрины (warning `schema_conflict`)

**Симптом:** ожидаемый `<kind>__<tool>` отсутствует. В логе менеджера: `proxy_tool_hidden{reason:"schema_conflict"}`.

**Причина:** два клиента того же `kind` зарегистрировали tool с одинаковым именем, но **разной** `input_schema`. Обычно — рассинхронизация версий расширения между клиентами.

**Проверка:** `session_list` показывает 2+ сессий одного `kind`; их `generation` или содержимое `tools` различается.

**Решение:**
- Привести расширение к одной версии на всех клиентах и переподключить.
- Если расхождение нужно осознанно — вызывать tool через низкоуровневый `session.call(session_id, tool_name, args)`.

## 5. `tools/call` вернул `no_live_session` (ADR-0035) или `session_id required`

**Симптом A — `isError:true`, `_meta.error_code="no_live_session"`** в ответе на `tools/call`:

```json
{ "isError": true, "_meta": { "error_code": "no_live_session", "kind": "...", "tool": "..." }, "content": [...] }
```

Это **не** JSON-RPC ошибка `method not found` (`-32601`) — tool на витрине есть (читается из persistent tools-cache, ADR-0035), но ни одна live-сессия с этим `kind` не подключена.

**Проверка/решение:**
- `session_list` пуст по этому `kind` → поднять клиент через оркестратор (`v8-runner`).
- Сессия есть, но `state="disconnected"` → дождаться reconnect или поднять заново.
- Если tool **никогда** не вернётся (расширение снято) — `tools_cache_reset` (см. кейс 6).

**Симптом B — `session_id required`:** на витрине свёрнутый tool от 2+ сессий, без явного `session_id` менеджер не знает, в какую слать.

**Проверка/решение:** взять нужный `session_id` из `session_list`, добавить параметром в `arguments`. См. `sessions-and-tools.md` § «свёртка».

## 6. Tool висит на витрине, хотя расширение удалено

**Симптом:** в `tools/list` присутствует `<kind>__<tool>`, который точно удалён из расширения и больше не должен появляться. Каждый его вызов теперь возвращает `no_live_session`.

**Причина:** persistent tools-cache (ADR-0035) хранит запись до истечения `tools_cache.cache_life_period` (дефолт 5d) с момента последнего `session.register`. Сам по себе кеш не «протухнет», пока не пройдёт TTL.

**Решение:**
- Точечный сброс: `tools/call tools_cache_reset` с `{"config_id": "<id>"}` — затирает запись только этой конфигурации. `config_id` берётся из `session_list[*].config_id` (или равен `kind`, если BSL-сторона не шлёт поле).
- Полный сброс: `tools/call tools_cache_reset` без аргументов — все записи удалены, файл `${workPath}/tools_cache.json` перезаписан в `{version:1, entries:[]}`, менеджер шлёт `notifications/tools/list_changed`.
- Альтернатива: подождать TTL (но это часто неприемлемо в dev).

**Когда `tools_cache_reset` НЕ нужен:** реконнект клиента (replace-семантика срабатывает сама), изменение `inputSchema` (следующий register перепишет), «давно не использовался» (TTL отвечает сам).

## 7. После рестарта менеджера витрина «правильная», но `tools/call` сразу `no_live_session`

**Симптом:** менеджер перезапущен, `tools/list` сразу полный (имена тулов всех конфигураций есть), но любой вызов возвращает `no_live_session`.

**Причина:** это **нормальное поведение по ADR-0035** — кеш на диске пережил рестарт, но WS-сессии 1С-клиентов нет. Менеджер честно говорит «имя знаю, обслуживать некому».

**Решение:** поднять нужный клиент через `v8-runner`. Кеш автоматически синхронизируется при первом `session.register`.

Это и есть основная мотивация persistent-кеша — стабильная поверхность `tools/list` для MCP-харнесов (в частности Claude Code), которые нестабильно реагируют на `notifications/tools/list_changed`.

---

Если симптом не покрыт — собрать в задачу: лог менеджера за интервал, снимок `session_list`, содержимое `${workPath}/tools_cache.json`, метрики `:9100/metrics`, версии расширений в проекте — и эскалировать.
