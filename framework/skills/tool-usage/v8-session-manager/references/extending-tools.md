# Разработка нового MCP-tool

> **Hard guardrail.** Создание, изменение или удаление MCP-tool — это изменение публичного контракта расширения. Запрещено выполнять **без прямого разрешения пользователя**. Без явного «да, добавь tool X в расширение Y» — стоп, спросить.

## Где живут tools

Tools регистрируются прикладными расширениями 1С (`exts/<extension>/`), не самим менеджером. Каждое расширение публикует свой набор:

| Расширение | Что обычно публикует |
|---|---|
| `client_mcp` | Базовый каркас, своих доменных tools обычно не имеет |
| `test_client` | Описание форм, чтение элементов, простые сценарии UI |
| `yaxunit_runner` | Запуск unit-тестов |
| `vanessa_test_client` | Управление Vanessa-сценариями |
| Любое новое расширение проекта | По доменной задаче |

При сомнениях, в каком расширении должен жить tool — **спросить пользователя**, не размещать самостоятельно.

## Алгоритм добавления tool (после получения разрешения)

1. **Уточнить контракт.** Имя tool, входная схема, выходные поля, побочные эффекты, ожидаемое поведение при ошибке. Зафиксировать в задаче (спека/ADR), если задача нетривиальная.
2. **Выбрать расширение.** Tool принадлежит одному `kind`. Если бизнес-логика разделена между расширениями — обсудить с пользователем.
3. **Реализовать BSL.** Регистрация tool через механизм `client_mcp` (см. skill соответствующего расширения; для `client_mcp` — отдельный skill, если есть). На витрину опубликуется как `<kind>__<имя_tool>`.
4. **Собрать проект.** Через профильный skill: `yaxunit-runner__build_project` для DRIVE или `v8-runner` для других проектов. Менеджер пересобирать **не нужно**.
5. **Запустить ИБ в режиме обновления**, если поменялись объекты метаданных (см. CLAUDE.md проекта).
6. **Перезапустить 1С-клиента.** Менеджер сам подхватит новые tools при `session.register` / `tools/publish`.
7. **Проверить регистрацию:**
   - `tools/call session_list` → клиент с нужным `kind` присутствует, в его поле `tools` появилось новое имя.
   - `tools/list` → на витрине есть `<kind>__<новый_tool>`.
   - Тестовый вызов `tools/call <kind>__<новый_tool>` с минимальным набором аргументов возвращает ожидаемый результат.

## Чего НЕ трогать

- **Исходники менеджера** (`src/`, `Cargo.toml`, `build.rs`). Расширение менеджера — отдельная задача в upstream-репозитории.
- **Транспорт `session_y8`.** Аддин не зависит от конкретных tools.
- **Имя на витрине вручную.** Префикс `<kind>__` ставит менеджер; задавать через `kind` клиента, не через переименование.
- **Существующие tools других расширений без отдельного разрешения.** Даже косметические правки имени/схемы — это смена публичного контракта.

## Признаки, что tool сделан правильно

- Появляется в `tools/list` сразу после регистрации клиента, без рестарта менеджера.
- `inflight` в `session_list` корректно увеличивается на время вызова и обнуляется после.
- При двух одновременно подключённых клиентах одного `kind` с этим tool — на витрине одна запись, вызов с `session_id` идёт в нужную сессию (см. `sessions-and-tools.md`).
- При разрыве WS клиента tool пропадает; при reconnect — возвращается без потерь.

Если что-то из этого не так — `troubleshooting.md`.
