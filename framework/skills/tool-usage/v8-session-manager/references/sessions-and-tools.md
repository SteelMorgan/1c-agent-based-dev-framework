# Сессии и tools

## Главный принцип: витрина — функция расширений, не менеджера

`tools/list` менеджера — динамическая витрина. Сам менеджер даёт ровно один встроенный tool: `session_list`. Всё остальное — это tools, которые подключённые 1С-клиенты регистрируют через `tools/publish`.

Следствия:
- **Нет клиента — нет tool.** Tool появляется в `tools/list` только когда клиент с соответствующим `kind` подключён и опубликовал tool.
- **Перезапуск клиента → пересборка витрины.** При разрыве WS tool пропадает, при reconnect появляется снова.
- **Нет расширения в проекте — tool никогда не появится.** Сначала разработка в `exts/<extension>/`, потом регистрация (см. `extending-tools.md`).
- **Запуск клиента — не задача менеджера.** Если ожидаемого tool нет — проверять оркестратор (типично `v8-runner`), а не менеджер.

## `session_list`

Единственный встроенный tool. Read-only снимок реестра сессий.

Поля записи:
- `session_id` — идентификатор сессии (равен `client_uid` клиента, если коллизий нет). Стабилен при soft-reconnect.
- `kind` — namespace клиента (из параметров запуска).
- `host_id`, `pid` — машина и процесс 1С.
- `infobase_name` — имя ИБ. Серверная — `Ref=` из строки соединения (например `dssl_drive_ai`); файловая — последний компонент пути из `File=`; иначе `"unknown"`. Различает сессии разных ИБ при одинаковых именах tools.
- `ib_session_number` — номер сеанса 1С в кластере (`НомерСеансаИнформационнойБазы()`, u32). Меняется при перезапуске процесса 1С. Нужен для соотнесения записи с сеансом в кластере 1С (RAC, ЦУП). Не путать с `session_id` менеджера.
- `last_call_at` — таймстемп последнего вызова в эту сессию.
- `inflight` — сколько вызовов в очереди прямо сейчас.
- `generation` — счётчик пересборки набора tools (растёт при `tools/list_changed`).
- `tools` — имена tools, опубликованных этой сессией (без префикса).

Использование:
- Понять, какие клиенты живы и под какими `session_id`.
- Перед вызовом проксированного tool — выбрать целевую сессию (по `kind`, `host_id`, `pid` или контексту задачи).
- Диагностика: длинный `inflight` или старый `last_call_at` — повод посмотреть `troubleshooting.md`.

## Имя tool на витрине

Опубликованное имя — `<kind>__<tool_name>`, разделитель — двойное подчёркивание. Примеры:

- клиент `kind=test_client` опубликовал `describe_form` → витрина: `test_client__describe_form`.
- клиент `kind=yaxunit_runner` опубликовал `run_module_tests` → витрина: `yaxunit_runner__run_module_tests`.

Это технический namespace — он гарантирует, что tools разных расширений не сталкиваются по имени. Адресация конкретной сессии при множественности — отдельный механизм (см. ниже).

## Свёртка однотипных tools и параметр `session_id`

Менеджер сворачивает однотипные регистрации. Группа определяется как `(kind, tool_name, schema_hash)`:

| Кейс | Что на витрине | Как вызывать |
|---|---|---|
| 1 сессия публикует tool | `<kind>__<tool>` (одна запись) | `session_id` опционален; менеджер сам подставит единственного кандидата |
| 2+ сессии с **равной** схемой | `<kind>__<tool>` (одна запись) | `session_id` **обязателен** — взять из `session_list` и положить в аргументы |
| 2+ сессий с **разной** схемой | tool **скрыт** + warning `proxy_tool_hidden{reason:"schema_conflict"}` | Только через низкоуровневый `session.call(session_id, tool_name, arguments)` |

Менеджер инжектит свойство `session_id` в `input_schema` опубликованного tool. При множестве кандидатов оно попадает в `required`. Перед отправкой вызова в клиента менеджер `session_id` из аргументов вынимает.

Алгоритм агента:
1. `tools/call session_list` — получить список сессий.
2. Выбрать целевую `session_id` по `kind`/контексту.
3. `tools/call <kind>__<tool>` с `session_id` в аргументах (или без, если кандидат единственный).
4. Если получена ошибка `session_id required` — добавить параметр; если `no active sessions` — клиент не подключён, идти в `troubleshooting.md`.

## Lifecycle сессии

- **FIFO в одну сессию.** Все вызовы в один `session_id` выполняются строго по порядку. Параллелизма внутри сессии нет.
- **Soft-reconnect.** При разрыве WS запись помечается `Disconnected` и держится `reconnection_grace_secs` (дефолт 30 с). Клиент, переподключившийся с тем же `client_uid`, получит ту же `session_id`, тот же набор tools и сохранённую очередь. После grace-таймаута запись удаляется.
- **Idle-killing.** Сессия без вызовов дольше `idle_timeout_secs` (дефолт 1800 с) удаляется по таймеру.
- **Round-robin.** При нескольких равнозначных кандидатах и вызове **без** `session_id` менеджер раздаёт запросы по кругу (per-group счётчик).
