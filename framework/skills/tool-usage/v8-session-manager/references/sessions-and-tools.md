# Сессии и tools

## Главный принцип: витрина — функция расширений + persistent-кеш

`tools/list` менеджера собирается из двух источников:

1. **Встроенные tools менеджера** — `session_list` и `tools_cache_reset` (ADR-0035). Доступны всегда.
2. **Проксированные tools** — из `tools_cache.json` (per-`(kind, config_id)`, TTL по умолчанию 5 суток), который обновляется при каждом `session.register` / `session.tools_changed` от подключённого 1С-клиента.

Следствия:
- **Имя tool в `tools/list` ≠ доступность вызова.** После disconnect клиента или рестарта менеджера имя остаётся на витрине из кеша, но вызов без live-сессии нужного `kind` вернёт MCP tool error `isError:true, _meta.error_code="no_live_session"` (не путать с JSON-RPC `method not found`).
- **Сначала расширение, потом регистрация.** Чтобы tool впервые попал в кеш, расширение должно быть в проекте и хоть раз успешно подключиться к менеджеру через WS (см. `extending-tools.md`).
- **TTL eviction.** Запись с `now - last_seen_at > cache_life_period` удаляется лениво на ближайшем `tools/list` или `session.register`. Дефолт — `5d`, настраивается через `tools_cache.cache_life_period` (см. `bootstrap.md`).
- **Запуск клиента — не задача менеджера.** Если нужен реальный вызов tool — клиент с этим `kind` должен быть поднят оркестратором (типично `v8-runner`), а не менеджером.

## `session_list`

Один из двух встроенных tools. Read-only снимок реестра сессий.

Поля записи:
- `session_id` — идентификатор сессии (равен `client_uid` клиента, если коллизий нет). Стабилен при soft-reconnect.
- `kind` — namespace клиента (из параметров запуска).
- `host_id`, `pid` — машина и процесс 1С.
- `infobase_name` — имя ИБ. Серверная — `Ref=` из строки соединения (например `dssl_drive_ai`); файловая — последний компонент пути из `File=`; иначе `"unknown"`. Различает сессии разных ИБ при одинаковых именах tools.
- `ib_session_number` — номер сеанса 1С в кластере (`НомерСеансаИнформационнойБазы()`, u32). Меняется при перезапуске процесса 1С. Нужен для соотнесения записи с сеансом в кластере 1С (RAC, ЦУП). Не путать с `session_id` менеджера.
- `last_call_at` — таймстемп последнего вызова в эту сессию.
- `inflight` — сколько вызовов в очереди прямо сейчас.
- `generation` — счётчик пересборки набора tools (растёт при `tools/list_changed`).
- `tools` — имена tools, опубликованных этой сессией (без префикса).
- `config_id` — идентификатор конкретной конфигурации/раскладки расширений на стороне 1С (ADR-0035). Один менеджер обслуживает несколько конфигураций; кеш ведётся по паре `(kind, config_id)`. Если клиент не передал поле в `session.register` — менеджер подставляет `config_id = kind`. Значение нужно для точечного `tools_cache_reset`.

Использование:
- Понять, какие клиенты живы и под какими `session_id`.
- Перед вызовом проксированного tool — выбрать целевую сессию (по `kind`, `host_id`, `pid` или контексту задачи).
- Диагностика: длинный `inflight` или старый `last_call_at` — повод посмотреть `troubleshooting.md`.

## Имя tool на витрине

Опубликованное имя — `<kind>__<tool_name>`, разделитель — двойное подчёркивание. Примеры:

- клиент `kind=test_client` опубликовал `describe_form` → витрина: `test_client__describe_form`.
- клиент `kind=yaxunit_runner` опубликовал `run_module_tests` → витрина: `yaxunit_runner__run_module_tests`.

Это технический namespace — он гарантирует, что tools разных расширений не сталкиваются по имени. Адресация конкретной сессии при множественности — отдельный механизм (см. ниже).

## Свёртка однотипных tools и параметр `session_id`

Менеджер сворачивает однотипные регистрации. Группа определяется как `(kind, tool_name, schema_hash)`:

| Кейс | Что на витрине | Как вызывать |
|---|---|---|
| 1 сессия публикует tool | `<kind>__<tool>` (одна запись) | `session_id` опционален; менеджер сам подставит единственного кандидата |
| 2+ сессии с **равной** схемой | `<kind>__<tool>` (одна запись) | `session_id` **обязателен** — взять из `session_list` и положить в аргументы |
| 2+ сессий с **разной** схемой | tool **скрыт** + warning `proxy_tool_hidden{reason:"schema_conflict"}` | Только через низкоуровневый `session.call(session_id, tool_name, arguments)` |

Менеджер инжектит свойство `session_id` в `input_schema` опубликованного tool. При множестве кандидатов оно попадает в `required`. Перед отправкой вызова в клиента менеджер `session_id` из аргументов вынимает.

Алгоритм агента:
1. `tools/call session_list` — получить список сессий.
2. Выбрать целевую `session_id` по `kind`/контексту.
3. `tools/call <kind>__<tool>` с `session_id` в аргументах (или без, если кандидат единственный).
4. Если получена ошибка `session_id required` — добавить параметр; если `no active sessions` — клиент не подключён, идти в `troubleshooting.md`.

## Lifecycle сессии

- **FIFO в одну сессию.** Все вызовы в один `session_id` выполняются строго по порядку. Параллелизма внутри сессии нет.
- **Soft-reconnect.** При разрыве WS запись помечается `Disconnected` и держится `reconnection_grace_secs` (дефолт 30 с). Клиент, переподключившийся с тем же `client_uid`, получит ту же `session_id`, тот же набор tools и сохранённую очередь. После grace-таймаута запись удаляется.
- **Idle-killing.** Сессия без вызовов дольше `idle_timeout_secs` (дефолт 1800 с) удаляется по таймеру.
- **Round-robin.** При нескольких равнозначных кандидатах и вызове **без** `session_id` менеджер раздаёт запросы по кругу (per-group счётчик).

## Persistent кеш и `tools_cache_reset` (ADR-0035)

Менеджер ведёт persistent-кеш проксированных tools в `${workPath}/tools_cache.json`. Ключ — пара `(kind, config_id)`; значение — список `ToolSpec` дословно из `session.register.tools`. Триггер обновления — приём `session.register` или `session.tools_changed`. Запись `last_seen_at` обновляется при каждом register; `tools/call` не bump'ает запись (иначе кеш «жив вечно»).

**Когда читается:**

- `tools/list` менеджера = `session_list` + `tools_cache_reset` + объединение всех записей кеша (lazy eviction по TTL).
- `tools/call <kind>__<tool>` — менеджер сначала ищет live-сессию через SessionDispatcher; не нашёл → возвращает `no_live_session` (см. ниже).

**`no_live_session` — что увидит агент.** Response в формате MCP tool call (НЕ JSON-RPC error):

```json
{
  "content": [{
    "type": "text",
    "text": "Tool '<kind>__<tool>' is currently unavailable: no live session of kind=<kind>."
  }],
  "isError": true,
  "_meta": {
    "error_code": "no_live_session",
    "kind": "<kind>",
    "tool": "<tool>"
  }
}
```

Это **не** означает, что tool «не существует» — у JSON-RPC `method not found` своя ветка. `no_live_session` означает: «в кеше я тебя знаю, но никто сейчас не обслуживает».

**Когда вызывать `tools_cache_reset`:**

1. **Tool осознанно удалён из расширения** и больше не появится. Без reset он провисит до истечения TTL (`tools_cache.cache_life_period`, дефолт 5 суток). Точечный сброс: `{"config_id": "<id>"}` — затрёт запись только для этой конфигурации, остальные `kind`/`config_id` останутся.
2. **Конфигурация снята полностью / `kind` больше не обслуживается** — `tools_cache_reset` без аргументов (полный сброс). Все записи удалены, файл атомарно перезаписан в `{version:1, entries:[]}`, отправлен `notifications/tools/list_changed`.
3. **Подозрение, что кеш «отстал»** от текущего состава расширения (например, после ручной правки extension'а вне нормального деплоя). Reset + первый register нового клиента восстановит правильный набор.

**Когда `tools_cache_reset` НЕ нужен:**

- При обычном reconnect'е клиента — replace-семантика срабатывает автоматически.
- При изменении `inputSchema` тула — следующий register перепишет запись.
- Просто потому что «давно не использовался» — TTL отвечает за это сам.

**Live-сессии reset НЕ трогает.** Если клиент подключён, его `register` после reset перезапишет запись в кеше. Это используется в сценарии «жёсткая чистка» для контролируемого пересоздания витрины.

**Конфиг секции `tools_cache:` и storage path** — см. `bootstrap.md` § «Persistent tools-cache».
