# Работа с технологическим журналом 1С (Tech Log)

## Назначение

Навык учит агента **управлять полным жизненным циклом технологического журнала (ТЖ)** и анализировать его содержимое. ТЖ — низкоуровневый инструмент платформы 1С для диагностики производительности: медленные запросы к СУБД, блокировки, исключения на уровне платформы, взаимодействие с внешними системами.

**Принцип:** ТЖ нагружает систему. Включать точечно, с минимально необходимым набором событий. Всегда восстанавливать исходную конфигурацию после диагностики.

Для поиска ошибок и аудита действий пользователей — отдельный навык [`event-log-analysis`](../event-log-analysis/SKILL.md).

---

## Полный жизненный цикл ТЖ

```
[1. Сохранить текущую конфигурацию]
        ↓
[2. Настроить нужные события]
        ↓
[3. Убедиться, что сбор идёт]
        ↓
[4. Воспроизвести проблему]
        ↓
[5. Прочитать и проанализировать записи]
        ↓
[6. Восстановить исходную конфигурацию / отключить ТЖ]
```

**Правило:** шаги 1 и 6 — обязательны. Никогда не оставлять ТЖ включённым после диагностики.

---

## Когда применять

| Триггер | Действие |
|---------|----------|
| Медленный запрос — нужно найти SQL | `search_tech_log` с `name: "DBMSSQL"` / `"DBPOSTGRS"` |
| Блокировки, deadlock | `search_tech_log` с `name: "TLOCK"` / `"TDEADLOCK"` / `"TTIMEOUT"` |
| Исключение платформы не в ЖР | `search_tech_log` с `name: "EXCP"` |
| Долгий серверный вызов | `search_tech_log` с `name: "CALL"` или `"SCALL"` |
| Перед анализом — статус ТЖ неизвестен | `logc_get_techlog_config` — прочитать текущую конфигурацию |
| ТЖ не ведётся | Полный цикл: сохранить → настроить → проверить → анализ → восстановить |

---

## Сценарии использования

### Режимы работы: пассивный и активный

- **Пассивный режим**: включили ТЖ и ждём естественного воспроизведения проблемы пользователем.
- **Активный режим**: включили ТЖ и сразу запускаем воспроизводящий сценарий (например, автотест/ручной сценарий).

В обоих режимах цикл одинаковый: сохранить → настроить → воспроизвести/дождаться → прочитать → восстановить.

### Сценарий 1: Полный цикл диагностики (основной)

**Шаги:**

**1. Сохранить текущую конфигурацию**
```
logc_save_techlog()
```
Возвращает `backup_id` — сохранить для шага 6.

**2. Прочитать текущее состояние (опционально)**
```
logc_get_techlog_config()
```

**3. Настроить нужные события**
```
logc_configure_techlog(
  location: "/var/log/1c/techlog",
  history: 24,
  events: ["EXCP", "DBMSSQL", "TLOCK", "TDEADLOCK"]
)
```

**4. Проверить, что сбор идёт**
```
logc_get_actual_log_timestamp()
```
Если метка времени обновляется — ТЖ активен.

**5. Воспроизвести проблему** (пользователь выполняет действие в 1С)

**6. Дождаться готовности лога к чтению (smart polling)**

После воспроизведения события данные могут появиться не мгновенно. Используй ограниченный цикл проверки готовности:

```bsl
// Псевдокод
ЦелевоеВремя = <время_воспроизведения_проблемы>;

Для Попытка = 1 По 10 Цикл
    ФактВремя = logc_get_actual_log_timestamp();
    Если ФактВремя >= ЦелевоеВремя Тогда
        Прервать;
    КонецЕсли;

    // Короткая пауза между проверками
    // (например, 3-5 сек; не бесконечный цикл)
КонецЦикла;
```

Если после лимита попыток метка не дошла до целевого времени — сообщи пользователю о проблеме парсинга/доставки лога и не делай ложных выводов по неполному окну.

**7. Прочитать записи**
```
search_tech_log(
  from: "2025-02-11T14:00:00Z",
  to:   "2025-02-11T14:15:00Z",
  name: "DBMSSQL",
  min_duration: 1000
)
```

**8. Восстановить исходную конфигурацию**
```
logc_restore_techlog(backup_id: "...")
```

**9. Финальная проверка (обязательно)**

- Убедиться, что исходная конфигурация действительно восстановлена.
- Явно сообщить пользователю итоговый статус:
  - `ТЖ восстановлен в исходное состояние`, или
  - `ТЖ отключён` (если исходно не был настроен).
- Если нужно продолжать расследование — зафиксировать, какой режим сейчас активен и кто отвечает за последующее отключение/восстановление.

Это снижает риск оставить ТЖ включённым надолго.

---

### Сценарий 1.1: Минимальный безопасный режим (если нельзя полностью отключить)

Иногда после диагностики требуется оставить базовый мониторинг. В этом случае вместо полного отключения включай **минимальный набор редких событий**, например:

- `EXCP` — исключения платформы
- `CONN` — события соединений
- `PROC` — системные процессы (если доступно в вашем окружении)

Правила:
1. Минимальный профиль — только по согласованию с пользователем/администратором.
2. Явно зафиксируй в ответе, что включён краткий/минимальный журнал, и перечисли активные события.
3. Зафиксируй, кто принял решение оставить минимальный профиль и кто его сопровождает далее.

Для большинства задач предпочтителен полный возврат через `logc_restore_techlog`.

---

### Сценарий 2: Анализ блокировок

**Шаги:**

1. Полный цикл (Сценарий 1), события: `["TLOCK", "TDEADLOCK", "TTIMEOUT"]`.
2. `search_tech_log` с `name: "TLOCK"` — найти блокирующие и блокируемые сессии.
3. Анализ `records`: `context`, `message`, `timestamp`, `session`.
4. Сопоставить с кодом через `navigate_symbol` по контексту вызова.
5. `logc_restore_techlog`.

---

### Сценарий 3: ТЖ уже был настроен — только чтение

Если ТЖ уже ведётся (например, настроен администратором):

1. `logc_get_techlog_config` — убедиться в наличии нужных событий.
2. `logc_get_actual_log_timestamp` — убедиться, что сбор актуален.
3. `search_tech_log` — читать записи.
4. **Не изменять конфигурацию**, не восстанавливать — ТЖ не наш.

---

### Сценарий 4: Быстрое отключение ТЖ

Если нужно срочно отключить (например, ТЖ заполняет диск):

```
logc_disable_techlog()
```

После решения проблемы — `logc_restore_techlog(backup_id)` если был сохранён бэкап.

---

### Сценарий 5: Активная диагностика через воспроизводящий тест

Подходит, когда есть стабильный автотест/ручной сценарий, вызывающий проблему.

1. Сохранить текущую конфигурацию (`logc_save_techlog`).
2. Включить ТЖ под конкретные события.
3. Запустить воспроизводящий сценарий.
4. Выполнить smart polling по `logc_get_actual_log_timestamp`.
5. Прочитать `search_tech_log` в узком окне времени вокруг теста.
6. Восстановить конфигурацию (`logc_restore_techlog`).
7. Явно подтвердить пользователю финальный статус ТЖ.

Преимущество: меньше шума в логе и проще привязка записей к конкретному шагу теста.

## События ТЖ — справочник

| Событие | Описание | Когда использовать |
|---------|----------|--------------------|
| `EXCP` | Исключения платформы | Ошибки, не видные в ЖР |
| `DBMSSQL` | Запросы к MS SQL | Медленные запросы, SQL-план |
| `DBPOSTGRS` | Запросы к PostgreSQL | Медленные запросы |
| `TLOCK` | Управляемые блокировки | Конфликты блокировок |
| `TDEADLOCK` | Взаимоблокировки | Deadlock-ситуации |
| `TTIMEOUT` | Таймауты блокировок | Зависания при блокировке |
| `CALL` | Серверные вызовы | Медленные серверные процедуры |
| `SCALL` | Системные вызовы | Внутренние вызовы платформы |
| `CONN` | Соединения | Проблемы подключения |
| `SDBL` | Запросы языка запросов | Трансляция в SQL |

**Стандартный набор для начала диагностики:** `["EXCP", "DBMSSQL", "TLOCK", "TDEADLOCK"]`

## Capabilities

| Capability | Назначение |
|------------|------------|
| `search_tech_log` | Поиск по записям ТЖ |
| `logc_get_techlog_config` | Прочитать текущую конфигурацию ТЖ |
| `logc_save_techlog` | Сохранить конфигурацию перед изменением |
| `logc_configure_techlog` | Настроить события, путь, период хранения |
| `logc_get_actual_log_timestamp` | Проверить, что сбор идёт |
| `logc_restore_techlog` | Восстановить сохранённую конфигурацию |
| `logc_disable_techlog` | Отключить ТЖ |
| `navigate_symbol` | Переход к коду по контексту из записи ТЖ |

## Чеклист после анализа (обязательный)

1. Анализ завершён и выводы зафиксированы.
2. ТЖ приведён в ожидаемое состояние:
   - либо восстановлен через `logc_restore_techlog(backup_id)`,
   - либо отключён через `logc_disable_techlog()` (если так согласовано).
3. Пользователю явно сообщён финальный статус ТЖ.
4. Если оставлен минимальный мониторинг — зафиксированы срок и ответственный.

Шаблон сообщения пользователю:
- `✅ Анализ завершён. ТЖ восстановлен в исходное состояние.`
- `✅ Анализ завершён. ТЖ отключён.`
- `✅ Анализ завершён. Включён минимальный профиль (события: <список>).`
- `✅ Анализ завершён. Включён минимальный профиль; решение согласовано с <кто>.`

## Типичные ошибки

| Ошибка | Обходной путь |
|--------|---------------|
| Забыли `logc_save_techlog` перед настройкой | Спросить пользователя о текущей конфигурации; документировать изменение |
| ТЖ не активен после `configure` | Платформа требует перезапуска служб; предупредить пользователя |
| `logc_get_actual_log_timestamp` не обновляется | Служба не перезапущена или неверный путь `location` |
| Слишком много событий — диск заполняется быстро | Ограничить набор событий; уменьшить `history` |
| Забыли восстановить конфигурацию | Всегда завершать цикл `logc_restore_techlog` |
| `search_tech_log` возвращает пусто | Проверить окно времени; убедиться, что событие было после включения ТЖ |
