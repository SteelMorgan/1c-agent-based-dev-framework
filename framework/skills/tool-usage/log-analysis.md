# Анализ логов (Log Analysis)

## Назначение

Навык учит агента **работать с журналами 1С** — журналом регистрации (ЖР) и технологическим журналом (ТЖ). Логи используются для отладки production-проблем, анализа производительности, аудита действий пользователей.

**Принцип:** Логи — read-only источник для диагностики. Не включать сырые данные логов в вывод без маскирования персональных данных.

---

## Когда применять

| Триггер | Действие |
|---------|----------|
| Отладка ошибок в production | `search_event_log` — поиск ошибок за период |
| Анализ производительности | `search_tech_log` — долгие запросы, блокировки |
| Пользователь сообщает об ошибке «вчера в 15:00» | `search_event_log` с узким окном `from`/`to` |
| Проверка действий пользователя | `search_event_log` — события, связанные с пользователем |
| Таймауты, deadlock | `search_tech_log` с фильтром `TLOCK`, `TDEADLOCK`, `TTIMEOUT` |
| Перед анализом ТЖ — ТЖ не ведётся | `configure_tech_log` — включить сбор нужных событий |

---

## Сценарии использования

### Сценарий 1: Поиск ошибок в журнале регистрации

**Шаги:**

1. Получить `cluster_guid` и `infobase_guid` из `cluster_map.yaml` (обязательно).
2. Определить период: `from` (начало), `to` (конец) в формате ISO 8601.
3. `search_event_log` с `level: "Error"` (по умолчанию).
4. Анализ `records` — `event_time`, `event_presentation`, `comment`, `metadata_presentation`.
5. При необходимости — `navigate_symbol` для перехода к метаданным, указанным в ошибке.

**Пример:** Найти все ошибки за последний час.

```
search_event_log(
  cluster_guid: "...",
  infobase_guid: "...",
  from: "2025-02-11T13:00:00Z",
  to: "2025-02-11T14:00:00Z",
  level: "Error",
  mode: "minimal",
  limit: 100
)
```

### Сценарий 2: Поиск долгих запросов в технологическом журнале

**Шаги:**

1. Убедиться, что ТЖ ведётся: `configure_tech_log` action `read` или `get_timestamp`.
2. Если ТЖ не настроен — `configure_tech_log` action `configure` (требует участия пользователя для перезапуска служб).
3. `search_tech_log` с `name: "DBMSSQL"` или `"DBPOSTGRS"` для запросов СУБД.
4. Анализ `records` по полю `duration` — выявить долгие запросы.
5. Сопоставить с кодом через `metadata_presentation` и `navigate_symbol`.

### Сценарий 3: Анализ блокировок и deadlock

**Шаги:**

1. `search_tech_log` с `name: "TLOCK"` или `"TDEADLOCK"` или `"TTIMEOUT"`.
2. Анализ `records` — `context`, `message`, `timestamp`.
3. Выявить конфликтующие сессии, объекты блокировок.

### Сценарий 4: Включение технологического журнала

**Шаги:**

1. `configure_tech_log` action `read` — проверить текущую конфигурацию.
2. При необходимости — action `configure` с параметрами:
   - `cluster_guid`, `infobase_guid`
   - `location` — путь к файлам логов
   - `history` — время хранения (12–48 часов)
   - `events` — массив событий: `['EXCP', 'DBMSSQL', 'TLOCK']` и т.д.
3. После изменения — пользователь должен перезапустить службы 1С.
4. `configure_tech_log` action `get_timestamp` — проверить, что сбор идёт.

## Безопасность и персональные данные

| Правило | Описание |
|---------|----------|
| **Маскирование** | Логи могут содержать ФИО, ИНН, контакты. Никогда не включать сырые записи в вывод без маскирования. |
| **Режим minimal** | По умолчанию использовать `mode: "minimal"` — экономия токенов и снижение риска утечки лишних данных. |
| **Ограничение limit** | Не запрашивать более 1000–10000 записей за раз. |
| **Узкое окно** | Сужение `from`/`to` — меньше данных, быстрее ответ, меньше риск. |

## MCP-инструменты

| Инструмент | MCP-сервер | Назначение |
|------------|------------|------------|
| `search_event_log` | log-checker | Поиск по журналу регистрации (ЖР) |
| `search_tech_log` | log-checker | Поиск по технологическому журналу (ТЖ) |
| `configure_tech_log` | log-checker | Управление конфигурацией ТЖ |
| `navigate_symbol` | lsp-bridge | Переход к коду по метаданным из логов |

## Типичные ошибки и обходные пути

| Ошибка | Обходной путь |
|--------|---------------|
| GUID-ы не из `cluster_map.yaml` | Агент обязан сначала прочитать конфигурационный файл; запросить у пользователя корректные GUID. |
| ClickHouse недоступен | Capability `search_event_log` зависит от ClickHouse; зафиксировать причину пропуска. |
| Слишком широкий временной диапазон | Сужение окна до 15–30 минут; уменьшение `limit`. |
| Технологический журнал не ведётся | `configure_tech_log` action `configure`; после настройки — перезапуск служб пользователем. |
| Таймаут при большом объёме логов | Уменьшить `limit`, сузить `from`/`to`; использовать `mode: "minimal"`. |
| Неизвестная структура `cluster_map.yaml` | Документировать ожидаемый формат; при отсутствии — запросить GUID у пользователя. |
