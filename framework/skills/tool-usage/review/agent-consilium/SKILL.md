# Архитектурный консилиум — правила для вызывающего

Этот навык — playbook вызывающего агента (primary agent), который созывает консилиум,
модерирует его фазы и получает advisory-вердикт. Механика протокола, схемы данных и
контракт адаптера здесь НЕ документируются — вызывающему они не нужны (см. раздел
«Что вызывающему не нужно знать»).

## Что это и governance

Консилиум — мультимодельное обсуждение material trade-off в архитектуре или требованиях: несколько фронтир-моделей
разных семейств (по единому реестру `review-harness/adapters.yaml`) работают в общем контексте по протоколу
«предложение → критика → ответ на критику», далее синтез модератора и вердикт с
minority report.

- **Advisory-only (FR-13).** Вердикт — НЕ acceptance/finalization gate и не условие
  никакого gate. Решение принимает primary agent (или человек), вердикт — вход для него.
- **Модератор — primary agent, не скрипт.** Дайджесты, синтез и вердикт авторит вы.
  Ядро (`scripts/consilium.py`) контролирует формальные инварианты протокола и
  отказывает fail-closed при их нарушении — обойти предикаты ядра нельзя.
- **Участники read-only** и работают только с sandbox-копиями материалов (по умолчанию
  focused-paths, НЕ `--full-context`); изменение реального проекта участником запрещено.
- Это оркестрационный слой НАД общей библиотекой `review-harness` (адаптеры,
  контракт, sandbox-lifecycle, track record, единый реестр); он её не заменяет
  и не изменяет.

## Когда созывать

Созывайте консилиум на **material-развилках с реальными trade-offs**:
несколько обоснованных вариантов, различимые долгосрочные последствия, неочевидный
компромисс между осями (производительность/сложность/стоимость сопровождения). Ценность
консилиума — в адверсарной полемике разных семейств моделей: рекомендуемый состав —
≥2 участников из ≥2 разных family (это и кворум: при невыполнении ядро откажет
fail-closed); слабее трёх семейств — по возможности.

Для бизнес-трактовок, границ scope, уровней MUST/SHOULD/MAY и проверяемости используй
домен `requirements`; он не принимает решения технического дизайна. Для архитектурных
границ, API и data flow используй подходящий архитектурный домен.

## Когда НЕ созывать

- **Мелкие и локальные решения** (naming, локальный рефакторинг, очевидный выбор без
  trade-offs) — цена консилиума 16–25 вызовов адаптеров (default при 3 участниках,
  жёсткий потолок 31) и десятки минут wall-clock; на локальную развилку это
  несоразмерно.
- **Как замену собственному суждению primary agent.** Консилиум — advisory-вход,
  а не оракул: разбор вердикта и финальное решение остаются на вас.
- **Как acceptance-вердикт.** Консилиум не подтверждает и не блокирует приёмку работы;
  для этого существуют review/finalization gates проекта.

## Как сформулировать вопрос

Качество вердикта определяется качеством вопроса в `convene --question`. Хороший
вопрос содержит:

1. **Контекст**: что за система/модуль, какие ограничения и нефункциональные требования
   действуют (ссылки на реальные артефакты репозитория).
2. **Варианты между которыми выбираем** — или явное «поле открыто», если вариантов
   пока нет.
3. **Критерии выбора**: по каким осям сравнивать (cost, сложность, миграция, риск).

Материалы передавайте через `--paths` (focused-paths), а не полным контекстом.

**Антипаттерн** — размытый вопрос («как лучше сделать авторизацию?»): участники
построят модели под разные скрытые допущения, полемика уйдёт в перекрёстную критику
несопоставимых решений, синтез выродится в компиляцию общих мест. Если вопрос не
укладывается в конкретную развилку — сначала сузьте его сами.

## Жизненный цикл вызова

Команды (ядро — `scripts/consilium.py`, запуск из корня репозитория):

```bash
SKILL_DIR="<абсолютный каталог навыка agent-consilium из каталога доступных skills>"
test -f "$SKILL_DIR/scripts/consilium.py"

python3 "$SKILL_DIR/scripts/consilium.py" doctor --json        # pre-flight healthcheck реестра
python3 "$SKILL_DIR/scripts/consilium.py" convene --question "<архитектурный вопрос>" \
    [--caller <id>] [--paths <focused paths>] [--timeout-sec 900]
python3 "$SKILL_DIR/scripts/consilium.py" round <session_id> [--digest-file f] \
    [--kill <participant_id>] [--synthesis-file f]
python3 "$SKILL_DIR/scripts/consilium.py" status <session_id>  # фаза/раунд/живые модели/счётчик вызовов
python3 "$SKILL_DIR/scripts/consilium.py" verdict <session_id> --decision-file f [--escalate]
python3 "$SKILL_DIR/scripts/consilium.py" close <session_id>   # парность cleanup (FR-10)
```

Пошагово:

1. **`doctor --json`** — pre-flight: доступность адаптеров и кворум. `convene` прогоняет
   doctor автоматически и исключает недоступного участника с явной записью; при
   нарушении кворума — отказ fail-closed.
2. **`convene --question ... [--caller <id>] [--domain <id>] [--paths ...]`** — создаёт сессию.
   **Правило композиции (FR-05): состав ВСЕГДА = все `enabled` из `review-harness/adapters.yaml`
   (включая семейство вызывающего — вы участвуете рядовым членом через свой адаптер)
   + вы как модератор.** Модератор не назначается — он тот, кто созвал консилиум;
   флага `--moderator` не существует. `--caller <id>` фиксирует id вызывающего в
   `session.json.moderator_id` и track record (default: `primary`). Флага `--members`
   не существует: состав — строго все enabled (точка, не опция); `--caller`,
   совпадающий с участником реестра, помечается как ваша модель-участник; caller
   вне реестра — легитимный модератор без адаптера (warning). Ядро назначает роли фазы A.
   **`--domain <id>`** (CONS-03) выбирает доменный пакет из `review-harness/domains.yaml`
   (default: `architecture` — текущее поведение): роли, линзы, риск-чеклист и
   evidence-требования пакета подставляются в промпты участников; снапшот каталога
   фиксируется в `session.json` (правка `review-harness/domains.yaml` посреди сессии на неё не влияет).
   Неизвестный id — отказ с перечнем доступных.
3. **`round <id>`** — фаза A: каждый участник вслепую выдвигает свою версию решения
   (единственная волна без дайджеста).
4. **Цикл фазы B (по 2 волны на раунд)**:
   - После каждой волны ядро генерирует **экстрактивный черновик дайджеста**
     (`digests/draft-*.md`, CONS-02 OPT-2): только факты ходов (атаки, изменения
     позиций, заимствования, findings) в fenced-блоках `participant-extract`,
     анонимизировано. Черновик — ваш помощник, НЕ автоподстановка: прочитайте
     `bundles/wave-*.bundle.md` и черновик, проверьте против transcript и напишите
     **финальный дайджест** сами (ядро отклоняет волну без него — digest-gate
     fail-closed; реальные id и превышение `context_budget` отклоняются) →
     `round <id> --digest-file ...` (волна «атака»);
   - снова дайджест по новому bundle → `round` (волна «ответ на критику»).
   - После каждого раунда ядро само оценивает стоп-условия (конвергенция ≤2 живых
     моделей / лимит раундов 2→3→4 / stalemate) и, если живых >2, печатает
     **kill-рекомендацию** с детерминированным кандидатом и прокси-метриками.
   - Kill (если рекомендован): `round <id> --kill <candidate> --digest-file ...` —
     ядро применяет ТОЛЬКО детерминированного кандидата (иное — отказ, exit 4) и
     проводит волну финального заявления исключённой модели.
5. **Фаза C**: вы пишете синтез итоговой модели. Формат обязателен (CONS-02 OPT-3):
   поэлементно `- [E<n>] <текст> (refs: seq:<n>, …)` (диапазоны запрещены, нужен
   ≥1 элемент) + секция `## Обоснование исключения вкладов` (почему вклад каждой
   невошедшей живой модели исключён) → `round <id> --synthesis-file ...`.
   Любой текст вне шаблона и секций — отказ fail-closed.
6. **Фаза D (ред-тим) — условная**: ядро пропускает её, только если ВСЕ элементы
   синтеза трассируются к единственной живой активной модели-источнику
   (membership-проверка по structured.elements; любая неопределённость → D
   выполняется). При пропуске — переход C→E без вызовов, причина в transcript и
   вердикте. Иначе: дайджест → `round <id> --digest-file ...` (1 атака на склейку,
   роль по кросс-ротации); дайджест → `round` (авторы подтверждают/оспаривают
   неискажённость вклада). Дефекты чините точечно, без перезапуска цикла.
7. **Фаза E**: `verdict <id> --decision-file ...` (шаблон —
   `references/consilium-prompts.md`, ядро проверяет обязательные разделы fail-closed);
   при material-разногласии добавьте `--escalate`.
8. **`close <id>` — обязательно всегда** (см. cleanup-дисциплину ниже).

`status <id>` в любой момент показывает фазу, раунд, живые модели, unresponsive-
участников, фактическое число вызовов адаптеров и wall-clock. Дополнительно (RVSW-01):
liveness-классификация участников (`active`/`quiet`/`dead_watcher` — диагностика,
не kill) и последний чекпоинт прогресса (`progress.jsonl` сессии: границы фаз/раундов).

## Наблюдение за сессией: watch (CONS-05)

`watch <id>` — read-only слой наблюдения за работающим консилиумом (вариант A:
исполнение остаётся headless, добавлена только observability). Исполнение и
протокол не меняются: watch не пишет в состояние сессии, не вызывает адаптеры
и сеть, не является гейтом и не входом для человеческих ходов.

```bash
python3 "$SKILL_DIR/scripts/consilium.py" watch <session_id> \
    [--participant <id>] [--interval 3] [--excerpt-lines 6] [--once]
```

- **По умолчанию — единый live-view**: фаза/раунд/волна, счётчик вызовов,
  последний чекпоинт и по каждому участнику блок: state, живость, счётчики
  вызовов/ретраев, последний ход (excerpt N последних строк). Во время волны
  файлы сессии молчат (пишутся после блокирующего run_wave), поэтому live-view
  дополнительно показывает **живой прогресс инвокации из runtime.json
  sandbox'а**: state/phase/elapsed, счётчики событий и tool-вызовов адаптера.
  Liveness-класс (`active`/`quiet`/`dead_watcher`) печатается только при идущей
  инвокации; в паузе между волнами — явное «инвокация не идёт» + возраст
  последней активности. Обновление по poll-интервалу (`--interval`, default
  3 с); реальные id участников показываются намеренно — наблюдатель это вы
  (модератор), не участники.
- **`--participant <id>`** — поток одного участника для отдельной панели:
  печатает его новые ходы и system-события о нём по мере появления
  (tail-семантика поверх transcript.jsonl).
- **Завершение**: watch выходит с понятным сообщением, когда сессия достигла
  терминального состояния (вердикт/close/удаление каталога); Ctrl+C — чистый
  выход, состояние сессии не затрагивается никогда.
- **`--once`** — один кадр без цикла (диагностика, тесты).

**Интерактивное наблюдение в herdr — ТОЛЬКО по явному запросу пользователя** (не по
умолчанию и не как шаг протокола): `scripts/consilium-watch-herdr.sh <session_id>` —
создаёт раскладку панелей herdr и запускает в каждой свой `watch`. Решение владельца
2026-08-04: раскладка панелей не создаётся автоматически; базовый способ наблюдения —
`watch` в текущей панели. Детали — `references/watch-mode.md`.

## Human-critic режим (CONS-06, опционально)

По умолчанию выключен. `convene --human-critic [--human-wait-cap-sec 1800]`
включает участие человека ТОЛЬКО в атакующих волнах (attack фазы B, redteam
фазы D): человек не генерирует идеи, не влияет на кворум/family-разнообразие,
track-record и kill-метрики; для участников он — обычный anon_id из общего
пространства `create_anon_map`, авторство не раскрывается.

- На атакующей волне ядро ждёт human-ход ДО запуска LLM-волны (антиякорение):
  модератор показывает человеку bundle, собирает критику в turn-файл и подаёт
  `round <id> --human-turn-file <path>` (JSON `{content, structured,
  human_approved: true}`; без аттестации — fail-closed отказ; максимум 1 ход
  на волну). Внутренние id участников в файле запрещены (lint).
- Ожидание останавливает wall-clock бюджет (`wall_clock.paused_sec`,
  экспонируется в `status`/`watch` как awaiting_human). По капу ожидания —
  `awaiting_moderator_decision`: round не исполняется до явного решения:
  `--human-continue-wait` | `--human-skip-wave` (одноразово) |
  `--human-withdraw --reason "..."` (свёртывание режима).
- Если человек сделал ≥1 ход в фазе B, фаза D обязательна (skip-предикат
  отменяется); участие human-critic раскрывается отдельной строкой в вердикте.

Полный протокол работы модератора с человеком (показ bundle, сбор критики,
запреты раскрытия авторства и маркировки вкладов, остаточные риски) —
`references/human-critic-playbook.md`.

## Доменные пакеты (CONS-03)

Консилиум вызывается в контексте доменного пакета (`review-harness/domains.yaml`): роли с линзами,
машиночитаемый риск-чеклист и evidence-требования домена.

- Доступные пакеты: `architecture` (default — текущее поведение), `requirements`,
  `security-compliance`, `data-schema-evolution`, `incident-postmortem`, `design-direction`.

**Какой пакет выбрать** (если ни один не подходит — используйте `architecture`):

| Пакет | Когда выбирать |
|-------|----------------|
| `requirements` | Бизнес-требования, RFC 2119, scope, acceptance criteria и test plan без выбора технического дизайна |
| `security-compliance` | Угрозы, уязвимости, ПДн/152-ФЗ, секреты/ключи, контур доступа |
| `data-schema-evolution` | Изменение контрактов/схем/моделей данных с существующими потребителями |
| `incident-postmortem` | Разбор уже случившегося сбоя/инцидента (причины, не устранение) |
| `design-direction` | Направление страницы/миниаппа/UX до реализации (не pixel-review) |
| `architecture` | Границы сервисов, структура решений, всё остальное (default) |
- **Формат хода участников ОБЯЗАТЕЛЬНО включает `risk_checklist_responses`** (для всех
  доменов, включая default): по каждому применимому к типу хода пункту чеклиста —
  `{"item_id", "verdict": "hit|clear|na", "note"}`; `hit`/`na` требуют note.
  Невалидный ход отклоняется fail-closed (ровно один контент-retry через ask, далее —
  unresponsive). `hit` с note засчитывается ядром как новый finding в предикатах
  стоп-условий; ответы чужих чеклистов участники не видят.
- Чужой домен в истории ролей/strengths на назначение не влияет (домен-фильтр);
  статистика чеклиста (`hit/clear/na`) и домен пишутся в track record.

## Обязанности и запреты модератора (FR-05)

Модератор — всегда вызывающий primary agent: консилиум всегда = все enabled-участники
реестра (включая вашу модель как рядового члена) + вы как модератор. Он:

- **НЕ голосует и НЕ выдвигает собственную модель.** Хотите высказать мнение —
  оформите себя рядовым участником через свой адаптер (запись в `review-harness/adapters.yaml`),
  и участвуйте на общих правилах.
- **Авторит дайджесты** для каждой волны после первой: сжатая карта живых моделей и
  полемики по anon_id, без реальных id участников (анонимизация в выдаче).
- **Kill — только по рекомендации ядра**: кандидат определяется детерминированным
  критерием из структурированных ходов; ядро отклоняет `--kill`, не совпадающий с
  кандидатом (защита от ownership bias). Права «убить по своему усмотрению» у
  модератора нет.
- **Синтез фазы C — с обязательной traceability**: каждый элемент склейки ссылается
  на `seq:<n>` модели-источника.
- **Minority report — только дословно**: тексты несогласных и финальные заявления
  исключённых моделей включаются без редактирования.
- **Эскалация к человеку** — только при material-разногласии (меняющем выбранный
  вариант вердикта).

## Как читать вердикт

`verdict.md` (обязательные разделы проверяются ядром): решение (синтез с seq-
traceability) · kill-log · minority report (дословно) · флаг состава · инциденты ·
стоимость · стоп-условие завершения фазы B · эскалация.

- **Minority report — обязательная часть решения**, а не приложение «для справки»:
  разбирайте его наравне с решением. Единогласие — анти-цель протокола; отсутствие
  несогласных — повод для недоверия, а не для радости.
- **Флаг состава**: выполнен/деградировал ли кворум и было ли family-разнообразие;
  при однородности family вердикт содержит явное предупреждение — учитывайте его как
  пониженную надёжность second-opinion.
- **Стоп-условие**: `converged` — полемика сошлась; `round_limit`/`stalemate`/
  `invocation_ceiling` — синтез сделан из текущего состояния, и его уверенность ниже.
- **Эскалация**: `ESCALATE_TO_HUMAN` выставляется только при material-разногласии —
  такой вердикт нельзя принимать без человека.
- Вердикт — вход для primary agent. Финальное решение (принять, изменить, отклонить)
  принимаете вы или человек; консилиум не является условием никакого gate.

## 🔴 КРИТИЧНО: cleanup-дисциплина (FR-10)

> **Уровень: CRITICAL / MUST.** По прецеденту gate-правила `cross-provider-review.md`, усилено двойным
> контуром. Автоматической уборки нет — только парность и checkpoint. Осиротевшие
> sandbox остаются на диске навсегда.

| Требование | Описание |
|-----------|----------|
| Парность convene↔close | Любой `convene` ОБЯЗАН иметь парный `close` на ЛЮБОМ пути завершения: вердикт, stalemate, эскалация, ошибка адаптера, отказ от консилиума |
| Парность start↔close участников | Каждый участник — сессия адаптера с собственным sandbox в `.review-sandboxes/`; `close` консилиума закрывает ВСЕХ участников |
| Cleanup fail-closed | При неуспешном close участника сессия НЕ удаляется и НЕ помечается closed: `cleanup.status=failed`, exit code 5; повторный `close` идемпотентен — **retry обязателен**, пока cleanup не пройдёт |
| `--keep` только forensic | `close --keep` сохраняет каталог сессии — ТОЛЬКО для forensic/debug с явной письменной причиной |
| Lock-only tombstone | После успешного adapter `close` допустим канонический lock-only tombstone, распознанный `adapter_contract.is_lock_only_tombstone()`; любой payload, неожиданный файл/каталог или symlink блокируют checkpoint |
| Отчёт о cleanup | В итоговый отчёт задачи записывается cleanup status каждой сессии и каждого участника: `closed` или обоснованный `kept` |

## Диагностика сбоев

- **Unresponsive-участник**: таймаут вызова (per-invocation, default 900 s,
  CONS-02 OPT-1) → участник
  помечается `unresponsive`, его модель замораживается (остаётся объектом критики и
  заимствования, ходов не делает); ошибка адаптера → ровно один retry → `unresponsive`.
  Протокол продолжается без него; факт фиксируется в transcript, `status` и вердикте.
  Участник, не доживший до первого proposal, исключается из живых моделей и
  kill-кандидатов. Если исключение нарушает кворум — сессия завершается с фиксацией
  причины и парным `close` (exit 3).
- **Отказы ядра (fail-closed)**: exit 2 — нарушение протокола/кворума; exit 4 —
  `--kill` не по детерминированному кандидату; exit 5 — cleanup failed (retry `close`).
  Не пытайтесь «обойти» отказ ядра ручными правками состояния сессии.
- **Где смотреть**: `status <id>` — фаза, живые модели, unresponsive, счётчик вызовов,
  wall-clock; transcript и логи вызовов адаптеров — в `.consilium-sessions/<id>/`;
  логи адаптеров участников — `status`/`log` соответствующего адаптера из
  `review-harness/scripts/adapters/` по `review_id` участника.
- **Таймауты (CONS-02 OPT-1)**: per-invocation default 900 s (`--timeout-sec`),
  волна = T + 240 s, wall-clock сессии = `max(7200, 13 × (T + 240) + 1800)` s
  (default 16620 s, предупреждение на 75 %) — пересчитывается от `--timeout-sec`.
  При приближении к cap — доводите до вердикта
  из текущего состояния и закрывайте сессию, не начинайте новых раундов.
