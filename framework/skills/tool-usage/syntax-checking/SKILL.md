# Проверка синтаксиса (Syntax Checking)

## Назначение

Навык учит агента **правильно использовать возможности проверки синтаксиса** BSL-кода. Проверка синтаксиса — обязательный этап после любого изменения кода. Без неё агент может «успешно» завершить задачу, а код окажется нерабочим.

**Принцип:** Каждое изменение кода должно быть проверено. Синтаксические ошибки обнаруживаются до коммита, а не в рантайме.

---

## Когда применять

| Триггер | Действие |
|---------|----------|
| После каждого изменения BSL-кода | Вызвать `check_syntax` |
| Перед коммитом / сохранением | Обязательная проверка изменённых файлов |
| После рефакторинга | Проверка всей затронутой области |
| После массового переименования (`rename_symbol`) | Проверка затрагиваемых модулей |
| Пользователь сообщает об ошибке компиляции | Сначала `check_syntax` для локализации |
| Перед запуском тестов | Рекомендуется (тесты могут не запуститься при ошибках синтаксиса) |

---

## Сценарии использования

### Сценарий 1: Стандартная проверка после правки

**Шаги:**

1. Агент вносит изменения в модуль (например, `CommonModule.УправлениеСкладом`).
2. Вызвать `check_syntax` с параметром `target`, указывающим на изменённый модуль или проект.
3. Режим по умолчанию: `edt` (через EDT validate) — наиболее быстрый и точный.
4. Если `success = false` — прочитать `errors`, исправить, повторить проверку.
5. Если есть `warnings` — оценить критичность, при необходимости исправить.

**Пример вызова:**

```
check_syntax(target: "путь/к/модулю/УправлениеСкладом/Module.bsl", mode: "edt")
```

### Сценарий 2: Проверка после рефакторинга нескольких модулей

**Шаги:**

1. Определить список затронутых модулей.
2. Вызвать `check_syntax` с `target: "all"` для проверки всей конфигурации (если доступно).
3. Либо выполнить проверку по каждому модулю последовательно.
4. Собрать все ошибки, исправить, перепроверить.

### Сценарий 3: EDT недоступен — fallback на Designer

**Шаги:**

1. Вызвать `check_syntax` с `mode: "edt"`.
2. Если capability возвращает ошибку (EDT не запущен, проект не открыт):
   - `mode: "designer_config"` — проверка конфигурации через Конфигуратор (CheckConfig);
   - `mode: "designer_modules"` — проверка модулей через Конфигуратор (CheckModules).
3. Режимы Designer требуют подключения к ИБ через Конфигуратор.

### Сценарий 4: Комбинирование с LSP-диагностикой

**Шаги:**

1. Для текущего открытого файла — `get_diagnostics` (uri: путь к файлу).
2. LSP даёт быструю обратную связь без полной проверки конфигурации.
3. Для финальной проверки — `check_syntax` (формальная проверка EDT/Designer).
4. `get_diagnostics` — частичный заменитель, если `check_syntax` недоступен.

## Интерпретация результатов

| Поле | Значение | Действие |
|------|----------|----------|
| `success` | `true` | Проверка пройдена, можно продолжать. |
| `success` | `false` | Обязательно исправить `errors` перед продолжением. |
| `errors` | непустой массив | Каждая ошибка: `file`, `line`, `message`, `severity`. Исправить по порядку. |
| `warnings` | непустой массив | Оценить: критические предупреждения исправить, остальные — по ситуации. |
| `check_time` | большое значение | При таймауте — сузить `target` (проверить отдельные модули). |

**Уровни серьёзности (severity):**

- `error` — блокирующая ошибка, код не скомпилируется.
- `warning` — предупреждение, компиляция возможна, но возможны проблемы.
- `information` / `hint` — рекомендации, не блокируют.

## Capabilities

| Capability | Назначение |
|------------|------------|
| `check_syntax` | Формальная проверка синтаксиса (EDT / Designer) |
| `get_diagnostics` | LSP-диагностика для текущего файла (быстрая обратная связь) |

---

## Типичные ошибки и обходные пути

| Ошибка | Обходной путь |
|--------|---------------|
| Пропуск проверки после правки | Правило: любое изменение BSL → немедленный вызов `check_syntax`. |
| `check_syntax` недоступен (EDT не запущен) | Использовать `get_diagnostics` как частичный заменитель; переключиться на `designer_config` или `designer_modules` при наличии Конфигуратора. |
| Таймаут при `target: "all"` | Проверять по отдельным модулям; увеличить timeout в конфигурации проекта. |
| Проект EDT не найден | Проверить путь к проекту, `sourceSet` в настройках; при необходимости использовать режимы Designer. |
| Ошибки в `errors` непонятны | Прочитать `message` и `file`/`line`; использовать `navigate_symbol` для перехода к месту ошибки; при необходимости `ask_ai_assistant` для пояснения. |
| `get_diagnostics` показывает ошибки, `check_syntax` — нет | LSP может быть строже или использовать другие правила; ориентироваться на `check_syntax` как на финальный вердикт. |
