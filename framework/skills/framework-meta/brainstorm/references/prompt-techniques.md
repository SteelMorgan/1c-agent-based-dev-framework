# Каталог промпт-приёмов для брэйнсторминга

> Справочник к навыку `brainstorm`. Здесь — техники генерации, проверки и схождения, которые работают в prompt-only режиме (без файнтюна модели). Для каждой указано: суть, когда подходит, шаблон применения, типовые ошибки.

## Карта приёмов

| Цель | Приёмы |
|------|--------|
| Расширить пространство | Морфологический анализ, аналогии, reversal, provocation, worst-idea, SCAMPER, TRIZ |
| Понять задачу глубже | 5 Whys, JTBD-переформулировка, Cynefin-классификация, Ishikawa |
| Сменить перспективу | Six Thinking Hats, persona switching, role injection, time/scale shift |
| Стресс-тест | Pre-mortem, assumption inversion, red-team, devil's advocate |
| Сузить выбор | Weighted criteria matrix, MMR/maximin, paired comparison |
| Снять mode collapse LLM | Independent generation, axis-explicit prompting, persona switching, completion-mode prefix, logit anchoring через примеры |

---

## Дивергентные приёмы (расширение пространства)

### 1. Морфологический анализ (Цвикки)

**Суть:** разложить решение на N независимых осей, для каждой — список значений. Решение = одна точка в N-мерном пространстве.

**Когда:** есть многомерное пространство решений, нужно гарантированное покрытие. Базовая техника навыка `brainstorm`.

**Шаблон промпта:**
```
Задача: <X>.
Шаг 1: предложи 3–5 осей, по которым решения этой задачи могут принципиально различаться.
Для каждой оси — название, объяснение, 2–4 значения.
Шаг 2: проверь ортогональность — обоснуй, что выбор по одной оси не предопределяет другую.
Если предопределяет — объедини оси.
```

**Типовая ошибка:** оси-оценки («хорошее vs плохое»). Это не оси, а критерии — им место в Phase 5.

---

### 2. SCAMPER

**Суть:** 7 операторов над существующим решением: **S**ubstitute, **C**ombine, **A**dapt, **M**odify, **P**ut to other use, **E**liminate, **R**everse.

**Когда:** уже есть стартовая идея/прототип/MVP, нужно расширить её вариациями. Не для задач «с чистого листа».

**Шаблон:**
```
Текущее решение: <описание>.
Применимо к каждому из 7 операторов SCAMPER предложи минимум одну
содержательную вариацию. Если оператор не применим — обоснуй почему.
```

**Типовая ошибка:** применять как чек-лист «для галочки». Если оператор не даёт интересного варианта — честно сказать «не применим», а не выдумывать слабую вариацию.

---

### 3. Аналогии из чужого домена / биомимикрия

**Суть:** «как эту задачу решают в [биологии / военной логистике / музыке / другой индустрии]».

**Когда:** мощнейший anti-mode-collapse приём. Помогает выйти из локального оптимума, особенно когда LLM зациклилась на «стандартном» решении из своей области.

**Шаблон:**
```
Задача: <X>.
Назови 5 несвязанных доменов (биология, военная логистика, классическая музыка,
средневековая торговля, спорт), в которых решают структурно похожую задачу.
Для каждого — как именно решают и какой механизм/приём можно перенести.
```

**Типовая ошибка:** брать «соседний» домен (например, для backend-задачи — frontend). Слабый эффект. Нужны действительно далёкие домены.

---

### 4. Assumption inversion / reversal

**Суть:** выписать неявные допущения задачи, инвертировать каждое, посмотреть что выживает.

**Когда:** задача сформулирована «как обычно», подозрение, что слепо приняли часть условий. Хорошо вскрывает ограничения, которые на деле необязательны.

**Шаблон:**
```
Задача: <X>.
Шаг 1: выпиши 5–7 неявных допущений в формулировке задачи (то, что мы
молча приняли как истинное).
Шаг 2: для каждого допущения — сформулируй инверсию.
Шаг 3: если инверсия истинна — какие новые решения становятся возможны?
```

**Типовая ошибка:** инвертировать только то, что инвертировать удобно. Самые ценные допущения — те, что кажутся «само собой разумеющимися».

---

### 5. First-principles decomposition

**Суть:** содрать задачу до аксиом домена (физика, экономика, базовые свойства пользователя), собрать решение заново.

**Когда:** когда стандартные решения раздражают своей похожестью; когда хочется не «как у других»; когда подозрение на legacy-thinking. Антипод аналогий.

**Шаблон:**
```
Задача: <X>.
Шаг 1: какие фундаментальные ограничения этой задачи (физические, информационные,
экономические, человеческие)? Не «как принято решать», а что объективно нельзя обойти.
Шаг 2: исходя только из этих ограничений, какое минимальное решение возможно?
Шаг 3: какие «стандартные» элементы решения на самом деле не следуют из ограничений
и являются конвенциональным наследием?
```

**Типовая ошибка:** называть «принципами» то, что на деле является конвенцией («у нас всегда был REST API»). Тест: если это можно изменить решением одного человека — это не принцип.

---

### 6. Provocation / PO (de Bono)

**Суть:** намеренно абсурдное утверждение как seed («что если у нас нет базы данных», «что если ответ должен прийти за 0 мс», «что если каждый запрос обрабатывают вручную»).

**Когда:** дёшево пробивает локальный минимум. Хорошо когда генерация скатывается в очевидные варианты.

**Шаблон:**
```
Задача: <X>.
Допустим, абсурдное условие: <провокация>.
Не отбрасывай его сразу. Опиши, как бы выглядело решение в этих условиях.
Какие из элементов такого решения можно перенести в реалистичный сценарий?
```

**Типовая ошибка:** недостаточно абсурдная провокация («что если бюджет на 20% меньше» — это не провокация, это вариация). Нужно нарушение базового допущения.

---

### 7. Worst possible idea

**Суть:** генерим заведомо плохие идеи, инвертируем.

**Когда:** снимает страх «выдать глупость», расширяет границы. Особенно полезно в начале сессии, когда модель «осторожничает».

**Шаблон:**
```
Задача: <X>.
Назови 5 максимально плохих решений этой задачи. Чем хуже — тем лучше.
Для каждого — что именно делает его плохим.
Затем: для 2–3 самых плохих — какая инверсия плохих свойств даёт интересное решение?
```

**Типовая ошибка:** генерить «слабые» идеи вместо «плохих». Слабые скучны, плохие — забавны и продуктивны.

---

### 8. TRIZ (упрощённо: противоречия)

**Суть:** сформулировать конфликт параметров («хотим X, но это ломает Y»), искать решения через разрешение противоречия.

**Когда:** инженерные задачи с явным trade-off. «Хотим скорость, но нужна надёжность», «хотим гибкость, но нужна простота».

**Шаблон:**
```
Задача: <X>.
Шаг 1: сформулируй центральное противоречие в формате «хотим увеличить A,
но это ухудшает B».
Шаг 2: предложи решения через типовые приёмы:
  - разделение в пространстве (A и B в разных частях системы)
  - разделение во времени (A в одну фазу, B в другую)
  - разделение по условию (A для одного класса случаев, B для другого)
  - переход на другой уровень (A на уровне системы, B на уровне подсистемы)
  - инверсия (сделать B полезным свойством)
```

**Типовая ошибка:** сразу искать «компромисс». TRIZ говорит — настоящее решение **разрешает** противоречие, а не балансирует его.

## Приёмы фрейминга (Phase 0)

### 9. 5 Whys

**Суть:** пять раз спросить «почему», чтобы дойти до корневой задачи.

**Когда:** запрос звучит как решение, а не как задача («сделайте кнопку X»). Опасно для action-bias.

**Шаблон:**
```
Запрос пользователя: <X>.
Задай 5 уровней вопроса «почему» (или «зачем»), уходя от сформулированного
решения к корневой потребности. После 5-го уровня — переформулируй задачу
как корневую потребность, а не как способ её решения.
```

---

### 10. Jobs-to-be-Done

**Суть:** «какую работу пользователь нанимает решение делать?». Сместить с «что построить» на «что нужно достичь».

**Когда:** продуктовые задачи, UX-решения, пограничные случаи интеграций. Помогает понять, что разные технические решения могут одинаково хорошо «делать работу».

**Шаблон:**
```
Когда <ситуация>, я хочу <мотивация>, чтобы <ожидаемый результат>.
Сформулируй 2–3 версии этой формулы для запроса <X>. Выбери ту, которая
лучше отражает реальную потребность.
```

---

### 11. Cynefin-классификация

**Суть:** классифицировать задачу: clear / complicated / complicated / chaotic. От класса зависит подход.

**Когда:** перед началом работы — чтобы понять, нужен ли вообще брэйнсторм.

| Класс | Признак | Подход |
|-------|---------|--------|
| Clear | Один правильный ответ есть и известен | Применить best-practice, брэйнсторм не нужен |
| Complicated | Решение есть, но требует анализа экспертом | Брэйнсторм короткий, упор на анализ |
| Complex | Решение проявляется только в экспериментах | Брэйнсторм полный, упор на дивергентность и гипотезы |
| Chaotic | Сначала надо стабилизировать | Не до брэйнсторма, нужно действовать и смотреть |

## Приёмы смены перспективы

### 12. Six Thinking Hats (de Bono)

**Суть:** принудительная ротация шести перспектив:
- **Белая:** факты, данные, что мы знаем
- **Красная:** эмоции, интуиция, без обоснований
- **Чёрная:** риски, что может пойти не так
- **Жёлтая:** выгоды, оптимистичный сценарий
- **Зелёная:** креатив, новые идеи
- **Синяя:** процесс, метаразмышление

**Когда:** обсуждение, в котором есть тенденция «все за» или «все против»; групповая динамика; для LLM — снятие «голоса ассистента» через явные роли.

**Шаблон:**
```
Задача: <X>.
Пройдись последовательно в 6 ролях. Для каждой — отдельный абзац.
Не смешивай роли в одном абзаце.
[список ролей с описаниями]
```

---

### 13. Persona switching / role injection

**Суть:** явно задать LLM роль с противоположной от дефолтной точкой зрения.

**Когда:** дефолтный «голос ассистента» — главный источник mode collapse в открытых задачах. Persona-промпт меняет распределение.

**Шаблон:**
```
Ты — <роль с конкретными чертами: суровый CTO с 20 годами в финтехе /
скептичный investor / параноик-безопасник / pragmatic product manager
с дедлайном через неделю>. С этой позиции — <вопрос>.
```

**Типовая ошибка:** размытая персона («креативный человек»). Нужны конкретные черты, формирующие точку зрения.

---

### 14. Time / scale shift

**Суть:** «как бы эта задача выглядела через 10 лет / при 1000-кратном масштабе / для одного пользователя вместо миллиона».

**Когда:** когда решение сильно зависит от текущего масштаба и есть подозрение, что мы оптимизируем под локальную точку.

**Шаблон:**
```
Решение: <X>.
Опиши, как оно будет работать (или ломаться) при:
- 10x росте нагрузки
- 100x росте нагрузки
- сжатии в 10 раз (нишевый сервис вместо массового)
- через 5 лет, если домен останется тем же
- через 5 лет, если рядом появится новая технология <Y>
```

## Стресс-тест (Phase 4)

### 15. Pre-mortem (Klein)

**Суть:** «представь, что мы это сделали и через год оно провалилось — почему?». Сильнее обычного risk-list, потому что меняет фрейм с «что может пойти не так» на «что уже пошло не так».

**Когда:** перед фиксацией решения. Лучше всего работает на shortlist (Phase 5), но можно и на каждой гипотезе после Phase 3.

**Шаблон:**
```
Допустим, мы выбрали решение <X> и реализовали его. Прошёл год.
Решение признано провалом. Опиши 5 наиболее вероятных причин провала
в порядке убывания вероятности.
Для каждой — какой ранний сигнал мы могли бы заметить до полного провала.
```

---

### 16. Assumption inversion (как стресс-тест)

То же, что приём №4, но применённый к **выбранному** решению, а не к задаче. «На каком допущении это решение держится? Что если оно неверно?».

---

### 17. Red team / devil's advocate

**Суть:** отдельный вызов с задачей «разнеси решение в пух и прах».

**Когда:** для финалистов перед окончательным выбором. Особенно ценно как **отдельный вызов** (без контекста генерации) — иначе тот же агент защищает то, что только что предложил.

**Шаблон:**
```
Решение: <X> (без контекста, как оно появилось).
Ты — red team. Твоя единственная задача — найти причины не делать это.
Не балансируй с плюсами. Назови 7 серьёзных проблем, отсортируй
по убыванию серьёзности.
```

---

## Конвергенция (Phase 5)

### 18. Weighted criteria matrix

**Суть:** критерии × веса × оценки = взвешенная сумма.

**Когда:** когда финалисты сопоставимы и нужен явный выбор. Скучно, но снимает «выбор по первому впечатлению».

**Критично:** веса фиксируются **до** оценки, иначе подгонка под фаворита.

**Шаблон:**
```
Шаг 1: предложи 5–7 критериев оценки решений для задачи <X>.
Шаг 2: назначь вес каждому (сумма = 100%).
Шаг 3: ПОДТВЕРДИ веса с пользователем — НЕ переходи к оценке без подтверждения.
Шаг 4: оцени каждое решение по каждому критерию (1–5).
Шаг 5: взвешенная сумма + ранжирование.
```

---

### 19. MMR / maximin отбор (anti-collapse конвергенция)

**Суть:** выбирать не топ-3 по сумме, а **3 максимально различных хороших** (порог качества + максимизация различия).

**Когда:** всегда, если финал — больше одного варианта. Иначе финалисты сходятся в одну точку пространства осей.

**Шаблон:**
```
Из shortlist выбери 3 решения по правилу:
- каждое имеет суммарную оценку ≥ <порог>
- из всех таких троек выбери ту, в которой решения максимально удалены
  друг от друга по осям из Phase 1
Покажи координаты выбранных в осях, чтобы было видно различие.
```

---

### 20. Paired comparison (для маленьких списков)

**Суть:** все пары попарно сравнить, кто кого побеждает. Финал — победитель турнира.

**Когда:** 4–6 финалистов, критерии сложно формализовать, но легко сравнить две конкретные опции.

**Шаблон:**
```
Финалистов <N>. Образуй все <N×(N-1)/2> пар.
Для каждой пары: какой вариант лучше и почему (1 предложение).
Подсчитай победы. Выведи таблицу.
```

## Анти-mode-collapse приёмы (специфика LLM)

### 21. Independent generation (изоляция контекста)

**Проблема:** генерация N идей в одном ответе анкорит на первой. К пятой идее модель уже еле находит вариации.

**Решение:** на каждую идею — отдельный вызов / отдельная инструкция «забудь предыдущие идеи». Если технически невозможно — явная инструкция:

```
Сейчас сгенерируй ОДНУ гипотезу для координаты <ось1=X, ось2=Y>.
Не сравнивай с предыдущими. Не пытайся быть «другой».
Просто следуй координатам.
```

---

### 22. Axis-explicit prompting

**Проблема:** «дай 5 разнообразных вариантов» даёт лексически разные, но семантически близкие идеи.

**Решение:** каждая генерация явно привязана к координатам из морфологического анализа. Это превращает «разнообразие» из субъективной просьбы в объективное условие.

---

### 23. Completion-mode / prefix injection

**Проблема:** RLHF-обученные модели имеют узкий «дефолтный голос ассистента», который сужает пространство.

**Решение:** дать сильный стилевой префикс или начало ответа, отличное от дефолтного. Работает как для tone, так и для содержания.

```
Начни ответ с фразы: «На самом деле, наиболее интересный угол здесь — это <...>».
Не используй формулировки «есть несколько подходов» / «давайте рассмотрим».
```

---

### 24. Logit anchoring через примеры (few-shot)

**Проблема:** модель не понимает, какого уровня дивергентности от неё ждут.

**Решение:** показать 1–2 примера сильно различных гипотез, чтобы задать «масштаб различия».

```
Пример того, насколько различными должны быть гипотезы:
- Гипотеза A: <радикально один подход>
- Гипотеза B: <радикально другой подход>
Теперь сгенерируй гипотезы того же масштаба различия для задачи <X>.
```

---

### 25. Verbalized distribution (как в обсуждаемой статье)

**Суть:** «дай N вариантов с оценками их вероятности/уместности».

**Когда:** хочется не только идей, но и понимания, насколько модель в них уверена. С калибровкой плохо, но как **отностельный сигнал** для отсева — полезно.

**Шаблон:**
```
Сгенерируй 7 гипотез решения <X>.
Для каждой укажи:
- вероятность, что она применима в стандартных условиях (0–1)
- условие, при котором она становится наиболее уместной
Не используй температуру оценки выше 0.9 и ниже 0.05 — это сигнал
о неоткалиброванности.
```

**Важно:** не верить абсолютным значениям вероятностей, использовать только относительный порядок.

## Что НЕ работает (антипаттерны)

| Приём | Почему не работает |
|-------|--------------------|
| «Дай 10 идей» без структуры | Идеи 4–10 — слабые вариации первой |
| «Будь креативным» | Размытая инструкция, не меняет распределение |
| «Думай нестандартно» | То же самое, риторика без механизма |
| Само-оценка той же моделью без смены роли | «Внутренний критик» ленив, защищает свои идеи |
| Брэйнсторм без явных критериев успеха | Нечего оценивать на конвергенции |
| Полный грид при 4+ осях с 3+ значениями | Взрыв комбинаций, теряется фокус |
| Конвергенция «по сумме баллов» без diversity-правила | 3 финалиста — варианты одного |

## Шпаргалка: какой приём для какой ситуации

| Ситуация | Стартовый приём |
|----------|-----------------|
| Запрос мутный, не ясно что хотят | 5 Whys / JTBD |
| Задача звучит «стандартно», нужен свежий угол | First-principles или аналогии |
| Уже есть решение, нужны вариации | SCAMPER |
| Конфликт параметров в задаче | TRIZ |
| Подозрение, что приняли лишние ограничения | Assumption inversion |
| Идеи получаются «правильными и скучными» | Provocation или worst-idea |
| Слишком много альтернатив, надо выбрать | Weighted criteria + MMR |
| Финалист выбран, нужна страховка от провала | Pre-mortem + red team |
| Группа склоняется к одному решению | Six Hats или devil's advocate |
| Решение оптимизировано под текущий момент | Time/scale shift |
