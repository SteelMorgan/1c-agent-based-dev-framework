# Как выяснить контекст окружения 1C-проекта

Агент не должен «додумывать» окружение — его нужно выяснить из проекта и
машины. Ниже — практические рецепты для каждого элемента «контекста
окружения» (см. SKILL.md, раздел про эскалацию).

Правило: сначала — из файлов проекта/репозитория, затем — из системы,
и только если нигде не нашлось — спросить пользователя.

## 1. Операционная система

Где искать (по приоритету):

1. **Переменные окружения / sysfs (Linux)** —
   `cat /etc/os-release` (поля `ID`, `VERSION_ID`, `PRETTY_NAME`).
2. **Ядро и архитектура** — `uname -a`. Строка содержит `Linux`,
   `microsoft-standard-WSL2` (значит Windows host + WSL2), `Darwin` (macOS).
3. **Windows (из bash)** — `systeminfo | grep -i "OS Name"` или
   `cmd.exe /c ver`. Через PowerShell: `[System.Environment]::OSVersion`.
4. **Docker-контейнер** — проверь, нет ли `/.dockerenv`; если есть —
   ОС внутри контейнера может отличаться от ОС хоста, это важно для 1С
   (сервер/клиент/агент могут работать в разных контейнерах).

Разделять: ОС, где **работает сервер 1С**, и ОС, где **работает клиент**
(толстый/тонкий/web). Вопросы про COM/WSH/пути чаще всего относятся к клиенту.

## 2. Версия платформы 1С

Где искать (по приоритету):

1. **CLAUDE.md / AGENTS.md проекта** — в секции «Окружение» обычно
   зафиксирована рабочая версия (например, `8.3.27.2074`).
2. **Установленные дистрибутивы на машине:**
   - Linux: `ls /opt/1cv8/x86_64/` или `ls /opt/1cv8/` — подкаталоги
     именуются по версии (`8.3.27.2074/`).
   - Windows: `dir "C:\Program Files\1cv8"` либо
     `reg query "HKLM\SOFTWARE\1C\1cv8\InstalledLocation"`.
3. **Запущенный сервер/кластер** — версия кластера через консоль
     администрирования или утилиту `rac` (`rac cluster list` → `version`).
     *Оговорка:* `rac` требует локально доступного агента кластера; внутри
     dev-контейнера без проброса портов обычно выдаёт `Connection refused` —
     в этом случае опирайся на CLAUDE.md/AGENTS.md и строку подключения ИБ.
4. **Информационная база** — при открытии база сама требует совместимую
   платформу; минимально допустимая версия — свойство конфигурации
   (`Configuration.xml`, элемент `<Version>` / `<ConfigurationExtensionCompatibilityMode>`).
5. **Режим совместимости конфигурации** — НЕ равен версии платформы, но
   ограничивает API; смотри в свойствах корневого узла конфигурации.

Если сервер и клиент разных версий — укажи **обе** и пометь это как риск:
часть багов и решений завязана именно на расхождение.

## 3. Текущая конфигурация и её версия

Где искать (по приоритету):

1. **`Configuration.xml`** (формат выгрузки Конфигуратора) — путь зависит
   от раскладки репозитория: типично `src/Configuration/Configuration.xml`,
   но встречаются `src/xml/Configuration.xml`, `cf/Configuration.xml` и др.
   Надёжно искать через `find <project> -maxdepth 5 -name Configuration.xml`
   и брать корневой (не из `Extensions/`). В нём ищи элементы `<Name>`,
   `<Synonym>`, `<Version>`, `<Vendor>`. Это даёт **имя** конфигурации
   (кириллицей у русскоязычных типовых — `ERPУправлениеПредприятием`,
   `БухгалтерияПредприятия`, `УправлениеТорговлей`; латиницей у
   англоязычных и форков — `DriveTrSalesAndServices`, `SmallBusiness`
   и т.п.), **версию релиза** (например, `2.5.17.123` или `1.6.1.4`)
   и поставщика.
2. **EDT-проект** — `src/Configuration/Configuration.mdo` (XML), те же поля.
3. **`docs/`, `README`, `AGENTS.md`** проекта — часто зафиксированы
   «название + версия + что это за типовая» (например, «DSSL Drive — форк
   УНФ, переведён на английский»).
4. **MCP-инструменты:** `mcp__1c-mcp__get_metadata_structure` /
   `list_metadata_objects` — видно корневое имя и состав.
5. **Из запущенной базы** — в Конфигураторе: Свойства корня конфигурации,
   поля «Имя», «Версия», «Поставщик».

Типовая vs доработанная — смотри наличие расширений (`exts/`, каталог
`Extensions/`) и наличие префиксов в метаданных (например, `DSSL_*`, `ep_*`).
Это важно: решение для «ванильной» УТ 11 может не работать в сильно
доработанной конфигурации.

**Версия БСП** (если проект использует БСП) — в типовых конфигурациях
обычно зашита в общем модуле `СтандартныеПодсистемыСервер` /
`StandardSubsystemsServer`, функция вида `ВерсияБиблиотеки()` /
`LibraryVersion()`. Альтернативно — `src/CommonModules/StandardSubsystemsServer/Ext/Module.bsl`
(grep по `"Версия"` / `Version`).

## 4. Вариант СУБД

Где искать (по приоритету):

1. **Строка подключения ИБ** — в проекте часто указана в `AGENTS.md` /
   `CLAUDE.md` (тип: файловая, клиент-серверная, DBMS-тип). Примеры:
   - `/F"..."` → файловая база;
   - `/S"server\base"` → клиент-серверная (СУБД уточняется отдельно);
   - `Srvr=...;Ref=...;DBMS=MSSQLServer|PostgreSQL|IBMDB2|OracleDatabase` —
     явно в строке подключения из `ibases.v8i` / `1CEStart.cfg`.
2. **Реестр баз кластера** — `rac infobase list --cluster=<id>` → поле
   `dbms` (`MSSQLServer`, `PostgreSQL`, `IBMDB2`, `OracleDatabase`).
3. **Запущенные процессы СУБД на сервере** (как косвенный сигнал):
   - Linux: `ps -ef | grep -Ei 'postgres|mssql|sqlservr'`;
   - Windows: `sc query | findstr /I "SQL Postgre"`;
   - Docker: `docker ps` — имена образов (`postgres:15`, `mcr.microsoft.com/mssql/server`).

   *Оговорка:* этот способ работает только если СУБД и агент/сессия на
   одной машине. В dev-контейнере, когда СУБД живёт на отдельном хосте
   (например, `onec-infra`), процессов видно не будет — опирайся на
   строку подключения ИБ из CLAUDE.md/AGENTS.md (п. 1).
4. **Файловая база** — если ИБ файловая (только `1CD`-файл), DBMS-вопросы
   неприменимы; это само по себе ответ: «файловый вариант».

Для вопросов производительности / блокировок / планов запросов — укажи
**и тип СУБД, и её мажорную версию** (например, PostgreSQL 15 vs 13
ведут себя заметно по-разному).

## 5. Режим работы и совместимости

- **Клиент-серверная vs файловая** — см. выше (строка подключения).
- **Режим совместимости** — свойство конфигурации
  (`Configuration.xml`, `<CompatibilityMode>`), определяет, какие платформенные
  новшества доступны.
- **Режим управляемого приложения / обычные формы** — корень конфигурации,
  свойства `ModalityUseMode`, `SynchronousPlatformExtensionAndAddInCallUseMode`,
  `InterfaceCompatibilityMode`.

## 6. Библиотеки проекта

Где искать:

1. **Проектная документация** — `docs/project-libraries.md` (если есть),
   `README`, `AGENTS.md` / `CLAUDE.md` часто явно перечисляют библиотеки
   (канонические названия: БСП, ДФИ, Коннектор_HTTP и т.п.).
   Файл `docs/project-libraries.md` не гарантирован — это конвенция, а не
   стандарт; если его нет, переходи к п. 2.
2. **Общие модули** — каталог `src/CommonModules/`:
   - БСП: наличие модулей `СтандартныеПодсистемы*` / `StandardSubsystems*`,
     `Common`, `Users`, `SafeModeManager`;
   - ДФИ: модули с префиксом/упоминанием `ДФИ` / `DFI`;
   - Коннектор_HTTP: модули/обработки с `Коннектор` / `Connector` и HTTP-функциями.
3. **Подсистемы** — `src/Subsystems/` или корневой узел «Подсистемы» в
   конфигурации; имена подсистем часто совпадают с именами библиотек.
4. **Расширения** — `exts/` может содержать вкладываемые библиотеки
   отдельными расширениями.

Для ответа сообщества важно не только «есть ли библиотека», но и её
**версия** (особенно для БСП) — правила поиска версии см. выше.

## 7. Что делать, если найти не удалось

Если после всех проверок какого-то элемента окружения нет — **не угадывай**.
Либо пометь в финальном ответе как «неизвестно» (и это валидный повод
снизить уверенность), либо, если без этого элемента выбор между
кандидатами TOP-N невозможен, задай пользователю точечный вопрос по
формату эскалации: «Для выбора между вариантами A и B мне нужна ОС
сервера (Windows/Linux) и вариант СУБД (MS SQL / PostgreSQL) — подскажи,
пожалуйста».

Плохо: спрашивать «какое у тебя окружение?» без конкретики.
Хорошо: спрашивать именно тот параметр, от которого зависит выбор ответа.
