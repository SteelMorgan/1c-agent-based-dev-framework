# Создание навыков для фреймворка 1С BSL

Мета-навык: учит агента создавать новые навыки (skills) для фреймворка агентной разработки 1С. Объединяет стандарт Anthropic Agent Skills и внутренний формат фреймворка.

---

## Два формата навыков

Фреймворк использует два формата — один для ядра, другой для IDE:

| Формат | Где | Frontmatter | Назначение |
|--------|-----|-------------|-----------|
| **Framework skill** | `framework/skills/` | `id`, `type`, `depends_on` | Ядро фреймворка. IDE-agnostic markdown. Описывает КОГДА/КАК/ПОЧЕМУ. |
| **IDE skill (SKILL.md)** | `.cursor/skills/`, `.claude/skills/` | `name`, `description` | Anthropic Agent Skills standard. Автообнаружение IDE. Progressive disclosure. |

**install.py** превращает framework-skills в IDE-skills (симлинки/копии). Поэтому каждый framework-skill — это одновременно и IDE-skill после установки.

---

## Когда создавать новый навык

| Триггер | Действие |
|---------|----------|
| Появился новый MCP tool, и агент не знает КОГДА его использовать | Создать `tool-usage/` skill |
| Обнаружен повторяющийся антипаттерн в BSL-коде проекта | Создать `bsl-practices/` skill |
| Нужно обучить агента специфике конкретной конфигурации | Создать **проектный** skill (в каталоге IDE проекта) |
| Нужна стандартная методология (SDD, TDD, ревью) | Создать `spec-writing/` или новый подкаталог |
| Агент повторяет одни и те же ошибки | Описать ошибку + правильный подход в skill |

**НЕ создавать** новый навык если:
- Информация уже есть в существующем навыке — дополнить его
- Это одноразовая инструкция — сделать prompt, не skill
- Это правило/политика (MUST/SHOULD) — создать rule, не skill

## Процесс создания (4 фазы)

### Phase 1: Анализ

1. **Определить тип навыка:**

| Тип | Каталог | depends_on | Для чего |
|-----|---------|-----------|----------|
| BSL-практика | `skills/bsl-practices/` | `[]` | Стандарты кодирования, паттерны, антипаттерны |
| Tool-usage | `skills/tool-usage/` | `[registry/tool-registry]` | Как и когда использовать capability |
| Методология | `skills/spec-writing/` | `[]` | SDD, TDD, стандарты документации |
| Мета-навык | `skills/creating-skills/` | `[]` | Навыки про навыки |
| Проектный | `.cursor/skills/` в проекте | — | Специфика конкретного проекта |

2. **Проверить: не дублирует ли существующий навык?** Прочитать навыки в целевом подкаталоге.

3. **Определить зависимости:** Ссылается ли навык на capability из tool-registry? На другие навыки?

### Phase 2: Проектирование

1. **Имя файла** — `kebab-case.md` (латиница, дефисы). Примеры: `query-patterns.md`, `syntax-checking.md`
2. **id** — `skill/<имя-файла-без-расширения>`: `skill/query-patterns`
3. **Структура содержимого** — определить секции (см. ниже)
4. **Объём** — целевой лимит **300 строк** для framework-skill (500 — абсолютный максимум по стандарту Anthropic)

### Phase 3: Написание

Использовать шаблон: [`_template-skill.md`](../_template-skill.md)

**Обязательные секции:**
- YAML frontmatter (`id`, `type`, `depends_on`)
- Заголовок + 1-3 предложения назначения
- **Когда применять** — таблица триггер → действие
- **Сценарии использования** — конкретные примеры с контекстом
- **Примеры кода** — правильно + неправильно с объяснением ПОЧЕМУ

**Опциональные секции:**
- Типичные ошибки (таблица)
- Связанные ресурсы (ссылки)
- Дополнительные файлы (progressive disclosure)

### Phase 4: Интеграция

1. Добавить файл в нужный подкаталог `framework/skills/`
2. Обновить `depends_on` в агентах, которые должны использовать навык
3. Запустить `python install.py --list` — убедиться что навык появился
4. Проверить зависимости: `python install.py --ide cursor --include skill/<id> --dry-run`

## Принципы написания (из стандарта Anthropic)

### 1. Краткость — главный принцип

Контекстное окно — общий ресурс. Каждый токен конкурирует с историей диалога, другими навыками и задачей.

**Базовое допущение:** Агент уже умный. Добавляй только то, чего он НЕ знает.

Проверяй каждый абзац:
- "Агенту реально нужно это объяснение?"
- "Можно предположить, что агент это знает?"
- "Абзац оправдывает стоимость токенов?"

**Правильно** (~50 токенов):
```bsl
// Проверка синтаксиса перед сохранением:
// 1. Вызвать check_syntax
// 2. Если ошибки — показать пользователю
// 3. Не сохранять при критических ошибках
```

**Неправильно** (~150 токенов):
```
Синтаксис BSL — это набор правил, определяющих структуру кода на языке
1С:Предприятие. Проверка синтаксиса важна, потому что ошибки в синтаксисе
могут привести к проблемам при компиляции и выполнении. Существует несколько
способов проверки синтаксиса: через EDT, через Конфигуратор или через LSP...
```

### 2. Степени свободы

Точность инструкций зависит от хрупкости операции:

| Уровень | Когда | Пример |
|---------|-------|--------|
| **Высокая свобода** | Несколько подходов валидны | Ревью кода: "Проверь обработку ошибок, именование, тестируемость" |
| **Средняя** | Есть предпочтительный паттерн | Формат запроса: "Используй шаблон, адаптируй под задачу" |
| **Низкая свобода** | Операция хрупкая | Миграция базы: "Выполни строго эту команду, без модификаций" |

Для BSL-навыков: стандарты кодирования — **низкая свобода** (конкретные правила ИТС). Архитектурные решения — **высокая**.

### 3. Progressive disclosure

Детальная информация — в отдельных файлах, не в основном файле навыка.

```markdown
# Паттерны запросов 1С

## Основные правила
[Компактные инструкции — 50-100 строк]

## Детальные примеры
Подробные примеры с разбором — см. [EXAMPLES.md](EXAMPLES.md)
```

**Правило:** Ссылки из основного файла — только на один уровень глубины. Не A → B → C, а A → B и A → C.

### 4. Объясняй ПОЧЕМУ, не только ЧТО

Специфика BSL-навыков: программист 1С должен понимать причину правила, иначе будет его обходить.

**Плохо:**
```markdown
Не используйте запросы в циклах.
```

**Хорошо:**
```markdown
Не используйте запросы в циклах.
**Почему:** Каждый вызов `Запрос.Выполнить()` — это обращение к СУБД через сеть.
В цикле из 1000 итераций = 1000 обращений к базе. Один запрос с условием `В (&Массив)` 
выполнит ту же работу за 1 обращение.
```

## Паттерны содержимого

### Паттерн "Триггер → Действие" (для tool-usage навыков)

```markdown
## Когда применять

| Триггер | Действие |
|---------|----------|
| Пользователь просит проверить запрос | `validate_query` → если ОК → `execute_query` |
| Пользователь прислал навигационную ссылку | `parse_nav_link` → `execute_query` по объекту |
| Нужно исследовать структуру объекта | `list_metadata_objects` → `get_metadata_structure` |
```

### Паттерн "Правильно / Неправильно" (для BSL-практик)

```markdown
### Правильно

```bsl
// Один запрос с условием ВСЕ записи
Запрос.УстановитьПараметр("МассивСсылок", МассивСсылок);
РезультатЗапроса = Запрос.Выполнить();
```

### Неправильно

```bsl
// ❌ Запрос в цикле: N обращений к СУБД вместо одного
Для Каждого Ссылка Из МассивСсылок Цикл
    Запрос.УстановитьПараметр("Ссылка", Ссылка);
    РезультатЗапроса = Запрос.Выполнить(); // Каждая итерация = поход в базу
КонецЦикла;
```
```

### Паттерн "Воркфлоу с чек-листом" (для методологий)

```markdown
## Процесс ревью спецификации

Копируй чек-лист и отмечай пункты:

```
Прогресс:
- [ ] Шаг 1: Прочитать контекст и цели
- [ ] Шаг 2: Проверить Requirements (RFC 2119)
- [ ] Шаг 3: Проверить Scope (in/out)
- [ ] Шаг 4: Проверить Test Plan
- [ ] Шаг 5: Сформировать вердикт (BLOCK/WARN/INFO)
```
```

### Паттерн "Условный воркфлоу" (для ветвлений)

```markdown
## Обработка ошибки теста

1. Определи тип ошибки:

   **Тест написан неправильно?** → Исправь тест
   **Ошибка в реализации?** → Верни Developer с описанием

2. Если тест неправильный:
   - Исправь ожидание или тестовые данные
   - Перезапусти: `run_tests`
   ...
```

## Проектные навыки (project-specific skills)

Навыки, актуальные только для конкретного проекта, размещаются **в каталоге проекта**, не во фреймворке.

### Где размещать

| IDE | Каталог |
|-----|---------|
| Cursor | `.cursor/skills/` в корне проекта |
| Claude Code | `.claude/skills/` в корне проекта |

### Формат проектного навыка

Проектные навыки используют **Anthropic SKILL.md формат** (не framework-формат):

```markdown
---
name: my-project-specifics
description: Специфика конфигурации ERP 2.5: ключевые подсистемы, регистры, 
  ограничения. Использовать при работе с модулями этого проекта.
---

# Специфика проекта

## Ключевые подсистемы
- УправлениеЗаказами — основной бизнес-процесс
- ИнтеграцияСCRM — REST API, интеграция с Битрикс24
...
```

### Что включать в проектные навыки

- Архитектура конфигурации (какие подсистемы, как связаны)
- Локальные coding conventions (если отличаются от стандарта)
- Бизнес-правила домена
- Список критичных модулей ("не трогать без ревью")
- Интеграции и внешние системы

### Чего НЕ включать

- Общие стандарты BSL (они во framework-навыках)
- Секреты, пароли, connection strings
- Информацию, которая быстро устаревает (даты релизов, текущие задачи)

## Чек-лист нового навыка

### Содержание
- [ ] Объясняет ПОЧЕМУ, не только ЧТО
- [ ] Примеры кода: правильно + неправильно
- [ ] Таблица "Когда применять" (триггер → действие)
- [ ] Нет дублирования с существующими навыками
- [ ] Объём ≤ 300 строк (целевой), ≤ 500 (максимум)

### Формат
- [ ] YAML frontmatter: `id`, `type`, `depends_on`
- [ ] id = `skill/<имя-файла-без-расширения>`
- [ ] type = `skill`
- [ ] depends_on корректен (tool-usage → `[registry/tool-registry]`, standalone → `[]`)
- [ ] Имя файла: kebab-case, латиница

### Интеграция
- [ ] Файл в правильном подкаталоге `framework/skills/`
- [ ] Агенты, использующие навык, обновлены (depends_on + "Используемые навыки")
- [ ] `python install.py --list` показывает навык
- [ ] Ссылки на файлы — один уровень глубины
