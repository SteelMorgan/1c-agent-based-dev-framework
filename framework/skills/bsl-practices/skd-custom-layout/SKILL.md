# СКД на своем макете

## Назначение

Используй этот навык, когда отчет формируется через СКД, но внешний вид результата задается собственными областями вкладки `Макеты`.

Этот навык описывает СКД-связку:

```text
наборы данных и поля
  -> настройки и структура варианта
  -> groupTemplate
  -> template
  -> параметр ячейки
  -> expression параметра
  -> ТабличныйДокумент
```

Оформление самих областей, сетку, границы, заливки, шрифты и визуальную сверку проектируй через `mxl-layout-patterns`.

Базовые возможности СКД проверяй через `skd-report-patterns`.

## Не путать с печатной формой

Печатная форма заполняет область BSL-кодом:

```bsl
Область = Макет.ПолучитьОбласть("Строка");
Область.Параметры.Поле = Значение;
ТабличныйДокумент.Вывести(Область);
```

СКД на своем макете использует похожую визуальную модель области, но значения вычисляет и выводит СКД:

- ячейка ссылается на параметр области;
- параметр имеет выражение СКД;
- `groupTemplate` решает, когда выводится область;
- настройки варианта решают структуру данных.

## Основные сущности

- `template.name` — техническое имя области.
- `groupTemplate.groupName` — имя элемента структуры настроек.
- `groupTemplate.templateType` — место вывода области: `Header`, `GroupHeader`, `OverallHeader` и т.д.
- `groupTemplate.template` — ссылка на `template.name`.
- `ExpressionAreaTemplateParameter.name` — имя параметра области.
- `ExpressionAreaTemplateParameter.expression` — выражение, которым СКД заполнит параметр.

Не выводи значение из имени параметра. Источник истины — `expression`.

## Workflow

1. Спроектируй данные и структуру отчета через `skd-report-patterns`.
2. Спроектируй области и визуальную модель через `mxl-layout-patterns`.
3. Для каждой области определи:
   - когда она выводится;
   - к какому элементу структуры привязана;
   - какие параметры содержит;
   - какие выражения заполняют параметры.
4. Сгенерируй/измени СКД поддержанным инструментом.
5. Проверь XML-структуру через `xml-gen skd info`.
6. Выполни runtime-проверку на платформе.

## Слои

Разделяй четыре слоя.

Функциональный слой описывает, какой отчет нужен пользователю:

- какие данные должны быть получены запросом;
- какие данные нужно сформировать кодом или внешними object-наборами;
- какие разделы, группы, строки и итоги должны быть видны;
- какие отборы и сортировки доступны пользователю;
- где стандартного вывода СКД недостаточно и нужен свой макет.

Технический слой СКД описывает, как это хранится и исполняется:

- `dataSets` — query/object/union наборы;
- `fields` — поля наборов;
- `totalFields` — ресурсы;
- `parameters` — параметры данных;
- `settingsVariants.settings.structure` — порядок вывода, группировки, отборы, сортировки, выбранные поля;
- `templates` — области макета результата;
- `groupTemplates` — связь структуры варианта с областями макета.

Технический слой MXL описывает визуальную форму областей:

- сетку колонок;
- ширины и высоты;
- объединения;
- стили;
- текстовые ячейки;
- ячейки-параметры;
- форматы чисел и дат.

Для этого слоя используй `mxl-layout-patterns`; для генерации обычных MXL — `mxl-dsl`; для СКД-областей — возможности `skd-dsl.templates`.

Runtime-слой описывает, что происходит при выполнении отчета:

- получение выполняемых настроек;
- построение макета компоновки;
- подготовка внешних object-наборов;
- инициализация процессора компоновки;
- вывод результата в `ТабличныйДокумент`;
- допустимая постобработка результата.

Внешний imported MXL/Excel-каркас сам по себе не становится СКД-макетом. Чтобы Excel или обычный
MXL стал источником для этого навыка, нужно явно восстановить СКД-структуру:

- `template`;
- `groupTemplate`;
- параметры областей;
- `expression` для параметров;
- связь с элементами структуры варианта.

## Что проверять

- Все параметры ячеек имеют `ExpressionAreaTemplateParameter`.
- Все expression ссылаются на доступные поля/ресурсы/выражения.
- Поля, используемые областью строки, доступны в контексте группы, которая выводит эту область.
- `groupTemplate.groupName` совпадает с именем элемента структуры настроек, а не с названием поля группировки.
- `templateType` соответствует ожидаемому месту вывода.
- Для DSL-семантики `GroupHeader` канонический Designer XML содержит отдельный
  `<groupHeaderTemplate>` с вложенным `<templateType>Header</templateType>`. Обычный DSL `Header`
  должен оставаться `<groupTemplate>` с `<templateType>Header</templateType>`. Нельзя подменять
  `GroupHeader` на `Header` во входном DSL или вручную переставлять узлы в сгенерированном XML:
  это меняет семантику макета и скрывает дефект генератора.
- Для `GroupHeader` проверь обе ветки: targeted regression для `GroupHeader` и контрольный `Header`,
  затем `skd compile`, `validate --type skd`, применимую валидацию контейнера и Designer package/load
  oracle. `validate` без Designer oracle недостаточен для структуры, чувствительной к сериализации.
- Если DSL заявляет оформление области, проверь, что итоговый XML действительно содержит соответствующий `dcsat:appearance` и что runtime-результат показывает это оформление.
- Для границ областей различай общий параметр `СтильГраницы` и side-specific параметры
  `СтильГраницы.Слева/Справа/Сверху/Снизу`. Каноническая структура для границ по сторонам:
  общий `dcscor:item` с параметром `СтильГраницы` и базовой линией `None`, а side-specific
  `dcscor:item` должны быть вложены внутрь него. Не пиши `СтильГраницы.Слева/Справа/...`
  соседними элементами на уровне `dcsat:appearance`: такая структура может проходить
  XML-валидацию и загрузку, но теряться при round-trip через Конфигуратор или давать
  неверную runtime-отрисовку. Если генератор пишет side-specific границы не вложенными,
  исправляй генератор/тесты, а не компенсируй дефект в макете.
- Для сложных границ СКД-макета делай round-trip proof: сгенерируй XML, собери ERF/отчет,
  выгрузи его обратно через штатную выгрузку платформы и проверь, что `СтильГраницы.*`
  не потерялись и остались вложены в `СтильГраницы`.
- Лишняя внутренняя линия в СКД-макете проверяется как negative proof: отсутствие `СтильГраницы.Снизу` у
  верхней ячейки и `СтильГраницы.Сверху` у нижней ячейки в XML не является достаточным доказательством,
  пока runtime-табличный документ не показал отсутствие сегмента. Если runtime рисует линию без явного
  параметра, проверь альтернативную структуру области: объединение ячеек/строк, один параметр вместо двух
  строк, другой template type или допустимую постобработку результата.
- Если явные `СтильГраницы.Снизу=None` / `СтильГраницы.Сверху=None` тоже не убирают разделитель между
  строками, не продолжай подбирать цвета/толщины. Проверяй структурный вариант: один `tableCell` с
  несколькими `dcsat:item`, один многострочный параметр, другой способ вывода блока или платформенное
  ограничение на смешанное оформление внутри СКД-ячейки.
- Не считай успешный `xml-gen validate` или Designer-pack доказательством визуального слоя: они могут подтвердить структуру XML, но не факт отрисовки цветов, шрифтов, ширин, объединений и границ.
- При любом дефекте поддержанной сериализации останови работу над зависимым отчетом и выполни
  процесс `xml-generation` §4.1: отдельная регистрация дефекта, воспроизведение, red/green,
  полный build инструмента, повторная генерация и live-check. Локально исправленный XML не является
  допустимым proof и не разрешает продолжить поток.
- Не объявляй imported Excel/MXL "готовым своим макетом СКД", пока не доказана вся цепочка
  `groupTemplate -> template -> parameter -> expression -> runtime ТабличныйДокумент`.
- Отчет открывается штатной формой отчета, если собственной формы нет.
- Кнопка формирования строит фактический `ТабличныйДокумент`.
- Результат сохранен или снят как доказательство: MXL/XLSX/PDF/PNG.

## Runtime

Для внешнего отчета с СКД обычный пользовательский маршрут проверки:

1. Открыть `.erf` через `Файл -> Открыть`.
2. Получить стандартную форму отчета.
3. Нажать штатную кнопку формирования.
4. Сохранить или снять результат.

Не подменяй этот маршрут регистрацией внешнего отчета, запуском обработки через `/Execute` или сценарием, если проверяется именно пользовательское открытие ERF.

## Связанные навыки

- `mxl-layout-patterns` — визуальная модель областей.
- `skd-dsl` / `skd-edit` — техническая генерация и правка XML.
