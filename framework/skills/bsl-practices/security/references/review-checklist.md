# Чеклист ревью безопасности

Стек-нейтральный чеклист. Агент-reviewer проходит его **обязательно**, если в pull request затронуты:

- секреты (регистр `БезопасноеХранилищеДанных` через `ОбщегоНазначения.*ДанныеВБезопасноеХранилище*`, пароли, токены, ключи API),
- криптография (`МенеджерКриптографии`, `СертификатКриптографии`, ЭЦП),
- аутентификация (OpenID/OAuth/basic/клиентский сертификат),
- права, RLS, привилегированный режим,
- внешние интеграции (`HTTPСоединение`, веб-сервисы, обмен данными).

Если хотя бы один пункт нарушен — это блокирующий комментарий ревью.

---

## Секреты

- [ ] Ни один секрет (пароль, токен, ключ API, refresh-токен, пароль контейнера) не закоммичен в код, конфигурацию, макет, константу, реквизит справочника.
- [ ] Секреты хранятся через `ОбщегоНазначения.ЗаписатьДанныеВБезопасноеХранилище`/`ПрочитатьДанныеИзБезопасногоХранилища` с владельцем-ссылкой (не строкой-константой).
- [ ] Чтение/запись секрета выполняется только на сервере.
- [ ] `УстановитьПривилегированныйРежим(Истина)` стоит **точечно** вокруг работы с секретом, а не на всю функцию.
- [ ] `УстановитьПривилегированныйРежим(Ложь)` парный, в `Попытка/Исключение`, в той же области видимости.
- [ ] Секрет не возвращается клиенту (`НаКлиенте`, форма, отчёт).
- [ ] Переменные с секретом обнуляются после использования (`Пароль = ""`).
- [ ] Параметры процедур, пересекающих границу клиент↔сервер, **не содержат** паролей/токенов/ключей.

## Криптография

- [ ] `МенеджерКриптографии` создаётся с явными `ИмяПровайдера` и `ТипПровайдера` (не дефолтный).
- [ ] Версия ГОСТ зафиксирована: ГОСТ Р 34.10-2012 (256 или 512); ГОСТ-2001 — **только** для проверки старых подписей.
- [ ] Сертификат ищется **по отпечатку**, не «первый из хранилища», не по СН.
- [ ] Проверены `ДействителенС` и `ДействителенДо` перед использованием.
- [ ] Закрытый ключ **не** появляется в коде, реквизите, макете, журнале, файле выгрузки.
- [ ] Если в проекте есть БСП «Электронная подпись» — используется она, а не самописная обёртка.
- [ ] `ПараметрыПодписиCMS` явно заданы (тип, открепленная/прикреплённая, кодировка, временной штамп).
- [ ] Двоичные данные подписи не логируются целиком.

## Аутентификация и внешние API

- [ ] Заголовок `Authorization` собирается на сервере и не возвращается клиенту.
- [ ] OAuth refresh-токен перезаписывается через `ОбщегоНазначения.ЗаписатьДанныеВБезопасноеХранилище` при каждом обновлении access-токена.
- [ ] Error semantics реализована: `missing credentials`, `expired token`, `invalid certificate`, `provider unavailable`, `denied rights`, `tenant mismatch` — каждая ошибка имеет собственный путь обработки.
- [ ] `401`/`403` от внешнего API не превращается в «общую ошибку операции» и не уходит в retry-цикл бесконечно.
- [ ] Клиентский TLS-сертификат подключается через `СертификатКлиентаФайл`/`СертификатКлиентаWindows`/`СертификатКлиентаOpenSSL`, путь к ключу — на сервере.
- [ ] Время на сервере 1С синхронизировано (NTP) — критично для OIDC/JWT.

## Права и привилегированный режим

- [ ] Привилегированный режим не используется как «выключатель ролей» вокруг бизнес-логики.
- [ ] Внутри привилегированного блока выполняется **только** работа с секретом/системной таблицей.
- [ ] Результат привилегированного блока не утекает в форму/отчёт без явной проверки прав текущего пользователя.
- [ ] Проверки ролей и RLS не закомментированы «временно» без тикета на восстановление.
- [ ] Запросы, обходящие RLS (`РАЗРЕШЁННЫЕ` снят / привилегированный режим), помечены комментарием с обоснованием.

## Логирование и наблюдаемость

- [ ] Журнал регистрации, `Сообщить`, ответ агента, исключения **не содержат** паролей, токенов, приватных ключей, полных `Authorization`-заголовков.
- [ ] Тело HTTP-запроса/ответа логируется только после санитизации чувствительных полей (`password`, `token`, `secret`, `authorization`).
- [ ] Сертификаты в логе — отпечаток (это открытая информация), не PEM/CER целиком.
- [ ] Журналируются: корреляционный идентификатор, внешний идентификатор операции, код ответа, длительность, идентификатор бизнес-объекта.
- [ ] Личные данные (`ФИО`, `СНИЛС`, `ИНН ФЛ`, паспортные данные) логируются с учётом политики ПДн или маскируются.

## Хранение временных данных

- [ ] Временные файлы с чувствительными данными создаются в каталоге временных файлов сервера 1С.
- [ ] У временного файла есть явный путь удаления (`Попытка/Исключение/КонецПопытки` с `УдалитьФайлы`).
- [ ] Размер и время жизни ограничены; отсутствует риск, что файл «останется навсегда» при ошибке.

## Тесты и фикстуры

- [ ] В тестовых данных нет реальных паролей, токенов, ключей, сертификатов.
- [ ] Тестовые секреты — заведомо невалидные синтетические значения, явно помеченные как тестовые.
- [ ] Тестовые сертификаты — самоподписанные, не из боевых УЦ.

## Финальный фильтр перед ответом агента

- [ ] В финальном сообщении (ответ ревьюера/архитектора/разработчика) **нет** значений секретов, токенов, приватных ключей.
- [ ] Если код в PR демонстрирует утечку секрета — это **первый** комментарий ревью, остальные комментарии после него.
