# MXL-макеты табличных документов

## Назначение

MXL-макет — это шаблон табличного документа:

- области;
- ячейки;
- строки и колонки;
- объединения;
- параметры;
- ширины и высоты;
- границы;
- заливки;
- шрифты;
- выравнивание;
- форматы чисел и дат.

Этот навык отвечает за визуальную и структурную модель макета. Он не определяет, кто заполняет параметры:

- печатная форма заполняет параметры BSL-кодом;
- СКД на своем макете заполняет параметры через выражения СКД;
- другой механизм может использовать те же области иначе.

## Выбор источника эталона

Если эталон задан картинкой, сначала используй `layout-from-image`.

Если эталон задан Excel-файлом, используй `layout-from-excel`: Excel нужно анализировать как
структуру workbook или через проверенный платформенный импорт в `ТабличныйДокумент`, а не как
картинку. Imported MXL из Excel считай визуальным каркасом; именованные области, параметры и
прикладные привязки проектируй отдельно.

Если эталон задан существующим MXL/Template.xml, сначала получи структуру через инструменты MXL и сравни области/параметры/стили.

Если эталон задан текстом, преврати его в явную `layout/border/style spec`.

## Унифицированная спецификация

Перед реализацией макета должна быть спецификация:

- `layout spec` — области, bbox, сетка, GAP, повторяемость;
- `border spec` — сегменты линий, цвет, толщина, наличие/отсутствие;
- `style spec` — заливки, шрифты, выравнивание, форматы;
- `data binding spec` — какие ячейки являются параметрами;
- `runtime proof plan` — как будет получен и проверен результат.

## Функциональный и технический слой

Разделяй две разные задачи.

Функциональный слой отвечает на вопросы:

- какие разделы видит пользователь;
- какая часть повторяется;
- где шапка таблицы, строка, итог, подвал;
- какие значения являются данными, а какие статическими подписями;
- какие блоки должны печататься условно.

Результат функционального слоя — карта областей:

```text
Заголовок -> один раз
ШапкаТаблицы -> один раз перед строками
Строка -> N раз
Итого -> один раз после строк
Подвал -> один раз
```

Технический слой отвечает на вопросы:

- сколько колонок в сетке;
- какие ширины и высоты;
- какие ячейки объединены;
- какие стили применяются;
- какие параметры есть в каждой области;
- какие форматы чисел/дат нужны;
- как область будет получена и выведена.

В `mxl-dsl` технический слой обычно выражается через:

- `columns`, `page`, `columnWidths`;
- `fonts`, `styles`;
- `areas[].name`;
- `rows`, `rowStyle`, `cells`;
- `text`, `param`, `template`, `detail`;
- `span`, `rowspan`, `format`.

MXL похож на Excel-лист на уровне строк, колонок, ячеек, объединений, ширин, высот, рамок, шрифтов, выравнивания и форматов. Но MXL-макет обычно не является конечной таблицей: он хранит фрагменты-шаблоны, которые выводятся кодом, СКД или другим механизмом.

Если источник пришел из Excel через импорт в `ТабличныйДокумент`, не переноси автоматически на MXL
доверие к Excel-специфичным свойствам: freeze panes, auto filter, print area, точные ширины колонок,
формулы и часть форматов должны считаться непроверенными, пока round-trip proof не показал обратное.

## Области

Типовые области:

- `Заголовок`;
- `Шапка`;
- `ШапкаТаблицы`;
- `Строка`;
- `Группа`;
- `Итого`;
- `Подвал`.

Для переменного количества строк не рисуй фиксированный набор строк. Делай повторяемую область `Строка`.

## Параметры

Статический текст оставляй текстом. Значения, которые зависят от данных, делай параметрами.

Для каждой параметрической ячейки зафиксируй:

- имя параметра;
- формат значения;
- источник значения;
- пример значения;
- выравнивание и стиль;
- допустимое поведение при пустом значении.

Если макет начался с imported Excel-каркаса, отдельно зафиксируй, какие данные будут:

- параметрами именованных областей;
- прямой записью по координатам;
- статическим текстом imported шаблона.

Не оставляй этот переход "само собой разумеющимся": imported каркас не создает прикладную модель
параметров автоматически.

## Сетка и объединения

Проектируй общую сетку макета осознанно.

Если разные визуальные зоны используют разные разбиения колонок, найди общую базовую сетку и выражай зоны через объединения. Иначе итоговый табличный документ может разъехаться: ширины строк будут выравниваться по общей сетке, а не существовать независимо.

## Границы

Границы проверяются отдельно от геометрии.

Для каждого блока опиши:

- внешний контур;
- внутренние разделители;
- границы таблицы;
- отсутствующие линии;
- цвет и толщину;
- отличие акцентных и вспомогательных линий.

Для отсутствующих линий нужен отдельный negative proof: в исходном макете/DSL не должно быть параметра
границы, а в runtime-результате не должно быть видимого сегмента. Если сегмент появляется только на
runtime-слое, проверяй возможности целевой технологии: объединение ячеек/строк, тип области, постобработку
табличного документа или другой способ построения блока.

### Внешняя нижняя граница повторяемой таблицы

Если заключительная внешняя нижняя граница таблицы должна быть нарисована один раз, не задавай ее в
шаблоне повторяемой строки: такая граница будет выведена под каждой строкой. Внутренние границы оставляй
в повторяемой области, а внешние левую, правую и заключительную нижнюю границы задавай одноразовой
завершающей областью (`GroupFooter`/конец таблицы). Если отдельная завершающая область невозможна,
допускается только контролируемая постобработка сформированного табличного документа.

Если технология не позволяет точно выразить нужную границу, сначала докажи это через API/документацию/runtime-пробу, затем фиксируй ограничение.

## Проверка возможностей MXL API

Если эталон содержит элемент, который выглядит как свободная графика, а не обычная ячейка таблицы
(например, скругленный угол, тень, нестандартный контур, декоративная подложка), сначала проверь
платформенное API табличного документа:

- `ОбластьЯчеекТабличногоДокумента` — свойства ячейки, границ, фона, шрифта, картинки;
- `Линия` — поддерживаемые типы и толщина линий;
- `РисунокТабличногоДокумента` — возможности рисунков, линий, фона и размещения;
- `ТабличныйДокумент` — коллекции рисунков, фоновая картинка и способы вывода.

Если у ячейки/линии/рисунка нет свойства для нужного эффекта, не подгоняй его через случайные
изменения сетки, толщин или цветов. Зафиксируй одно из решений:

- штатная реализация через найденное свойство API;
- осознанная имитация через картинку/рисунок, если это допустимо для задачи;
- доказанное допустимое отклонение, если эффект пришел из картинки-образца и не поддерживается MXL.

## Проверка результата

Минимальный proof после реализации:

1. Сгенерировать/собрать макет поддержанным инструментом.
2. Проверить структуру через `info/validate`, если инструмент доступен.
   Если подключён MCP `1c-form-viewer`, после генерации или правки макета выполнить `open_preview` (`audience="agent"`) и `capture_preview`. Это быстрая визуальная оценка без сборки. Сервер работает только на просмотр и runtime-proof шага 3 не заменяет: `xml-generation/references/form-viewer-mcp.md`.
3. Получить runtime `ТабличныйДокумент`, MXL/XLSX/PDF или скриншот.
4. Проверить:
   - layout proof;
   - border proof;
   - style proof;
   - negative checks.
5. В отчете не смешивать доказанные совпадения и остаточные отличия.

Если поддержанная генерация MXL или MXL-слоя собственного макета СКД создает неканонический XML,
который теряется при round-trip, не открывается или иначе расходится с платформой, останови
зависимый поток и примени `xml-generation` §4.1. Локальная ручная правка XML не является
исправлением: нужны отдельная регистрация дефекта, воспроизведение, regression test, полный build
инструмента и live-check заново сгенерированного артефакта.

## Инструменты

Для MXL/XML используй специализированные инструменты:

```bash
xml-gen mxl info <Template.xml> --with-text --limit 200
xml-gen mxl compile layout.json Template.xml
xml-gen validate --type mxl Template.xml
```

Для СКД-макета MXL-слой применяется через `skd-custom-layout`, а техническая генерация идет через `skd-dsl`.

## Связанные навыки

- `layout-from-image` — если эталон картинка.
- `layout-from-excel` — если эталон Excel.
- `skd-custom-layout` — если MXL-области заполняет СКД.
- `print-form-patterns` — если MXL-области заполняет BSL-код печатной формы.
- `mxl-dsl` — технический инструмент генерации MXL.
