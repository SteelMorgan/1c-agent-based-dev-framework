# Проверка данных табличного вывода

Отделяй доказательство корректности данных от верстки и визуальной приемки. Не начинай
компоновку, заполнение областей или запись ячеек, пока проверочный запрос и data contract
не подтвердят будущий набор вывода.

## Когда применять

| Триггер | Действие |
|---|---|
| Проектируется или изменяется СКД-отчет | Проверить запросом каждый набор до запуска компоновки |
| Печатная форма выводит MXL-области вручную | Независимо проверить строки и итоги до заполнения областей |
| Код напрямую записывает данные в `ТабличныйДокумент` | Проверить будущий набор до первой runtime-записи |
| Визуальный каркас получен импортом Excel | Проверить данные независимо от импортированного scaffold |
| Печатная форма получает объект документа | Проверить запросом строки и итоги документа; не считать объект доказательством |

## Обязательный gate

Всегда проходи цепочку:

```text
требования к данным
  -> безопасный запрос 1С
  -> зафиксированный результат проверки
  -> data contract для колонок, параметров и ячеек
  -> компоновка или ручной вывод
```

Механизм вывода и происхождение визуального каркаса не отменяют ни один шаг. Excel-import
scaffold доказывает только структуру представления. Объект документа удобен для runtime-
заполнения, но сам по себе не доказывает полноту строк, отсутствие дублей и правильность
итогов.

## Порядок проверки

1. Зафиксируй требования к каждому набору: поля, бизнес-смысл, ключ строки, ожидаемую
   кардинальность, правила пустых значений, итоги, период, параметры и активные отборы.
2. Через `platform-data-core` проверь существование метаданных и типы источников. Для нового
   проверочного запроса примени `query-patterns`.
3. Составь минимальный безопасный запрос 1С, достаточный для доказательства требований.
   Не копируй производственный запрос целиком без необходимости и не обращайся к СУБД напрямую.
4. Выполни запрос с теми же периодом, параметрами и отборами, которые получит будущий вывод.
5. Для каждого набора зафиксируй все проверки из обязательной матрицы.
6. Составь data contract и явно раздели доказанные факты и допущения.
7. Разреши компоновку или ручной вывод только при полном `PASS`. При расхождении останови
   зависимый маршрут, исправь источник данных или требования и повтори проверку.

## Обязательная матрица доказательств

Для каждого набора фиксируй:

| Проверка | Что доказать |
|---|---|
| Состав полей | Каждое поле существует, имеет ожидаемый типовой и бизнес-смысл |
| Число строк | Фактическая кардинальность соответствует требованиям при активных отборах |
| `NULL` и пустые значения | Обязательные поля заполнены, допустимые пустые значения классифицированы |
| Дубли | По бизнес-ключу нет неожиданных повторов; ожидаемые повторы объяснены |
| Агрегаты и итоги | Контрольные суммы, количества и другие итоги совпадают с требованиями |
| Репрезентативная выборка | Видны граничные и типовые строки, а не только удобный положительный пример |

Не заменяй проверку строк только агрегатом: правильная общая сумма может скрыть дубли или
компенсирующие ошибки. Не заменяй агрегат только выборкой: несколько верных строк не
доказывают полный итог.

### Печатная форма из объекта документа

Если runtime-код получает объект документа, сформируй отдельный запрос-проверку по ссылке
документа. Проверь как минимум:

- состав и количество строк каждой выводимой табличной части;
- дубли по бизнес-ключу строки;
- обязательные пустые значения;
- итоги документа и итоговые значения по строкам;
- соответствие параметров, периода и отборов будущей печати.

## Data contract

Составляй контракт отдельно для каждого набора. Минимальный шаблон:

| Колонка/параметр макета | Источник | Правило пустого значения | Ключ строки | Ожидаемая кардинальность | Проверяемый итог | Статус знания |
|---|---|---|---|---|---|---|
| `<имя>` | `<набор.поле или выражение>` | `<запрещено/допустимо/замена>` | `<бизнес-ключ>` | `<1, 0..1, N>` | `<сумма/количество/не применимо>` | `<доказано/допущение>` |

Контракт обязан связывать каждую выводимую колонку и каждый параметр области/ячейки с
источником. Не оставляй визуальные параметры без data-binding и не маскируй допущение как
результат запроса.

Заполненный пример контракта и контекста доказательства:
`references/data-contract-example.md`.

Дополнительно фиксируй контекст доказательства:

| Набор | Период | Параметры | Активные отборы | Число строк | Пустые | Дубли | Итоги | Выборка | Вердикт |
|---|---|---|---|---:|---|---|---|---|---|
| `<имя>` | `<значение>` | `<значения>` | `<условия>` | `<N>` | `<результат>` | `<результат>` | `<результат>` | `<ссылка/фрагмент>` | `PASS/FAIL` |

## Правильно и неправильно

Правильно: сначала выполнить отдельный минимальный запрос с runtime-параметрами, сохранить
результаты матрицы и только затем передать доказанный контракт в `skd-report-patterns` или
`print-form-patterns`.

Неправильно:

```bsl
Объект = Ссылка.ПолучитьОбъект();
// Немедленный вывод строк объекта без независимой проверки набора и итогов.
ВывестиПечатнуюФорму(Объект);
```

Такой код может сформировать визуально корректный документ при неполных, задублированных
или неверно агрегированных данных.

## Критерий завершения

Gate закрыт только когда для каждого набора:

- выполнен платформенный запрос 1С;
- зафиксированы все шесть обязательных проверок;
- учтены период, параметры и активные отборы;
- каждая колонка/параметр связана data contract с источником и правилами;
- доказанные факты отделены от допущений;
- вердикт равен `PASS` до начала runtime-компоновки или ручного вывода.
