# Макет из картинки-образца

## Назначение

Используй этот навык, когда источник истины по внешнему виду — картинка: скриншот, PNG/JPG-макет, экспорт из дизайнера, изображение печатной формы или отчета.

Картинка не является готовой спецификацией. Перед реализацией нужно извлечь из нее проверяемую модель:

- `layout spec` — геометрия;
- `border spec` — линии и контуры;
- `style spec` — заливки и текст;
- `negative checks` — зоны, где элемента быть не должно.

Этот навык не зависит от технологии реализации. Его результат может использовать MXL-макет, СКД-макет, печатная форма, HTML-отчет или другая система вывода.

## Выходной артефакт

Создай markdown-спецификацию с разделами:

```text
1. Source
2. Normalization
3. Layout spec
4. Border spec
5. Style spec
6. Negative checks
7. Acceptance tolerances
8. Open questions
```

Не переходи к реализации, пока не выделены хотя бы крупные зоны, границы и текстовые стили.

## 1. Source

Зафиксируй:

- путь к картинке;
- размер изображения;
- рабочий crop, если на картинке есть поля, UI-хром, номера строк/колонок или посторонний фон;
- почему выбран именно этот crop;
- масштаб сравнения: исходный, приведенный к ширине, приведенный к сетке.

## 2. Normalization

Перед сравнением результата и образца приведи их к одной системе координат:

- bbox содержимого;
- масштаб;
- поворот, если есть;
- crop без внешней UI-обвязки;
- сетка колонок/строк, если она видна или может быть выведена из повторяющихся границ.

Если сравниваются скриншоты разных размеров, не сравнивай абсолютные пиксели без нормализации.

## 3. Layout Spec

Опиши геометрию:

| Поле | Что фиксировать |
|---|---|
| Зона | Имя смыслового блока: заголовок, KPI, таблица, строка, подвал |
| bbox | Координаты в crop или в нормализованной сетке |
| Размер | Ширина/высота |
| Позиция | Относительно соседних зон |
| GAP | Пустые промежутки между зонами |
| Повторяемость | Одна зона или шаблон строки/группы |

Layout proof отвечает только на вопрос "где находится зона и какого она размера". Он не доказывает правильность границ, цвета и шрифта.

## 4. Border Spec

Опиши границы как сегменты, а не как общее впечатление:

| Поле | Что фиксировать |
|---|---|
| Сегмент | `top`, `left`, `right`, `bottom`, внутренняя линия, разделитель |
| Откуда/куда | Координаты начала и конца |
| Цвет | RGB/HEX или допустимый диапазон |
| Толщина | px или диапазон |
| Непрерывность | Сплошная, пунктир, разрыв |
| Назначение | Внешний контур, линия заголовка, граница таблицы |

Обязательно разделяй:

- внешний контур блока;
- внутренние разделители;
- границы таблицы;
- серые вспомогательные линии;
- акцентные цветные линии.

Для каждой важной линии добавь negative check для зон, где линии быть не должно. Лишняя линия — такой же дефект, как отсутствующая.

Border proof должен подтверждать не только наличие нужных линий, но и отсутствие лишних сегментов:
проверяй отрицательные зоны на runtime-изображении отдельно от исходной спецификации. Если в исходном
макете/DSL линия не задана, но runtime все равно ее рисует, это не считается пройденной проверкой —
нужно зафиксировать расхождение как ограничение или дефект технологии вывода и проверить альтернативную
структуру макета.

## 5. Style Spec

Опиши оформление:

| Поле | Что фиксировать |
|---|---|
| Заливка | Цвет фона зоны |
| Текст | Значимый текст или паттерн параметра |
| Цвет текста | RGB/HEX или диапазон |
| Размер | Относительно зоны или оценка px/pt |
| Начертание | Обычный, bold, italic, underline |
| Выравнивание | Горизонтальное и вертикальное |
| Отступы | Внутренние отступы текста от границ |
| Формат | Числа, даты, проценты, пробелы разрядов |

Если точный шрифт нельзя доказать по картинке, фиксируй измеримые признаки: высота букв, жирность, цвет, выравнивание, относительный размер.

## 6. Negative Checks

Отдельно перечисли запреты:

- в этой зоне не должно быть границы;
- между этими строками не должно быть разделителя;
- фон должен быть пустым/белым;
- текст не должен выходить за bbox;
- таблица не должна иметь лишнюю колонку;
- блок не должен уходить за видимую область.

Такие проверки нужны, потому что визуальные дефекты часто появляются как лишние элементы.

## 7. Acceptance Tolerances

Для каждого класса проверки укажи допустимое отклонение:

- bbox/позиции: обычно `1-3 px` после нормализации или доля ячейки сетки;
- цвет: допустимый delta RGB/HSV, если есть антиалиасинг;
- толщина линии: точное значение или диапазон;
- текст: допускается антиалиасинг, но не изменение размера/начертания;
- общий размер: отдельно от локальных зон.

Не объявляй "похоже" приемкой. Приемка должна ссылаться на конкретные измерения.

## 8. Proof Workflow

1. Извлеки `layout/border/style spec` из картинки.
2. Для спорных визуальных требований проверь API целевой технологии до реализации:
   - если API поддерживает элемент напрямую — реализуй штатным свойством;
   - если API поддерживает только имитацию через другой механизм — отдельно зафиксируй стоимость и риски имитации;
   - если API не поддерживает элемент — зафиксируй доказанное допустимое отклонение, а не подгоняй невозможное пикселями.
3. Реализуй макет.
4. Получи runtime-результат тем же способом, которым пользователь будет его видеть.
5. Нормализуй target и actual.
6. Проверь три слоя:
   - layout proof;
   - border proof;
   - style proof.
7. Отдельно проверь negative checks.
8. В отчете разделяй:
   - доказано;
   - не доказано;
   - отличается;
   - требует исследования возможностей платформы.

## Что нельзя делать

- Нельзя считать bbox/grid proof доказательством полного визуального соответствия.
- Нельзя проверять только крупные зоны и игнорировать границы/шрифты/заливки.
- Нельзя считать отсутствие линии в DSL/XML доказательством ее отсутствия в результате без runtime-проверки.
- Нельзя утверждать невозможность повторения элемента, пока не проверены возможности API целевой технологии.
- Нельзя долго подгонять визуальный элемент, если целевая технология не имеет соответствующего свойства или поддерживает его только через отдельный механизм имитации.
- Нельзя переносить частный пример в универсальное правило без обобщения.
