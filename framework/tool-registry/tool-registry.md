# Реестр инструментов (Tool Registry)

> **Source of truth** для всех абстрактных возможностей (capabilities) фреймворка.
> Навыки и правила ссылаются ТОЛЬКО на capability из этого реестра, никогда — на конкретные имена MCP-tool-ов.

---

## Назначение

Слой tool-registry решает одну ключевую проблему: **развязку навыков/правил фреймворка от конкретных MCP-серверов**.

Без этого слоя каждый навык и каждое правило содержали бы прямые ссылки на tool-ы конкретного MCP-сервера (`logc_get_event_log`, `check_syntax_edt`, `symbol_explore`). При замене MCP-сервера пришлось бы переписывать десятки файлов.

С tool-registry:
- Навыки и правила оперируют абстрактными capability: `check_syntax`, `navigate_symbol`, `search_platform_api`
- Маппинг capability → конкретный tool описан в **provider profile** (один файл на MCP-сервер)
- **Замена MCP-сервера = изменение одного provider profile**, если новый сервер реализует те же capability

### Принцип работы

```
Навык/правило                Provider profile              MCP-сервер
─────────────               ─────────────────             ──────────
"используй                  platform-context.md:          mcp-bsl-platform-context:
 search_platform_api"  →    search_platform_api → search  →  search(query, type, limit)
```

---

## Терминология

| Термин | Определение |
|--------|-------------|
| **MCP server** | Конкретный сервер, реализующий Model Context Protocol. Определяется репозиторием, версией и endpoint. Пример: `alkoleft/mcp-bsl-platform-context v1.0` |
| **Provider profile** | Файл-маппинг, описывающий: какие capability реализует данный MCP server, через какие конкретные tool-ы, с какими параметрами и ограничениями. Один файл = один MCP server |
| **Capability** | Абстрактная возможность фреймворка, не привязанная к конкретному MCP server. Пример: `check_syntax` — проверка синтаксиса, независимо от того, кто её выполняет (EDT, Designer, LSP) |
| **Capability contract** | Формальное описание интерфейса capability: входные параметры, формат результата, типичные ошибки, побочные эффекты. Provider profile обязан реализовать контракт или явно указать отклонения |

---

## Capability Contracts

Каждая capability описывается контрактом ниже. Provider profile обязан реализовать контракт или явно указать ограничения/отклонения.

### Формат результата (Result Format)

Capability контракт описывает **идеальный** структурированный результат. Но реальные MCP-серверы могут возвращать данные в разных форматах:

| Формат | Описание | Пример |
|--------|----------|--------|
| `structured` | JSON с предсказуемыми полями | `{success: true, rows: [...]}` |
| `raw_text` | Текстовый/markdown ответ | Форматированная таблица или список |
| `mixed` | JSON-обёртка с текстовым payload | `{valid: true, message: "текст"}` |

**Правило:** Provider profile ДОЛЖЕН указать реальный `result_format` для каждой capability. Агент ДОЛЖЕН быть готов парсить `raw_text` — не полагаться на точные JSON-ключи, если провайдер указал `raw_text`.

### Категории

| Категория | Уровень | Capability | Краткое описание |
|-----------|---------|------------|-----------------|
| **Core (MUST)** | Обязательные — без них фреймворк не функционален | `search_platform_api`, `check_syntax`, `run_tests`, `navigate_symbol`, `get_diagnostics` | Поиск по API, проверка синтаксиса, тесты, навигация, диагностика |
| **Important (SHOULD)** | Важные — деградация качества, но работать можно | `get_type_info`, `build_project`, `search_metadata`, `rename_symbol`, `get_call_graph`, `ask_ai_assistant` | Типы, сборка, метаданные, рефакторинг, граф вызовов, AI |
| **Optional (MAY)** | Опциональные — дополнительные возможности | `search_event_log`, `search_tech_log`, `configure_tech_log`, `dump_config`, `launch_app`, `get_code_actions`, `search_templates`, `search_ssl_functions`, `execute_query`, `validate_query`, `resolve_nav_link` | Логи, выгрузка, запуск, быстрые действия, шаблоны, БСП, запросы, навигационные ссылки |

#### search_platform_api

**Категория:** Core (MUST)
**Описание:** Поиск по API платформы 1С:Предприятие — типы, методы, свойства, глобальные функции.

**Входные параметры:**

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:------------:|----------|
| `query` | string | ✓ | Поисковый запрос. Конкретные термины 1С: `СтрНайти`, `ТаблицаЗначений`, `Справочник` |
| `type` | string | — | Фильтр по типу элемента: `method`, `property`, `type`. По умолчанию — все |
| `limit` | integer | — | Максимум результатов (по умолчанию 10, максимум 50) |

**Результат:**

| Поле | Тип | Описание |
|------|-----|----------|
| `results` | array | Список найденных элементов API |
| `results[].name` | string | Имя элемента (например, `СтрНайти`) |
| `results[].kind` | string | Тип: `method` / `property` / `type` |
| `results[].description` | string | Краткое описание элемента |
| `results[].signature` | string | Сигнатура (для методов) |

**Типичные ошибки:**
- Сервер недоступен → capability помечается `unavailable`, агент фиксирует причину пропуска
- Пустой результат при нечётком запросе → уточнить запрос конкретными терминами 1С

**Побочные эффекты:** нет (read-only)

#### check_syntax

**Категория:** Core (MUST)
**Описание:** Проверка синтаксиса BSL-модуля или конфигурации целиком.

**Входные параметры:**

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:------------:|----------|
| `target` | string | ✓ | Путь к модулю, имя проекта EDT или `all` для всей конфигурации |
| `mode` | string | — | Режим проверки: `edt` (через EDT validate), `designer_config` (CheckConfig), `designer_modules` (CheckModules). По умолчанию: `edt` |
| `options` | object | — | Дополнительные параметры режима (режимы эмуляции клиентов, расширения и т.д.) |

**Результат:**

| Поле | Тип | Описание |
|------|-----|----------|
| `success` | boolean | Проверка пройдена без ошибок |
| `errors` | array | `[{file, line, message, severity}]` — список ошибок |
| `warnings` | array | `[{file, line, message}]` — список предупреждений |
| `check_time` | integer | Время проверки в миллисекундах |

**Типичные ошибки:**
- Сервер недоступен → capability `unavailable`
- Таймаут на больших конфигурациях → увеличить timeout в конфигурации проекта
- Проект EDT не найден → проверить путь и sourceSet в настройках

**Побочные эффекты:** нет (read-only)

#### navigate_symbol

**Категория:** Core (MUST)
**Описание:** Навигация по символам BSL-кода — переход к определению, поиск символов, информация при наведении.

**Входные параметры:**

| `line` | integer | — | Номер строки (0-based, для позиционных операций) |
| `character` | integer | — | Позиция символа (0-based, для позиционных операций) |
| `operation` | string | — | Тип операции: `search` (поиск по имени), `definition` (переход к определению), `hover` (информация о символе). По умолчанию: `search` |

**Результат:**

| Поле | Тип | Описание |

**Побочные эффекты:** нет (read-only)

#### get_type_info

**Категория:** Important (SHOULD)
**Описание:** Получение детальной информации о типе платформы 1С — методы, свойства, конструкторы.

#### rename_symbol

**Категория:** Important (SHOULD)
**Описание:** Переименование символа (переменной, процедуры, функции) во всех файлах проекта через LSP.

| `character` | integer | ✓ | Позиция символа (0-based) |
| `new_name` | string | ✓ | Новое имя символа |
| `preview` | boolean | — | Если `true` — только предпросмотр изменений без применения. По умолчанию: `true` |

**Входные параметры:**

| `from` | string | ✓ | Начало периода (ISO 8601) |
| `to` | string | ✓ | Конец периода (ISO 8601) |
| `name` | string | — | Фильтр по типу события: `EXCP`, `DBMSSQL`, `DBPOSTGRS`, `TLOCK`, `TTIMEOUT`, `TDEADLOCK`, `CONN`, `SESN` |
| `mode` | string | — | Детализация: `minimal`, `full`. По умолчанию: `minimal` |

**Результат:**

| Поле | Тип | Описание |

| `records[].duration` | integer | Длительность (мкс) |

- Широкий временной диапазон → использовать узкие окна (15-30 мин)

**Побочные эффекты:** нет (read-only)

#### configure_tech_log

**Категория:** Optional (MAY)
**Описание:** Управление конфигурацией технологического журнала — создание, сохранение, восстановление, отключение.

**Входные параметры:**

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:------------:|----------|
| `action` | string | ✓ | Действие: `configure` (создать конфигурацию), `save` (сохранить бэкап), `restore` (восстановить из бэкапа), `disable` (отключить), `read` (прочитать текущую), `get_timestamp` (актуальная метка времени) |
| `cluster_guid` | string | * | GUID кластера (обязателен для `configure`) |
| `infobase_guid` | string | * | GUID ИБ (обязателен для `configure` и `get_timestamp`) |
| `location` | string | * | Путь для файлов логов (обязателен для `configure`) |
| `history` | integer | * | Время хранения в часах (обязателен для `configure`, рекомендуется 12-48) |
| `events` | array | * | Типы событий: `['EXCP', 'DBMSSQL', 'TLOCK']` (обязателен для `configure`) |
| `properties` | array | — | Свойства для сбора: `['all']` или конкретные `['sql', 'duration']` |
| `config_path` | string | — | Путь к файлу `logcfg.xml` |

**Результат:**

| Поле | Тип | Описание |
|------|-----|----------|
| `success` | boolean | Операция выполнена |
| `message` | string | Описание результата |
| `config_content` | string | Содержимое XML (для `configure` и `read`) |
| `max_timestamp` | string | Актуальная метка времени (для `get_timestamp`) |

**Типичные ошибки:**
- Нет прав на запись `logcfg.xml` → проверить разрешения
- Бэкап не найден при восстановлении → ранее не было сохранения

**Побочные эффекты:** создание/изменение/удаление файла `logcfg.xml` (mutating). Требуется перезапуск служб 1С для применения.

#### execute_query

**Категория:** Optional (MAY)
**Описание:** Выполнение запроса на языке запросов 1С против информационной базы. Возвращает структурированный JSON с автоконвертированными ссылками. **SECURITY:** данные уходят в LLM — не передавать конфиденциальную информацию.

**Входные параметры:**

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:------------:|----------|
| `queryText` | string | ✓ | Текст запроса на языке запросов 1С (SELECT/ВЫБРАТЬ) |
| `parameters` | object | — | Параметры запроса. Поддерживает описания ссылочных объектов: `{_objectRef: true, УникальныйИдентификатор, ТипОбъекта}` |
| `limit` | number | — | Ограничение строк (по умолчанию 100, максимум 1000) |

**Результат:**

| Поле | Тип | Описание |
|------|-----|----------|
| `success` | boolean | Запрос выполнен успешно |
| `columns` | array | `[{name}]` — имена колонок |
| `rows` | array | Массив объектов — строки результата |
| `truncated` | boolean | Результат обрезан по limit |
| `message` | string | Сообщение об ошибке (при `success: false`) |

**Типичные ошибки:**
- Ошибка синтаксиса запроса → использовать `validate_query` для проверки
- Неизвестная таблица/поле → проверить через `get_metadata_structure`
- Таймаут на тяжёлых запросах → уменьшить `limit`, сузить условия

**Побочные эффекты:** нет (read-only, только SELECT)

## Как добавить нового провайдера

1. Скопировать шаблон [`_template-provider.md`](./_template-provider.md)
2. Заполнить метаданные MCP-сервера (репозиторий, версия, категория)
3. Для каждой реализуемой capability:
   - Указать конкретное имя tool в MCP-сервере
   - Описать маппинг параметров: capability-параметр → tool-параметр
   - Отметить отклонения от контракта
   - Привести пример вызова
4. Добавить файл в `providers/`
5. Обновить матрицу совместимости в этом документе

Подробный шаблон со всеми секциями — в [`_template-provider.md`](./_template-provider.md).
