# Политика SDD (Spec-Driven Development)

> RULES — обязательные политики, ограничивающие поведение агента. Спецификация создаётся до реализации и является контрактом.

---

## Назначение

Это правило обеспечивает управление scope и качество решений за счёт SDD: спецификация создаётся до кода, ревьюируется до реализации, реализация не должна отклоняться от утверждённой спеки без её обновления.

---

## Условия срабатывания

Правило применяется, когда агент:

- Получает задачу на реализацию
- Классифицирует задачу по сложности (простая / средняя / сложная)
- Создаёт или изменяет спецификацию
- Реализует функциональность по спецификации

---

## Требования

### MUST (обязательно)

| Требование | Описание |
|------------|----------|
| Спека для новых фич | Спецификация MUST быть создана для новых фич, архитектурных изменений, сложных исправлений багов |
| Формат спецификации | Спецификация MUST следовать формату из `skills/spec-writing/spec-standard.md` |
| Ревью до реализации | Спецификация MUST быть ревьюирована до начала реализации |
| Соответствие реализации | Реализация MUST NOT отклоняться от утверждённой спецификации без обновления спеки |
| Ревью при изменении спеки | Изменения утверждённой спеки требуют повторного ревью |

### SHOULD (настоятельно рекомендуется)

| Требование | Описание |
|------------|----------|
| Спека для рефакторинга | Спецификация SHOULD быть создана для крупного рефакторинга, умеренных изменений |

### MAY (допустимо)

| Ситуация | Описание |
|----------|----------|
| Простое исправление бага | Спецификация MAY быть пропущена |
| Форматирование, правки опечаток | Спецификация MAY быть пропущена |

---

## SDD Workflow

```
1. Получить задачу → классифицировать по сложности
2. Если спека нужна → создать спеку по стандарту
3. Отправить спеку на ревью (применяется cross-review-policy)
4. Итерировать до отсутствия BLOCK-замечаний
5. Получить одобрение пользователя (для средних/сложных задач)
6. Реализовать согласно спецификации
7. Проверить соответствие реализации спецификации
```

---

## Классификация сложности

| Тип задачи | Нужна спека | Обоснование |
|------------|-------------|-------------|
| Новая функциональность | MUST | Фиксирует scope, требования, альтернативы |
| Архитектурные изменения | MUST | Изменение структуры требует обоснования |
| Сложное исправление бага | MUST | Влияние на архитектуру или поведение |
| Рефакторинг | SHOULD | Рекомендуется для крупного рефакторинга |
| Простое исправление бага | MAY | Локальное изменение, можно без спеки |
| Форматирование, опечатки | MAY | Не требуется |

---

## Отклонение от спеки

Если в процессе реализации выявлена необходимость отклониться от спеки:

1. Остановить реализацию
2. Обновить спецификацию (изменения, обоснование)
3. Отправить обновлённую спеку на ревью
4. Получить одобрение (если требуется)
5. Продолжить реализацию по обновлённой спеке

---

## Исключения

- Простые задачи (форматирование, опечатки, очевидные фиксы) — спека не нужна
- Пользователь может явно запросить реализацию без спеки для прототипирования
- В свободном режиме (без full-cycle) создание спеки — advisory, не mandatory
