# Политика SDD (Spec-Driven Development)

> Спецификация создаётся до реализации и является контрактом. Реализация MUST NOT отклоняться без обновления и повторного ревью.

## Классификация: когда нужна спека

| Тип задачи | Уровень |
|------------|---------|
| Новая функциональность, архитектурные изменения, сложный баг | MUST |
| Крупный рефакторинг | SHOULD |
| Простой баг, форматирование, опечатки | MAY (пропустить) |

## SDD Workflow

```
1. Классифицировать задачу по сложности
2. Создать спеку по стандарту (spec-standard) + Acceptance Scenarios (Gherkin) для MUST-требований
3. Ревью спеки → итерации до снятия BLOCK
4. Архитектура + Task Breakdown JSON → ревью → итерации до снятия BLOCK
5. Одобрение пользователя (для средних/сложных)
6. Реализация строго по спеке и JSON-декомпозиции
7. Проверка соответствия реализации спеке
```

## MUST-требования

- Спека создаётся для новых фич, архитектурных изменений, сложных багов
- Формат — `spec-standard`; ревью до реализации
- Task Breakdown JSON — отдельный `.json`, ревью до реализации
- Любое изменение утверждённой спеки/JSON требует повторного ревью

## Отклонение от спеки

1. Остановить реализацию
2. Обновить спеку + ревью + одобрение
3. Продолжить по обновлённой спеке

## Исключения

- Простые задачи — спека не нужна
- Прототипирование по запросу пользователя — без спеки
- Свободный режим (без full-cycle) — advisory
