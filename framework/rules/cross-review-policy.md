# Политика кросс-ревью (Cross-Review Policy)

> RULES — обязательные политики, ограничивающие поведение агента. Правила опираются на паттерн Evaluator-Optimizer (Anthropic).

---

## Назначение

Это правило обеспечивает контроль качества артефактов, созданных агентом: всё, что сгенерировал один агент, проверяется другим агентом в детерминированном режиме. Ревьюер оценивает артефакт против цели задачи и использует чек-листы по типу артефакта.

---

## Условия срабатывания

Правило применяется в **детерминированном режиме** фреймворка, когда:

- Выполняется full-cycle workflow
- Создаёт артефакт агент-генератор (разработчик, архитектор, аналитик)
- Тип артефакта попадает в категории Full review / Standard review / Light review (см. Review Gating)

---

## Требования

### Основной принцип

Всё сгенерированное одним агентом MUST быть проверено другим агентом (в детерминированном режиме).

### Протокол ревью

| Элемент | Описание |
|---------|----------|
| **Вход ревьюера** | [TASK] + [SPEC] + [ARTIFACT] + [CHECKLIST] |
| **Выход ревьюера** | BLOCK / WARN / INFO с описаниями |
| **Макс. итераций** | 3, после чего — эскалация пользователю |
| **Иерархия ревьюера** | Tier ревьюера ≥ tier автора |

### Результаты ревью

| Уровень | Значение | Действие |
|---------|----------|----------|
| **BLOCK** | Критичные ошибки, блокирующие приёмку | Исправить до продолжения |
| **WARN** | Серьёзные замечания, желательно исправить | Исправить или обосновать отказ |
| **INFO** | Рекомендации, улучшения | Допустимо отложить |

---

## Review Gating (4 уровня)

| Уровень | Типы артефактов | Требование | Tier ревьюера |
|---------|-----------------|------------|---------------|
| **Full review** | Спеки, архитектура, интеграционные изменения, новые модули | Обязательное кросс-ревью | Premium |
| **Standard review** | Бизнес-логика, тесты, рефакторинг | Кросс-ревью | High |
| **Light review** | Мелкие правки <20 строк, исправления по ревью | Самопроверка + `check_syntax` | — |
| **No review** | Форматирование, комментарии, переименование переменных | Только автоматические проверки | — |

## Чек-листы по типу артефакта (ссылка на SPEC-001)

### Чек-лист спецификации (8 пунктов)

- [ ] Context описывает КТО имеет проблему и ЧТО не работает
- [ ] Каждое MUST имеет соответствующий тест в Test Plan
- [ ] Scope явно указывает Out of scope
- [ ] Considered Options содержит минимум 2 альтернативы
- [ ] Decision имеет чёткое обоснование
- [ ] Technical Design разделяет метаданные (пользователь) и код (агент)
- [ ] Нет противоречий между разделами
- [ ] Нет неоднозначных требований — использованы RFC 2119

### Чек-лист архитектуры (5 пунктов)

- [ ] Описаны границы компонентов и их ответственность
- [ ] Зависимости между компонентами явные и обоснованные
- [ ] Учтены риски масштабирования и производительности
- [ ] Решение согласовано со спецификацией
- [ ] Альтернативы рассмотрены и обоснован отказ

### Чек-лист BSL-кода (6 пунктов)

- [ ] Код соответствует coding-standards
- [ ] Нет антипаттернов из bsl-practices/anti-patterns
- [ ] Обработка ошибок следует error-handling
- [ ] Запросы соответствуют query-patterns
- [ ] Формы соответствуют form-patterns (если применимо)
- [ ] Использованы БСП-функции где уместно (ssl-patterns)

### Чек-лист тестов (5 пунктов)

- [ ] Покрытие MUST-сценариев из спецификации
- [ ] Есть positive и negative тесты
- [ ] Учтены граничные случаи
- [ ] Тесты изолированы и не зависят от порядка выполнения
- [ ] Имена тестов отражают проверяемый сценарий

---

## Исключения

- В **свободном режиме** (без full-cycle workflow) кросс-ревью опционально
- Light review и No review — агент выполняет самопроверку через `check_syntax` без отдельного агента-ревьюера
- Пользователь может явно отключить ревью для конкретной задачи
