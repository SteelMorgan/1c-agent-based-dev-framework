# Тесты не оставляют следов (zero-residue)

> **Триггер:** проектирование, написание или ревью ЛЮБОГО автотеста на искусственных данных (см. «Область действия») (YaxUnit unit, серверный YaxUnit-хелпер «Vanessa-перехват», Vanessa `.feature`, интеграционный, сквозной), который создаёт/изменяет/записывает объекты в БД. Применяется ко ВСЕМ видам автотестов на искусственных данных. При срабатывании — применить навык `test-writing` (`framework/skills/bsl-practices/test-writing/SKILL.md`) и соответствующий механизм изоляции: `yaxunit-isolation` для YaxUnit, `vanessa-test-isolation-policy` для Vanessa.

## Область действия (что считается «тестом» для этого правила)

**Касается** только тестов на **заведомо искусственных данных**, созданных самим тестом или его фикстурами: YaxUnit (unit, интеграционные, серверные хелперы), Vanessa `.feature`, сквозные автотесты с генерируемыми объектами. Эти данные не должны переживать прогон.

**НЕ касается** живых функциональных прогонов: ручной или агентской работы через штатный интерфейс системы с реальными операциями на тестовом/демо-контуре внешней системы (демо-счёт биржи, песочница платёжного шлюза и т.п.). Это реальная работа: созданные ею документы, операции, позиции и движения регистров сохраняются как история и **не зачищаются**; дельта-0 к ним не применяется. Возвращать внешнюю систему в исходное состояние (закрыть позиции, отменить хвосты) нужно только если это требуется следующему прогону, и тем же штатным путём.

Не расширяй правило на живые прогоны: зачистка реальных операций уничтожает историю, на которой проверяются отчёты и учёт.

**GUARD:** тест, оставивший после прогона данные в боевой базе, НЕ принимается (Reviewer BLOCK) — даже если «зелёный».

## Принцип

Мусор, оставшийся в базе после прогона тестов, — это **ошибка**, а не мелкая неаккуратность и не «издержки тестирования». Его нельзя списывать на особенности механизма изоляции, на «потом вычистим руками» или на то, что тест при этом зелёный: ручная дочистка базы человеком означает, что тест спроектирован неправильно. Ответственность за нулевой след лежит на авторе теста, а не на том, кто потом наводит порядок.

Тест, накапливающий хвосты, засоряет реальные данные, ломает другие тесты (регламенты выбирают тестовые объекты → таймауты; идемпотентность видит чужие прогоны как дубли) и маскирует деградацию базы. Чистка постфактум — симптом; корень — отсутствие teardown в АРХИТЕКТУРЕ теста. Это закладывается в архитектуру каждого теста, а не делается разовой уборкой.

**Если что-то мешает гарантировать отсутствие мусора — это не повод замолчать и продолжить.** Ограничение механизма изоляции, конфликт с production-гвардом, конкурентный писатель, объект, который штатным способом не удаляется, — любая такая помеха фиксируется явно (видимая запись уровня Ошибка + запись в контексте роли) и эскалируется владельцу фазы/пользователю вместе с предложением решения. Молча сдаться и оставить хвост, обойти проблему скрытием объекта от выборок или «зазеленить» тест поверх невывезенной уборки — запрещено.

## MUST (инвариант, всегда)

| Требование | Описание |
|-----------|----------|
| Нулевой след | Дельта количества по КАЖДОМУ затронутому справочнику / регистру / документу / набору записей до и после прогона = **0** |
| Механизм изоляции обязателен | YaxUnit — `.ВТранзакции()` (откат) ИЛИ явный teardown `.После()` при допустимом исключении (см. `yaxunit-isolation`). Vanessa и серверные хелперы вне транзакции — физическая зачистка созданного, устойчивая к падению Act/Assert |
| Объекты — трекаемо | Справочники создавать через `ЮТест.Данные()` (автотрекинг + автоудаление по `.УдалениеТестовыхДанных()`), а не `Справочники.X.СоздатьЭлемент()` мимо трекинга |
| Физическое удаление нетрекаемого | То, что не чистится транзакцией/автотрекингом (документы через `Документы.X.СоздатьДокумент()`, объекты из хелперов, объекты из `КонструкторОбъекта().Записать()`) — удалять физически: `ОбменДанными.Загрузка = Истина` + `Удалить()`, в порядке зависимые → владелец; не пометка на удаление |
| **Коллектор обязателен** | Тест, генерирующий данные, ОБЯЗАН регистрировать КАЖДЫЙ созданный объект в коллекторе тестовых объектов В МОМЕНТ создания; teardown (`.После()` / финальный шаг сценария / `ПослеВсехТестов`) проходит по коллектору и физически удаляет всё, что пережило откат транзакции. Работает ДАЖЕ если Act/Assert упали. Деталь механизма — навык `test-writing` («Коллектор тестовых объектов») |
| **Запрет молчаливого проглатывания ошибки удаления** | Дренаж/teardown коллектора НЕ имеет права молча проглатывать ошибку `Удалить()`. Удаление штатно может упасть на конфликте версии (optimistic-lock: объект конкурентно перезаписан подпиской/фоновым заданием между чтением и удалением) → ОБЯЗАН повторить с повторным свежим `ПолучитьОбъект()` (ограниченное число попыток), повторяя ТОЛЬКО на конфликте версии. Если после повторов объект не удалён ИЛИ ошибка не-конфликтная — записать в журнал регистрации запись УРОВНЯ Ошибка (НЕ Предупреждение) с типом+ссылкой неудалённого остатка и продолжить дренаж остальных ссылок (не прерывать дренаж исключением — иначе осиротит остальное). Ошибка удаления, погашенная в `Попытке` без видимого следа уровня Ошибка = невидимая утечка, которую приёмка дельта-0 по ЖР не ловит |
| **Любой отказ звена цепочки уборки — видимый** | Нулевой след держится цепочкой «объект создан → объект взят под учёт teardown → объект удалён». ЛЮБОЕ звено, которое отказало или отработало вхолостую (объект не взят под учёт; условие уборки не выполнилось; защитная проверка отфильтровала объект и вышла), ОБЯЗАНО оставить видимый след уровня Ошибка с типом/идентификатором объекта. Тихий выход из служебной процедуры уборки по защитной проверке запрещён: объект, не взятый под учёт, гарантированно станет остатком, а без следа дефект существует только в рантайме и не виден ни ревью по коду, ни зелёному прогону |
| **Помеха уборке — эскалация, не умолчание** | Обнаружено ограничение, из-за которого нулевой след не гарантируется (механизм изоляции неприменим, конкурентный писатель, объект не удаляется штатным способом) → зафиксировать в контексте роли, доложить владельцу фазы/пользователю и искать решение. Оставить хвост, скрыть его или сдать тест зелёным поверх нерешённой проблемы — запрещено |
| Сквозной тест — шаг-зачистка | Если данные обязаны жить во время прогона (end-to-end) — единственное исключение, и тест ОБЯЗАН завершаться явным шагом, удаляющим всё созданное (через коллектор) |
| Приёмка = дельта-0 | Проверка дельты ключевых объектов до/после — часть приёмочного критерия фазы; ненулевая дельта = тест не принят |
| Запрет band-aid | Скрытие созданного от выборок/регламентов (флаг-исключение объекта, спец-префикс-фильтр) НЕ засчитывается как зачистка — объект должен быть удалён физически |
| Запрет хрупких селекторов | Зачистка перебором базы по ИМЕНИ/префиксу/регекспу («удалить всё `ПОДОБНО "Тест%"`», смешение алфавитов) НЕ является основным механизмом teardown: ложно-широкий отбор рискует снести боевые данные, ложно-узкий — оставляет хвост. Допустима ТОЛЬКО как разовый сметатель уже накопленного исторического мусора, не как штатный teardown теста. Штатный teardown — коллектор (точные ссылки) |

## Связь с механизмами

- `yaxunit-isolation` — КАК изолировать серверный YaxUnit-тест (`.ВТранзакции()`, допустимые исключения, teardown `.После()`). Это правило задаёт ИНВАРИАНТ (дельта-0), то правило — механизм.
- `vanessa-test-isolation-policy` — изоляция Vanessa-сценариев (создание своих объектов). Усиливается требованием физической зачистки до нуля.
