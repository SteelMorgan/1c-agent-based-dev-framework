# Политика TDD (Test-Driven Development)

> RULES — обязательные политики, ограничивающие поведение агента. Тесты пишутся до реализации, а не после.

---

## Назначение

Это правило обеспечивает качество и предсказуемость кода за счёт дисциплины TDD.

**Ключевой принцип:** тесты и реализация пишутся **разными агентами** в **разных фазах**. Порядок фаз (сначала тесты, потом код) обеспечивается **оркестратором**, а не самими агентами. Это исключает конфликт интересов: автор тестов не знает реализацию, автор кода не модифицирует тесты.

```
Оркестратор управляет порядком:
  Phase 3a: Developer-Tests → пишет тесты по спеке (Red)
  Phase 3b: Developer-Code  → пишет код чтобы тесты прошли (Green)
  Phase 4:  Tester          → дополняет edge cases и регрессию
```

---

## Условия срабатывания

Правило применяется, когда агент:

- Реализует новую функциональность с бизнес-логикой
- Вносит изменения в протестированные модули
- Исправляет баги в коде с существующими тестами
- Работает по full-cycle workflow с утверждённой спецификацией

---

## Требования

### MUST (обязательно)

| Требование | Описание |
|------------|----------|
| План тестов в спецификации | Тест-план MUST быть описан в спецификации ДО написания кода |
| Тесты до реализации | YaxUnit-тесты для MUST-сценариев MUST быть написаны ДО реализации бизнес-логики |
| Цикл Red → Green → Refactor | Соблюдать порядок: сначала RED (тест падает), затем GREEN (минимальный код), затем Refactor |
| Ревью тестов | Тесты MUST быть проверены другим агентом (покрытие против спеки) |
| Повторный прогон после исправлений | После исправления замечаний ревью — запустить ВСЕ затронутые тесты |

### SHOULD (настоятельно рекомендуется)

| Требование | Описание |
|------------|----------|
| Тесты для SHOULD-сценариев | Тесты для SHOULD-приоритетных сценариев SHOULD быть написаны после базовой реализации |

### MAY (допустимо)

| Ситуация | Описание |
|----------|----------|
| UI-only изменения | Тесты MAY быть пропущены |
| Изменения конфигурации | Тесты MAY быть пропущены |
| Документация | Тесты MAY быть пропущены |

---

## TDD Workflow

```
1. Прочитать спецификацию → выявить тест-сценарии из Test Plan
2. Написать тест-модуль → выполнить run_tests (тест RED — падает)
3. Реализовать минимальный код для прохождения теста
4. Запустить run_tests → убедиться в GREEN
5. Рефакторинг (если нужен)
6. Запустить run_tests снова → остаётся GREEN
7. Выполнить check_syntax
```

---

## Требования к тестам

- Тесты MUST вызывать `run_tests` после изменений
- Тест MUST падать до реализации (Red) — иначе сценарий уже покрыт или тест некорректен
- После исправления замечаний ревью — MUST перезапустить все затронутые тесты
- Ревьюер проверяет: соответствие тестов Test Plan, покрытие MUST-сценариев, граничные случаи

---

## Исключения

- Изменения только UI (формы, оформление) — тесты не обязательны
- Конфигурационные изменения (реквизиты, метаданные без кода) — тесты не обязательны
- Документация, комментарии — тесты не обязательны
- Quick-fix для простых задач — допустимо писать тест после исправления, если время критично (с пометкой в отчёте)

## Граница ответственности: Developer vs Tester

Developer и Tester не конкурируют — они покрывают **разные слои** тестирования.

### Developer пишет тесты **изнутри** (знает реализацию)

| Что покрывает | Описание |
|---------------|----------|
| Unit-тесты на каждый публичный метод | Red→Green→Refactor для каждого реализуемого метода |
| MUST-сценарии из Test Plan | Основные позитивные пути, описанные в спецификации |
| Базовые негативные случаи | Очевидные ошибки входных данных, предусмотренные спецификацией |

Developer **не обязан** покрывать: комбинаторные edge cases, интеграционные сценарии между модулями, регрессию по смежным подсистемам — это зона Tester.

### Tester пишет тесты **снаружи** (знает только спецификацию)

| Что покрывает | Описание |
|---------------|----------|
| Edge cases | Граничные значения, нетипичные комбинации входных данных |
| Негативные сценарии | Некорректные данные, нарушения бизнес-правил |
| Интеграционные тесты | Взаимодействие между модулями и подсистемами |
| Регрессионные тесты | Защита от поломки смежной функциональности |

Tester **не дублирует** тесты Developer — сначала анализирует что уже покрыто, затем дополняет.

### Правило при падении теста у Tester

```
Тест упал
    │
    ├── Это ошибка в тесте?  →  ДА  →  Tester исправляет тест, перезапускает
    │                                   (метка test_error — оркестратор не вмешивается)
    │
    └── Это баг в коде?      →  НЕТ →  СТОП. Tester НЕ правит BSL-код.
                                        Tester сигнализирует оркестратору (метка implementation_error):
                                        - какой тест упал
                                        - что ожидалось
                                        - что получено фактически
                                        Оркестратор возвращает задачу Developer.
```

> Сабагенты не общаются напрямую. Tester не вызывает Developer —
> он завершает работу с меткой `implementation_error`, и оркестратор
> принимает решение о повторном запуске Developer.
> См. [orchestrator.md](../workflows/orchestrator.md) → раздел 3.
