# Раскладка памяти и работа с RLM

> Два слоя памяти с разной моделью загрузки. Native — push (всегда в контексте), RLM — pull (достаётся по запросу). Не путать назначение.

## Раскладка (GUARD)

| Знание | Куда | Почему |
|---|---|---|
| Маленькое, нужно **каждый ход**, критичное: безопасность, инварианты, стоячие предпочтения, указатель активной задачи | **native** (`MEMORY.md` + `memory/*.md`) | push — висит в контексте всегда, переживает компакт даром |
| Универсальное, переиспользуемое, **растущее**, детальное: паттерны/антипаттерны, арх-решения с альтернативами, устойчивые домен-факты 1С/БСП, находки по модулям | **RLM** (pull) | НЕ должно висеть в контексте; достаётся по теме семантическим поиском |
| Transient состояние задачи: PENDING, следующий шаг, WIP | `task_dir/.context/*.md` (agent-context) | живёт в задаче, не в памяти |

**GUARD:** универсальные знания НЕ держать в native/контексте постоянно (раздувает каждый старт). Transient — НЕ в RLM.

## TRIGGER — ЗАПИСАТЬ в RLM

- Узнал переиспользуемый паттерн/антипаттерн (после ≥2 итераций, см. `skill-learning`)
- Принял архитектурное решение с альтернативами
- Нашёл устойчивый домен-факт (поведение платформы/БСП), значимый за пределами текущей задачи

→ применить навык `rlm-workflow` (как писать: tool, level, causal-решение).

## TRIGGER — ПРОЧИТАТЬ из RLM (на границе работы, НЕ каждый ход)

- Начинаешь нетривиальную задачу или арх-решение в домене D
- Упёрся в проблему, которая пахнет повторяющейся (ошибка, интеграционная особенность)

→ один `rlm_enterprise_context(query=<домен/симптом>)` ДО проектирования/реализации. Детали — в навыке.

> Параллель: `search-before-write` проверяет существующий **код**; этот триггер — существующее **знание**. Триггер фазовый: на входе в работу, иначе pull вырождается в push.

## MUST (инвариант, всегда)

- Любая запись в RLM — только после `rlm_start_session` (иначе молчаливый провал).
- Универсальное знание пишется в RLM, НЕ дублируется в native always-on ядро.
