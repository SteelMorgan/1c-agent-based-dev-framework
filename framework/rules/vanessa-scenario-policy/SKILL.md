# Политика сценариев Vanessa Automation

> **Триггер:** создание или изменение `.feature`-файла. При срабатывании — применить навык `vanessa-authoring` (`framework/skills/tool-usage/vanessa/vanessa-authoring/SKILL.md`).

## Назначение слоёв тестирования (MUST — фундаментальное)

> Сценарный (Vanessa) тест существует, чтобы проверять **клиентское поведение через UI, имитируя действия пользователя**. Это его прямое назначение. Серверная бизнес-логика — зона **юнит-тестов** (YaxUnit). Путать слои нельзя: серверный тест в обёртке Vanessa не проверяет то, ради чего сценарные тесты нужны.

| Что проверяем | Каким тестом |
|---------------|--------------|
| Серверная/бизнес-логика: проверка заполнения (`ОбработкаПроверкиЗаполнения`), проведение, расчёты, запросы, регистры, регламенты | **Юнит (YaxUnit)** |
| Клиентское/UI-поведение: открытие формы, `ПриСозданииНаСервере`/`ПриОткрытии`, видимость/доступность/обязательность элементов, реакция на ввод (`ПриИзменении`), команды формы, навигация, ввод на основании | **Сценарный (Vanessa) через UI** |

- **Проверяемое поведение идёт ТОЛЬКО через UI.** Сценарий открывает форму и имитирует пользователя реальными UI-шагами (`открылось окно`, `в поле с именем … я ввожу`, `я нажимаю … кнопку`, `я вижу элемент`, `элемент … доступен`). **ЗАПРЕЩЕНО** подменять путь пользовательского действия серверным вызовом (`ПроверитьЗаполнение()`, `ЗаписатьОбъект()`, прямой вызов общего модуля) — такой «сценарий» является юнит-тестом в костюме Vanessa и пропускает дефекты слоя формы.
- **Серверный BSL в Vanessa допустим ТОЛЬКО для подготовки/уборки данных** (фикстуры, сетап, teardown — см. двухсессийный сплит ниже), НЕ как замена проверяемого пользовательского сценария. Граница: код «готовит сцену» — можно серверно; код «проверяет поведение» — только через UI.
- **Зачем правило.** Если сценарий вызывает серверную логику вместо открытия формы, **вся клиентская логика остаётся без тестирования вообще** — её не покрывает ни сценарий (обошёл UI), ни юнит-тест (это не его слой). Без проверки оказываются: клиентские обработчики (`&НаКлиенте`, `ПриОткрытии`, `ПриИзменении`, обработчики команд), клиент-серверные вызовы формы (`ПриСозданииНаСервере` и пр.), условное оформление, видимость/доступность/обязательность элементов, реакция на ввод и навигация, структура самой формы. Итог — серверная валидация зелёная, а форма в runtime падает (битая структура формы, необработанное событие, неверная видимость — например «Поле объекта не обнаружено»), и это всплывает только у пользователя. Клиентскую логику проверяет ТОЛЬКО сценарий, реально открывающий форму и имитирующий пользователя (`создать → открылось окно → я вижу элемент … / ввожу / нажимаю`).

## MUST

- Сценарий опирается на спецификацию задачи или существующий бизнес-кейс — без вымышленных кейсов.
- Один сценарий = одно наблюдаемое поведение.
- Перед новым шагом — искать существующий в библиотеке Vanessa и сценариях проекта.
- Первый сценарий для нового кейса — короткий smoke.
- Сценарий выполняется под конкретным **бизнес-пользователем**, а не под admin/AgentAI — исключение только если проверяемая функция доступна исключительно администратору; пользователь определяется из описания задачи, при отсутствии — **спросить у человека**.
- **Двухсессийный сплит:** инфраструктурная подготовка данных (создание объектов, VAExtension-шаги, BSL-фикстуры) — под техническим пользователем (AgentAI); бизнес-поток (проверка поведения) — под конкретным бизнес-пользователем. Переключение через `И я закрываю TestClient` + новый `Дано я подключаю TestClient`. Нельзя выдавать бизнес-пользователю технические роли ради прохождения инфраструктурных шагов.
- **Тег задачи обязателен.** Каждый `.feature`-файл MUST содержать тег `@task-<ID>` (например `@task-103`) на уровне `Функциональность:`.
- **Комментарий-источник.** В шапке файла (перед тегами) MUST быть комментарий: `# Задача: <ID> — <название>`.
- Не гадай логику — читай код (делегируй Explorer / `code-navigation`). Расхождение кода и теста — это найденное несоответствие, фиксируй как результат.
- **Не гадай интерфейс** — имена и заголовки элементов, поля, кнопки, закладки, доступность и состояние элементов берутся из **реального отрендеренного интерфейса**, исследованного через веб-клиент (`gui-control` / `screenshot` / `chrome-devtools`-snapshot), а не из догадок по коду или памяти. Помни о разнице идентификаторов: шаги «содержит строки» / «перехожу к строке» ждут **заголовок (Title)**, «запоминаю значение поля» ждёт **имя (name)** — точное значение узнаётся осмотром формы, не угадывается. Расхождение сценария и реального UI — найденное несоответствие, фиксируй как результат.
- **Ручное заполнение перед сценарием.** Новый сценарий по документу пишется ПОСЛЕ ручного заполнения формы в веб-клиенте со сверкой состава формы **на каждом шаге** (значение поля влияет на видимость/обязательность других полей); ключевые поля шапки и обязательные ТЧ (≥ нескольких строк) заполнены; Подсказка/справочные данные документа изучены; учтены полосы прокрутки, скрывающие поля. При необходимости по смыслу теста — документ **записан и проведён**, всплывающие ошибки внизу экрана разобраны и заполнение скорректировано. Сценарии заполнения — переиспользуемые «кубики» (`@exportscenarios`), один документ может иметь несколько. Детали — `vanessa-authoring`.
