## 3. Оценка методологии (задача 3)

### 3.1. Что совпадает с зрелыми практиками агентной разработки

| Механизм фреймворка | Индустриальный аналог / практика |
|---|---|
| Spec-first + два approval-gate (Phase 1, 2) до дорогих фаз | SDD/RFC-driven development; human-in-the-loop в самой дешёвой точке отката — это правильнее, чем ревью готового кода |
| Red→Green с раздельными авторами тестов и кода (3b vs 3d) | классика TDD, усиленная против главного LLM-риска — self-fulfilling tests (автор кода не подгоняет тесты) |
| Разделение 3a (intent-Gherkin) / 3c (step-реализация) | аналог «three amigos»/SbE: бизнес-намерение отделено от инженерии шагов; главный практический выигрыш — чистый Red-гейт и ответственный за reuse step-library |
| source-of-truth L1→L6, запрет бинарного «виноват тест/код» | структурный RCA; прямо бьёт по документированному LLM-байасу «чинить тест под кривой код» |
| Reviewer tier ≥ author tier | стандартная рекомендация LLM-as-judge |
| Cross-provider review (advisory + gate с evidence pack и anti-deception чек-листом) | ансамблевое судейство разными семействами моделей; gate-режим с обязательными сырыми stdout — сильная защита от test theater / fake acceptance, встречается редко и это конкурентное преимущество фреймворка |
| Ретиринг: durable-профиль / read-on-choice механика / тонкие rules-триггеры | progressive disclosure (Anthropic Skills), правильная экономика контекста |
| bug-report контракт (`expectation.quote`, `self_fix_attempts`) + лимиты самовосстановления | анти-šум и предотвращение бесконечных self-fix циклов |
| Health-check фоновых сабагентов 5→10→15 мин + «две проверки без прогресса → stop» | production-практика оркестрации; редко формализуется — здесь формализовано |
| learned-patterns с «тестом абстракции» (урок = класс ошибки) | post-mortem культура, перенесённая на агентов |

Итог: методология **зрелая, выше типичного уровня** публичных мультиагентных фреймворков. Главные проблемы найдены не в дизайне, а в **синхронизации документов между собой** (см. §5).

### 3.2. Существенные риски и расхождения

1. **Противоречие о параллельности 3a/3b.** `full-cycle/SKILL.md` требует «строго последовательно 3a→3b→3c→3d», а ASCII-диаграмма `orchestrator-structures.md` показывает 3a∥3b. Артефакты фаз независимы (Gherkin vs YaxUnit) — параллель легальна и экономит wall-clock. Зафиксировать одну норму (рекомендую: 3a∥3b, затем 3c→3d).
2. **Стоимость двойного ревью.** Advisory cross-provider на *каждый* артефакт + Reviewer — это 2 ревью × 7 фаз. Для simple-medium задач возможен risk-based режим (cross-provider только spec/arch/code, для bdd/tests — по триггеру). Решение бизнесовое: точность vs стоимость; сейчас выбрана точность — это валидно, но стоит сделать выбор явным в правиле.
3. **Три источника модельной маршрутизации** (README-таблица с конкретными моделями, orchestrator §2 с тирами, прямое указание модели debugger в тексте §3a) — уже разошлись: README не знает scenario-coder/debugger, устаревшие имена моделей. Нужен один источник (рекомендую: таблица роль→tier в `agent-development-ext`, остальные ссылаются).
4. **Семь числовых лимитов самовосстановления** без общей таблицы (self-fix 2, Red-гейт 2, tester 3, debugger 5+3, BLOCK 3, debug-fix review 1, bug→fix→bug 2). Риск путаницы «какой лимит к чему». Одна сводная таблица-источник + ссылки.
5. **Методология не самотестируема.** Дисциплина держится на тексте; регрессии правил (например, дрейф нумерации фаз) ловятся вручную. knowledge-probe закрывает часть (знания); для консистентности документов напрашивается линтер перекрёстных ссылок (фазы/scope/лимиты) в pre-commit.

## 4. Шаблоны артефактов (задача 4) — только существенное

Общий вердикт: шаблоны **нагружены, а не декоративны** — почти каждое поле работает на следующую фазу или на Reviewer. Массовых правок не требуется. Существенных пункта три:

1. **Рассинхрон `done_criteria`.** Чек-лист `technical-design-standard` §6 требует у задач `done_criteria`, но схема/примеры `task-breakdown.json` этого поля не содержат. Это реальный контрактный дефект (developer-code полагается на JSON как контракт). → Добавить поле в схему task-breakdown (или убрать пункт из чек-листа TD).
2. **Два ADR-механизма.** spec-standard ведёт inline «Журнал решений (ADR)», technical-design-standard — файловый `task_dir/adr/*.md` (MADR). Как соотносятся — не определено: точка расхождения источника истины. → Одна норма: spec-ADR = только бизнес-решения уровня требований, файловый ADR = технические решения дизайна, с явной ссылкой между ними; или единый файловый механизм с этапом.
3. **JSON Schema для task-breakdown отсутствует** (формат «template + example»). Контракт, на который опираются три роли, заслуживает машинной валидации — schema + проверка в pre-commit/оркестраторе. Дёшево, сильно повышает надёжность.

Не трогать: spec-standard §4a/4b (выглядят тяжёлыми, но закрывают конкретные дорогие антипаттерны — дубль BDD поверх unit и тест не того слоя); Test Users анти-placeholder (предотвращает документированный провал «Не смог подключить TestClient <Сидоров>»); agent-context (6 полей, всё resume-критично); escalation-format (эталонно компактен).

## 5. Промты сабагентов (задача 5) — существенные промахи и улучшения

### 5.1. Дефекты консистентности (чинить в первую очередь — дёшево и опасно)

1. **Reviewer не знает scope `bdd-steps`.** full-cycle §3c и orchestrator предписывают «Ревью (scope=bdd-steps)», но в таблице маппинга reviewer.md такого scope нет — ни контекст-файла, ни чек-листа. Фаза 3c ревьюится «на глазок». → Добавить строку маппинга + чек-лист (Red-гейт критерии уже есть в scenario-coder — оттуда).
2. **Нет чек-листов BLOCK/WARN/INFO для scope=spec и scope=arch** — двух самых дорогих для отката артефактов (у bdd/tests/code/debug они детальные). Чек-листы уже существуют в spec-standard §7 и technical-design-standard — достаточно перенести ссылкой с пометкой уровней BLOCK/WARN.
3. **README сабагентов устарел:** не знает scenario-coder и debugger (2 из 12 ролей), использует старую нумерацию фаз (3c=Developer-Code против 3c=Scenario-Coder в orchestrator/scenario-coder/reviewer:47 «Phase 3c» у scope=code), в артефактах task_dir нет bugs/, debug/, reviewer-context-debug.md. → Перегенерировать README по факту; добавить в pre-commit проверку «каждый framework/subagents/*.md упомянут в README».
4. **`form-info`** упомянут в scenario-author.md, но не существует ни в skills:, ни в depends_on, ни на диске — битая ссылка на удалённый/переименованный навык.
5. **Неполнота `depends_on` против `skills:`** (architect −8, developer-code −7, reviewer −6 вкл. syntax-checking, debugger −3, explorer/tester −1). При полной установке не влияет (всё раскладывается по каноничным каталогам), но ломает выборочную установку и вводит в заблуждение читателя профиля. → Либо дополнить depends_on, либо научить install.py объединять skills: ∪ depends_on.

### 5.2. Структурные улучшения

6. **Блок «КРИТИЧНО: обязательное чтение навыков» (~20 строк) дословно в 10 профилях** — держится синхронно вручную. → Вынести в одно правило (`skill-learning-policy` или новое `skill-reading-protocol`), в профилях — одна строка-ссылка. Экономия ~180 строк и единая точка правки.
7. **Дубли содержания между профилями:** «Когда спрашивать» (analyst↔architect), «Coverage by runtime layer» (analyst шаг 7 ↔ tester шаг 3), BSL-security BLOCK-критерии (reviewer ↔ developer-code Границы), Red/Green TDD переформулирован трижды (developer-tests/scenario-coder/developer-code; tdd-policy в depends_on только у 2 из 4 TDD-ролей). → По каждому: канон в одном месте + ссылка; tdd-policy добавить в depends_on developer-tests и developer-code.
8. **Единая таблица лимитов самовосстановления** (см. §3.2 п.4) — в правило, профили ссылаются.
9. **orchestrator.md (660 строк ≈ 11–14k токенов durable каждый запрос)** сам нарушает собственный принцип «детальные процедуры не инлайнятся»: §3a bug-routing (~35 строк) и §7 cross-provider (~95 строк) — процедурная механика. → Вынести в references read-on-choice, в профиле — нормативный минимум (когда запускать, лимиты, кто решает). Цель ~400 строк без потери норм.
10. **Недоопределённости поведения** (точечно): developer-tests — что делать, если Red-тест *не падает* (частичная реализация уже есть) — некому заметить до 3d; developer-code шаг 7 — нет порога «тест завис»; tester — что считается «попыткой» (прогон или правка); debugger — процедура получения согласия на L7/L8 через оркестратора (таймаут?).
