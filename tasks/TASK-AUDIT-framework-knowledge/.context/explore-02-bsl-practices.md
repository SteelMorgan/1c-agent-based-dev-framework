## 1. api-design/SKILL.md (334 строки)

**purpose:** Классификация 5 категорий экспортных методов БСП (#Область) и правила обратной совместимости/версионирования API подсистем 1С.

**type:** 1c-доменное (конвенции БСП) с элементами общепрограммистского (API versioning как концепция).

**probe_facts:**
1. Экспортный метод обязан принадлежать ровно одной из 5 категорий: `ПрограммныйИнтерфейс`, `СлужебныйПрограммныйИнтерфейс`, `ПереопределяемыйИнтерфейс`, `ДляВызоваИзДругихПодсистем`, `СлужебныеПроцедурыИФункции` — секция «Классификация экспортных методов».
2. Добавление обязательного параметра в `ПрограммныйИнтерфейс` требует deprecated-обёртки со старой сигнатурой — секция «Правила обратной совместимости».
3. Устаревшие методы переносятся в `#Область УстаревшиеПроцедурыИФункции` с комментарием «Устарела. Используйте …()» — секция «Deprecated-области и миграция».
4. Bump `build`-версии допустим только для bug fix, расширение API запрещено — секция «Версионирование интерфейса».
5. `ПереопределяемыйИнтерфейс` не может получать новые обязательные процедуры/параметры после релиза — категория 3 классификации.
6. Вызов метода из `#Область СлужебныеПроцедурыИФункции` другой подсистемы — архитектурный дефект — «Типичные ошибки».

**verbosity:** med. Декоративная фраза-заявка: «Произвольный вызов через границы подсистем — это архитектурный дефект, а не удобный приём» (Назначение) — риторика без новой информации. Основная масса — конкретные таблицы/примеры кода.

**duplicate_of:** пересекается с `ssl-patterns` (упомянут как связанный навык, конвенции БСП), с `coding-standards` (структура `#Область`).

**verdict_candidate:** нужен как есть — точные русские названия 5 категорий БСП и таблицы допустимых/недопустимых изменений — узкое конвенциональное знание конкретной экосистемы БСП, маловероятно точно в весах.

## 2. background-jobs/SKILL.md (361 строка)

**purpose:** Паттерны идемпотентных фоновых/регламентных заданий 1С: захват задачи, mutex, checkpointing, retry-классификация.

**type:** 1c-доменное (платформенный API) + общепрограммистское (идемпотентность, retry/backoff, checkpointing — универсальные концепции job processing).

**probe_facts:**
1. Фоновое задание обязано выдерживать прерывание/перезапуск без потери данных и дублирования работы — «Ключевой принцип».
2. HTTP/внешний вызов внутри транзакции — антипаттерн: таймаут 30 сек = блокировка всей ИБ — «Запрещённые паттерны».
3. Батч = одна транзакция; checkpoint сохраняется в той же транзакции, что и полезная работа батча — Сценарий 3.
4. Ошибки делятся на retryable (сеть, 503, захват блокировки) и permanent (400/404, бизнес-правило); повторять нужно только retryable — Сценарий 4.
5. Mutex через `БлокировкаДанных` на константу/флаг защищает от параллельного запуска — Сценарий 2.
6. Стейл-лок без TTL — антипаттерн: задание не запускается после краша — «Правила дизайна заданий».

**verbosity:** low. Плотный, code-backed.

**duplicate_of:** канонический паттерн транзакций дословно повторяет `error-handling`; идемпотентность концептуально пересекается с `data-exchange`.

**verdict_candidate:** сжать (редакторски) — канонический паттерн транзакций (`НачатьТранзакцию/Попытка/...`) повторён здесь почти дословно из `error-handling`; заменить на отсылку вместо полного повтора кода. BSL-специфичный синтаксис (`БлокировкаДанных`, захват задачи, retry-классификация) — оставить как есть.
**weights-hypothesis (отдельно, для проб):** общие концепции retryable/permanent, checkpointing, mutex — вероятно известны модели как universal job-processing practice; это гипотеза для приоритизации проверочных вопросов, не основание для решения о сжатии выше.

## 3. coding-standards/SKILL.md (411 строк)

**purpose:** 19 конкретных правил BSL-кодстайла: именование, структура модуля/#Область, директивы компиляции, работа со строками, НСтр(), явные JOIN, magic numbers и др.

**type:** 1c-доменное (платформа/язык, стандарты ИТС) с частью общепрограммистских правил, обёрнутых в BSL-примеры.

**probe_facts:**
1. Конкатенация строк через «+» в цикле — O(N²); замена — `Массив` + `СтрСоединить()` — Правило 7.
2. `&НаСервереБезКонтекста` передаёт только параметры без сериализации контекста формы, в отличие от `&НаСервере` — Правило 3.
3. Локальные переменные не должны называться именами глобальных коллекций (`Документы`, `Справочники`, `РегистрыСведений` и т.д.) — затеняют менеджер — Правило 6.
4. Явные JOIN предпочтительнее точечной нотации через ссылки — иначе неявный JOIN ко всем таблицам составного типа — Правило 15.
5. `НСтр()` обязателен для всех пользовательских строк (локализуемость) — Правило 10.
6. `Выполнить()`/`Вычислить()` запрещены без крайней необходимости (аналог eval, невидимы для статического анализа) — Правило 13.
7. Формы открываются через `ОткрытьФорму()`, а не `ПолучитьФорму()` (не работает в управляемом интерфейсе) — Правило 16.

**verbosity:** low. Почти весь текст — конкретные правила с кодом; минимум декоративных фраз (единственная — «самодокументируемым» в Правиле 11).

**duplicate_of:** Правило 3 (директивы компиляции) почти дословно = `form-patterns` Rule 1; Правило 15 (явные JOIN) пересекается с `query-patterns`; Правило 18 явно отсылает к `error-handling`; Правило 19 — к `form-patterns`.

**verdict_candidate:** нужен как есть (редакторски) — сам файл не многословен, правила терсны и все content-backed примерами кода; нет пустых формулировок, которые стоило бы вычищать по чисто editorial-критерию.
**weights-hypothesis (отдельно, для проб):** Правило 9 («комментарии зачем, не что»), Правило 11 («одна процедура — одна ответственность»), Правило 14 (magic numbers) — формулировки общей software engineering-практики (не специфичной для BSL), кандидаты на проверку «модель и так это знает» независимо от 1С-контекста. BSL-специфичный синтаксис (директивы компиляции, зарезервированные имена коллекций, порядок `#Область`) — предполагаемо нишевое знание, кандидат на проверку с противоположной гипотезой (вероятно НЕ в весах). Обе гипотезы — материал для проб, а не сами по себе основание менять текст файла.

## 4. data-exchange/SKILL.md (473 строки)

**purpose:** Обмены данными 1С — РИБ/избирательный обмен БСП/КД2.0/КД3.0/EnterpriseData: регистрация изменений, идемпотентность загрузки, разрешение конфликтов, диагностика.

**type:** 1c-доменное (платформенный механизм `ПланыОбмена` специфичен для 1С).

**probe_facts:**
1. Обработчик `ПриЗаписи` обязан проверять `Источник.ОбменДанными.Загрузка` и выходить — иначе бизнес-правила сработают повторно при загрузке — Правило 2.
2. `УстановитьНомерОтправленного` фиксируется только после подтверждения доставки, не раньше — Правило 3.
3. Идемпотентность загрузки обеспечивается сравнением `НомерСообщения <= НомерПринятого` перед обработкой — Правило 4.
4. КД 3.0 использует BSL-правила и поддерживает EDT; КД 2.0 — устаревший XML-формат правил — Правило 7.
5. Регистрация изменений внутри обработчика загрузки создаёт бесконечный цикл обмена А→Б→А→Б — «Типичные ошибки».
6. Разрешение конфликтов должно быть явным (приоритет узла/дата/бизнес-правило); молчаливая победа последнего изменения недопустима — Правило 5.

**verbosity:** low-med.

**duplicate_of:** канонический паттерн транзакций в загрузке дублирует `error-handling`; явная связь с `background-jobs` (обмен часто в фоновом задании).

**verdict_candidate:** нужен как есть — специфика `ПланыОбмена`/EnterpriseData/КД2.0 vs 3.0 узкая и нишевая, малое покрытие в общем обучающем корпусе за пределами русскоязычного 1С-сообщества.

## 5. error-handling/SKILL.md (605 строк, крупнейший «правиловый» SKILL)

**purpose:** Канонический паттерн транзакций 1С (`НачатьТранзакцию/Попытка/ЗафиксироватьТранзакцию/Исключение/ОтменитьТранзакцию`), управляемые/пессимистичные блокировки, логирование, retry для внешних вызовов.

**type:** 1c-доменное (платформа) — ключевая специфика: 1С требует ручного управления транзакциями (в отличие от большинства ЯП с авто-commit/ORM).

**probe_facts:**
1. `НачатьТранзакцию()` должна идти непосредственно перед `Попытка` — ошибка между ними оставит транзакцию незакрытой — Правило 2.
2. `ЗафиксироватьТранзакцию()` — последняя операция перед `Исключение`; операция после неё не откатится при ошибке — Правило 2.
3. `ОтменитьТранзакцию()` — первая операция в `Исключение`; запись в ЖР — после отката (иначе лог теряется) — Правило 2.
4. Вложенный `НачатьТранзакцию()` не создаёт новую транзакцию, а увеличивает счётчик; `ОтменитьТранзакцию()` помечает всю транзакцию как отменённую вплоть до внешнего уровня — Правило 3.
5. `БлокировкаДанных` устанавливается ДО чтения данных — иначе race condition (два сеанса читают одно значение, оба списывают лишнее) — Правило 5.
6. `ЗаблокироватьДанныеДляРедактирования` — пессимистичная блокировка на уровне сервера 1С; `БлокировкаДанных` — управляемая блокировка на уровне СУБД — Правило 6.
7. `КраткоеПредставлениеОшибки()` — для пользователя, `ПодробноеПредставлениеОшибки()` — для ЖР (полный стек) — Правило 1.
8. Единый порядок блокировки ресурсов (по отсортированной ссылке) предотвращает deadlock — Правило 11.

**verbosity:** low. Плотные таблицы «Критические правила порядка» и «Неправильные варианты (ловушки платформы)».

**duplicate_of:** канонический паттерн транзакций повторяется дословно/почти дословно в `background-jobs`, `data-exchange`; `coding-standards` Правило 18 отсылает сюда.

**verdict_candidate:** нужен как есть, вероятно один из самых ценных файлов в наборе — не «модель и так знает». Общая идея «не глотай исключения, логируй перед пробросом» общепрограммистская, но точный порядок операций и «счётчиковая» природа вложенных транзакций 1С (где `ОтменитьТранзакцию()` на любом уровне отравляет фиксацию на внешнем) — специфичная и коварная платформенная семантика, которую типичная LLM не выведет из общих знаний о транзакциях SQL/ORM.

## 6. form-patterns/SKILL.md (466 строк, англ.) + references/learned-patterns.md (28 строк)

**purpose:** Паттерны клиент-серверного взаимодействия управляемых форм 1С — иерархия директив, `ДанныеФормыВЗначение`/`ЗначениеВРеквизитФормы`, события формы, notifications, типы данных клиент↔сервер.

**type:** 1c-доменное (платформа управляемых форм).

**Примечание:** SKILL.md написан по-английски — единственный такой файл среди всех 13 SKILL.md в bsl-practices (остальные на русском). Возможная непоследовательность языковой политики / кандидат на проверку через `tools/sync-skill.py --check` (не проверялось в рамках этой задачи).

**probe_facts:**
1. Порядок предпочтения директив: `&НаКлиентеНаСервереБезКонтекста` > `&НаСервереБезКонтекста` > `&НаСервере` > `&НаКлиенте` — Rule 1.
2. `РеквизитФормыВЗначение`/`ЗначениеВРеквизитФормы` обязательны для вызова методов объекта из контекста формы — данные формы не являются реальным объектом — Rule 3.
3. Забытый `ЗначениеВРеквизитФормы` после `РеквизитФормыВЗначение` — изменения теряются молча — Rule 3, typical mistake.
4. Модальные диалоги (`Предупреждение()`, `Вопрос()`) запрещены в веб-клиенте, заменяются `ОписаниеОповещения` — Rule 7.
5. `ТаблицаЗначений`/`ДеревоЗначений` НЕ передаются между клиентом и сервером напрямую — только через реквизиты формы — Rule 12.
6. Команда, изменяющая сохраняемые данные, обязана иметь `ИзменяетСохраняемыеДанные` — иначе форма не станет модифицированной — Rule 13.
7. **learned-patterns.md (кандидат, НЕ в весах):** локальная переменная в контекстном методе формы с именем зарезервированного свойства (`Параметры`, `Объект`, `Элементы` и т.п.) резолвится в read-only свойство формы — присваивание падает в рантайме («Поле объекта недоступно для записи»), при этом статика/LSP молчат; в `&НаСервереБезКонтекста` того же имени свободно.

**verbosity:** low.

**duplicate_of:** Rule 1 почти дословно = `coding-standards` Правило 3; Rule 13/14 пересекаются с `form-visual-requirements` и `metadata-object-design` (platform properties).

**verdict_candidate:** нужен как есть — платформенное поведение сериализации форм (`ДанныеФормыВЗначение`, ограничение типов клиент↔сервер, `ИзменяетСохраняемыеДанные`) узко специализировано, маловероятно в деталях в весах.

**learned-patterns.md — точно НЕ в весах:** единичный runtime-обнаруженный edge case («headless-форма внешней обработки под БСП, рантайм-прогон, 2026-06»), статус `candidate` (не подтверждено повторно), после cutoff модели по дате.

## 7. form-visual-requirements/SKILL.md (69 строк)

**purpose:** Чеклист визуальной проверки форм 1С — layout, подписи, удобство использования, platform properties.

**type:** смесь 1c-доменного (платформенные свойства форм) и общепрограммистского (UX-эвристики: выравнивание, группировка, обрезание текста — универсальный дизайн-здравый смысл).

**probe_facts:**
1. Горизонтальная прокрутка строго запрещена для основной области формы 1С — секция 3.
2. Ключевые поля (Наименование, Код, Дата) должны быть в левом верхнем углу — секция 3.
3. Для документов: Дата/Номер — вверху, Статус/Организация/Склад — в заголовке, итоги/комментарий/автор — внизу — секция 4.
4. Команда, меняющая сохраняемые данные, должна иметь `ИзменяетСохраняемыеДанные` — иначе форма не станет модифицированной даже при `ТолькоПросмотр` — секция 5.
5. На форме — не более одной основной команды по умолчанию — секция 3.

**verbosity:** med-high. Значительная часть — generic UX-чеклист («элементы выровнены по сетке, без эффекта лесенки», «подписи не должны обрезаться троеточием») — общий UI best practice, не специфичный для 1С; такие пункты можно найти в любом чеклисте UI-ревью.

**duplicate_of:** секция 5 (Platform Properties) почти дословно повторяет `form-patterns` Rule 13.

**verdict_candidate:** сжать (редакторски) — секции 1-3 многословны относительно информационной плотности: пункты вроде «элементы выровнены по сетке, без эффекта лесенки» и «подписи не должны обрезаться троеточием» — общее место, которое не требует отдельного bullet-а на файл; секция 5 (Platform Properties) дублирует `form-patterns` Rule 13 почти дословно — оставить только в одном месте.
**weights-hypothesis (отдельно, для проб):** общий UX-чеклист (секции 1-3) вероятно совпадает с general UI best practice, известной модели независимо от 1С; 1С-специфичные пункты (`ИзменяетСохраняемыеДанные`, `ПроверкаЗаполнения`, `ГруппаПользовательскихНастроек`, `ПутьКДаннымЗаголовка`) — кандидаты на проверку с противоположной гипотезой.

## 8. integration-patterns/SKILL.md (483 строки) + references/auth-schemes.md (218 строк)

**purpose:** HTTP/REST/SOAP-интеграции 1С — контракт-first, тонкий HTTP-сервис, retry, идемпотентность, аутентификация, версионирование интерфейса.

**type:** 1c-доменное (конкретный BSL API: `HTTPСоединение`, `WSПрокси`, `БезопасноеХранилище`) + общепрограммистское (idempotency key, retry policy, error taxonomy — универсальные integration patterns).

**probe_facts:**
1. Секреты хранятся только в `БезопасноеХранилище`, никогда в константах/реквизитах справочников — Правило 3.
2. HTTP-вызов внутри транзакции 1С — таймаут 30 сек = блокировка всех связанных записей — «Типичные ошибки».
3. `Idempotency-Key` в заголовке или `НомерВнешнего` с уникальным индексом защищают изменяющие операции от дублей — Правило 5.

## 11. query-patterns/SKILL.md (409 строк)

**purpose:** Базовые паттерны написания запросов 1С — параметризация, `ЕСТЬNULL`, виртуальные таблицы, временные таблицы, индексация, `ВЫРАЗИТЬ`, `ПО` vs `ГДЕ`.

**type:** 1c-доменное (язык запросов 1С — SQL-подобный диалект с нестандартным синтаксисом).

**probe_facts:**
1. Запрос в цикле — антипаттерн; замена — один запрос + `Соответствие` (пример из ТЗ дословно совпадает) — Правило 1.
2. `ЕСТЬNULL()` обязателен при LEFT JOIN — `NULL > 0 = Ложь`, необработанный NULL превращает LEFT JOIN в фактический INNER JOIN через фильтр — Правило 4.
3. Параметры виртуальных таблиц (`Остатки`/`Обороты`/`СрезПоследних`) должны передаваться внутрь функции, не в `ГДЕ` — иначе СУБД вычисляет по всем данным — Правило 5.
4. Условие в `ПО` фильтрует правую таблицу ДО соединения (LEFT JOIN сохраняется), условие в `ГДЕ` — ПОСЛЕ (LEFT JOIN превращается в INNER) — Правило 13.
5. `ВЫРАЗИТЬ(Поле КАК Тип)` ограничивает JOIN составного типа (напр. `Регистратор`) до одной таблицы вместо JOIN ко всем возможным типам — Правило 12.
6. `РАЗЛИЧНЫЕ` не должен маскировать лишний JOIN — правильная замена — подзапрос — Правило 11.
7. Порядок: сначала `Запрос.Текст`, затем `Запрос.УстановитьПараметр(...)` — Правило 14 review checklist.

**verbosity:** low — почти весь текст конкретные code-backed правила со ссылкой на стандарт ИТС.

**duplicate_of:** сильное пересечение с `query-optimize` (см. выше); Правило 15 `coding-standards` (явные JOIN) пересекается тематически.

**verdict_candidate:** нужен как есть (редакторски) — ядро-навык языка запросов 1С, правила терсны, content-backed примерами кода, без пустых формулировок; дублирование с `query-optimize` — см. п.10, решается на стороне query-optimize.
