# Аудит framework/rules/ — 40 файлов SKILL.md

Общий паттерн: подавляющее большинство `rules/*/SKILL.md` — тонкие **триггер-указатели** (frontmatter + 1 абзац
«Триггер: … При срабатывании — применить навык X») на полновесные навыки в `framework/skills/**`. Собственного
фактического содержания там немного. Небольшая группа файлов (`no-direct-db-access`, `no-manual-xml-edit`,
`predefined-elements`, `report-discovered-issues`, `test-zero-residue`, `yaxunit-isolation`, `semantic-code-comments`,
`tdd-policy`, `vanessa-scenario-policy`, `vanessa-test-isolation-policy`, `git-workflow`, `sdd-policy`,
`escalation-format`, `codex-subagent-orchestration`, `protected-paths`, `capability-resolution`,
`framework-bootstrap`, `rlm-workflow`, `skill-learning-policy`) несёт самостоятельный, не дублируемый в другом месте
текст.

**По корректировке оркестратора:** для КАЖДОГО файла ниже извлечено 2-4 проверяемых утверждения (probe_facts), включая
процессные и проектно-специфичные правила. Для каждого факта указана метка `expected_in_weights`:
`да` — общеизвестная практика, модель вероятно знает без файла; `частично` — общий принцип известен, но конкретные
числа/имена/пороги — нет; `нет` — чистая конвенция этого фреймворка, непроверяемая по общим знаниям. Формулировка
вопроса подобрана так, чтобы у модели БЕЗ доступа к файлу был шанс ответить из общих знаний. Пометка «не подлежит
пробе» оставлена только там, где в файле буквально нет ничего кроме голого списка путей/имён без какого-либо
обоснования.

## Сводка по expected_in_weights (по фактам, не по файлам) — ГИПОТЕЗА для приоритизации проб, не основание для правок

Важно: эта сводка — гипотеза о том, какие вопросы имеет смысл тестировать в первую очередь на разных моделях
(Sonnet/Haiku и т.п.), и НЕ является основанием для решения «сжать» или «удалить» файл. Решение по каждому файлу
принимается отдельно, по чисто редакторским критериям (verbosity/повторы/структурная необходимость — см. поле
`verdict_candidate` выше), а после эмпирического прогона проб — по матрице «вопрос × модель».

- Фактов с меткой **да** (общеизвестно, модель вероятно знает без файла): search-before-write GUARD, TDD Red-Green-Refactor, «не логируй секреты», «комментируй почему, не что», DRY/single-source для настроек, «1С работает через платформу, не через прямой SQL», базовая номенклатура метаданных 1С, `pg_stat_*`/`EXPLAIN ANALYZE`, БСП/SSL как факт существования, «не удаляй файлы без явного согласия», «test isolation/idempotency», «не расширяй scope молча». Эти факты — приоритетные кандидаты для эмпирической пробы «знает ли модель Х без файла»; результат пробы (не сама гипотеза) станет основанием для решений по контенту.
- Фактов с меткой **нет** (чистая конвенция фреймворка, не выводима без файла): почти все пути/имена файлов (`{role}-context.md`, `va-status.json`, `**/exts/YAXUNIT/**`, `vanessa-tests/features`), числовые пороги (health-check 5/10/15 мин, reuse-порог 80%, ≥2 итерации, <20 строк), конкретные API (`ЮТест.Данные()`, `ОбменДанными.Загрузка`, `$VarName$`), версионно-специфичный баг платформы 8.3.27 в `yaxunit-isolation`, критерии полей bug-report (`expectation.quote`, `self_fix_attempts`), архитектура RU/ENG-зеркала. Гипотеза: эти факты в весах отсутствуют — проба должна эмпирически это подтвердить; если подтвердится, это довод за то, что соответствующий файл/факт обязан остаться в контексте (отдельно от вопроса, водянисто ли он написан).
- Фактов с меткой **частично** — большинство: общий принцип предположительно известен модели, но конкретная реализация/порог/API — нет; для таких фактов проба должна разделить ответ на «общий принцип» (ожидаемо верный без файла) и «точную деталь» (ожидаемо неверную/отсутствующую без файла).
