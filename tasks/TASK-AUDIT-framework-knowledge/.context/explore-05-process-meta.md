## Кросс-находки (не по одному файлу)

- **Дублирование ADR-механизма.** `spec-standard` держит собственную секцию «Журнал решений (ADR)» внутри spec.md, а `technical-design-standard` определяет отдельный файловый ADR-каталог `task_dir/adr/*.md` (MADR 4.0 lean). Не описано явно, как соотносятся эти два места записи ADR — потенциальная точка расхождения источника истины.
- **Возможный дубль вне заданной области.** `framework/skills/other/find-skills/SKILL.md` содержательно почти идентичен `.claude/rules/find-skills.md` (правило верхнего уровня, упомянутое в системном промпте) — оба описывают один и тот же `npx skills find/add` workflow с allow-list-политикой. Нарушает собственный принцип фреймворка «одна норма — один источник истины» (`skill-drying` П1).
- **Несоответствие базового agent-development и реальной архитектуры.** `agent-development` (Anthropic base) описывает расположение сабагентов только как `.cursor/agents/`, но весь full-cycle/quick-fix ссылается на `framework/subagents/<role>.md` как реальный механизм ролей — база не покрывает фактически используемый путь.
- **Скелет retiering.** `framework/workflows/orchestrator/SKILL.md` явно документирует, что `full-cycle/SKILL.md` — НЕ always-on документ, а поднимается оркестратором «по входу в фазу» из его профиля (`framework/subagents/orchestrator.md`, вне текущей области чтения). Это объясняет, почему сам full-cycle компактен (108 строк) — тяжёлая дисциплина оркестрации живёт в профиле, а не здесь.
- **task-breakdown vs technical-design-standard рассинхрон полей.** Чек-лист `technical-design-standard` §6 требует у задач поле `done_criteria` («done_criteria проверяемы и конкретны»), но собственный шаблон/пример JSON в `task-breakdown/SKILL.md` этого поля не содержит (только `task_id/task_type/title/description/depends_on/spec_refs/deliverables`) — недоопределённость между двумя нормативными файлами.

## Шаблоны артефактов

### 1. Спецификация (`spec.md`, spec-standard)

Секции: Контекст и постановка проблемы → Требования (RFC 2119: MUST/SHOULD/MAY/MUST NOT) → Границы
(входит/не входит в scope) → Рассмотренные варианты → Выбранное решение → Технический дизайн (кратко:
объекты метаданных/модули/поток данных) → План тестирования (TDD) с обязательной подсекцией **Test
Users** (запрет placeholder-имён, обязательны логин+роли+источник) → §4a Недублирование уровней теста
(критерий «дубль 1-в-1» vs «расширяет слой») → §4b Покрытие по runtime-слою (таблица: что затронуто →
обязательный тип теста) → Приёмочные сценарии (Gherkin) → Открытые вопросы → Журнал решений (ADR).
Чеклист ревью — 13 пунктов.

**Оценка:** сбалансирован. Секции 4a/4b выглядят как потенциальный оверхед, но по факту закрывают
конкретный наблюдавшийся антипаттерн (дублирующий BDD поверх unit, тест не того runtime-слоя) —
работают на Reviewer (Phase 1) и на Developer-Tests/Scenario-Author (Phase 3a/3b) напрямую через
трассировочную строку «требование → слой → тип теста → new/existing». Балласт: секция «Журнал решений
(ADR)» частично дублирует отдельный ADR-механизм technical-design-standard.

### 2. Технический дизайн (`technical-design.md`, technical-design-standard)

Заголовок-таблица (ссылки на spec/Explorer/decomposition/ADR-каталог) → 10 секций с
MUST/SHOULD/Conditional MUST маркировкой (§1 Обзор: цели/не-цели/предыстория/ограничения; §2 Стратегия;
§3 Структурные блоки — C4 L1-L3 + интерфейсы-контракты BSL-сигнатур; §4 Данные и метаданные — таблица
объектов + правило JSON DSL для сложных объектов (формы/SKD/роли) в `artifacts/`; §5 Сквозные концепции
— таблица аспект→решение→обоснование; §6 Ключевые решения — таблица + отдельные ADR-файлы формата MADR
4.0 lean; §7 Риски и недостатки; §8 Допущения/открытые вопросы; §9 Миграция и откат — Conditional MUST;
§10 Трассируемость — матрица Requirement→Section→TaskID). Чеклист ревью — самый длинный в выборке (~30
пунктов по 8 под-блокам).

**Оценка:** перегружен по объёму (391 строка, самый длинный SKILL.md всей области), но структурно не
избыточен — правило «неприменимо → указать N/A с причиной» защищает от формального разбухания на
простых задачах. Работающие поля: матрица трассируемости §10 (прямой вход для Reviewer и для проверки
задач в task-breakdown.json), таблица §5 сквозных концепций (закрывает типовые для 1С развилки: клиент/
сервер, БСП vs своё). Недоопределённость: чеклист требует `done_criteria` у задач, но JSON-шаблон
task-breakdown это поле не описывает (см. кросс-находки).

### 3. Task Breakdown JSON (task-breakdown)

Поля: `task_id`, `task_type` (`analysis|design|implementation|test`), `title`, `description`,
`depends_on`, `spec_refs`, `deliverables`. Два режима: **Linear** (self-check вместо ревью, для
one-shot/single-agent исполнения) и **Subagent** (Architect формирует → Reviewer cross-review → BLOCK-
цикл ≤ 3 итерации → эскалация при исчерпании). Оба режима — с полным примером JSON и чеклистом.

**Оценка:** недоопределён по одному пункту (`done_criteria` — см. выше), в остальном сбалансирован:
минимальный набор полей, каждое line-item в чеклисте нетривиально (`depends_on` без циклов, `spec_refs`
привязка к разделам, а не «на глаз»).

### 4. Agent Context (`{role}-context.md`, agent-context)

Секции: Status (`completed|clarification_needed|implementation_error`) → Completed Steps → Findings →
Assumptions → Pending Questions (только при clarification_needed) → User Answers (заполняет
оркестратор). Явный запрет: не включать полное содержимое файлов, промежуточные рассуждения, данные из
других артефактов задачи.

**Оценка:** сбалансирован, минимален. Все поля работают на resume/handoff — ничего лишнего для сжатия.

### 5. Escalation Format (escalation-format)

Что (1 предложение) → Почему это проблема (с `file:line`/REQ-ID) → Варианты (≥2, буквенная нумерация) →
Оценка каждого варианта (плюсы/минусы/влияние на артефакты, включая затраты) → Рекомендация (или явное
«выбор за пользователем»). Плюс правило группировки при нескольких проблемах.

**Оценка:** сбалансирован, эталонно компактен (57 строк) для формата с высокой поведенческой нагрузкой —
каждое поле напрямую предотвращает конкретный анти-паттерн («один вопрос без контекста»).

### 6. Full-cycle — передача артефактов (сводная таблица, а не форма)

Таблица «От→К: артефакт» (explorer-context.md → spec.md → TD+task-breakdown.json → .feature →
test-модули → BSL+.feature+зелёные тесты) + отдельная строка «обязательные поля» на каждый тип
артефакта (Spec: Context/Requirements/Scope/Test Plan; TD: компоненты/интерфейсы; Task Breakdown JSON:
task_id/task_type/depends_on/spec_refs/критерии завершения; Код: coding-standards; Тесты: связь с
MUST-сценариями).

**Оценка:** не шаблон в смысле формы документа, а компактный индекс минимально необходимых полей —
удобен как быстрый чек, ничего лишнего.

**Не найден в этой выборке:** отдельный шаблон bug-reporting (лежит вне заданной области —
`framework/skills/tool-usage/diagnostics/bug-reporting/`).

## Скелет методологии (full-cycle)

**Классификация:** Explorer (Economy) исследует кодовую базу → orchestrator (Lead-слой) решает
простая→`quick-fix` skill / средняя-сложная→Phase 1. Explorer-context передаётся в Phase 1 и 2.

**Phase 1 — Анализ.** Analyst (Mid/High) пишет `spec.md` (MADR 4.0 + RFC 2119) из задачи +
explorer-context. Reviewer (Premium) ревью, ≤3 BLOCK-итерации → иначе эскалация. + cross-provider-review
(advisory) + **STOP: обязательный User OK** (approval gate — фиксирует бизнес-решения до траты ресурса
Architect на потенциально неверный контракт).

**Phase 2 — Архитектура.** Architect (High/Premium): утверждённая spec + explorer-context →
`technical-design.md` + `task-breakdown.json`. Ревью + **STOP: User OK**.

**Phase 3 — строго последовательно 3a→3b→3c→3d** (каждая следующая после ревью предыдущей +
cross-provider advisory; 3a и 3b по факту запускаются параллельно, судя по ASCII-диаграмме
orchestrator-structures, но 3c ждёт обоих):
- **3a Scenario-Author (Mid):** Vanessa MCP исследование формы → `.feature` intent-Gherkin с
  `unknown_step_candidate` для нераспознанных шагов. Ревью scope=bdd.
- **3b Developer-Tests (Mid/High), параллельно 3a:** YaxUnit unit/integration тесты (Red) для
  server-layer MUST. Ревью scope=tests.
- **3c Scenario-Coder (Mid):** реализует Vanessa-шаги для `.feature` из 3a (@exportscenarios либо BSL в
  `vanessa-tests/support/`), заменяет unknown_step_candidate; Red-гейт обязан падать на отсутствующей
  prod-логике, не на неизвестных шагах. Ревью scope=bdd-steps.
- **3d Developer-Code (High):** вход = Phase 2 + тесты 3b + Red .feature 3a/3c → пишет код до Green и по
  тестам, и по сценариям. При test_failure + suspected_test_error → Reviewer-арбитраж → маршрут в
  3b/3c/остаётся в 3d.

**Phase 4 — Покрытие и регрессия.** Tester (Mid/High): все тесты + edge/integration/regression +
проверка матрицы покрытия из Test Plan (server→YaxUnit, UI/client→сценарный, процесс→e2e — все
закрыты). Ревью (High). Не дублирует Phase 3.

**Передача артефактов:** 0→1,2 explorer-context.md; 1→2 spec.md; 2→3a,3b spec+TD+task-breakdown.json;
3a→3c `.feature` (intent, unknown_step_candidate); 3b→3d test-модули bsl; 3c→3d `.feature` реализован +
новые шаги; 3d→4 BSL+.feature+зелёные тесты.

**Лимиты итераций:** BLOCK ≤3 на артефакт-ревью → эскалация пользователю (единая норма и в full-cycle, и
в task-breakdown Subagent-режиме). Отклонение пользователем Phase 1/2 → автор фазы перерабатывает (не
считается BLOCK-итерацией ревьюера).

**Bug-routing / source-of-truth (L1→L6):** бизнес-цель+ответы пользователя → утверждённая
spec+acceptance criteria → TD+task-breakdown → BDD/acceptance scenarios → unit/integration тесты → код.
При любом конфликте/падении теста — обязательна сквозная проверка сверху вниз, поиск ПЕРВОГО сломанного
звена; запрещён бинарный вывод «виноват тест»/«виноват код» без проверки верхних уровней. Классификация
по уровню обнаружения: L1-2→проблема требований, L3→design/decomposition, L4→BDD, L5→тесты, L6→
реализация. Конкретная маршрутизация в full-cycle: test_failure в 3d → свой код чинить сам; unit-test
suspect → suspected_test_error → Reviewer-арбитраж → 3b; Vanessa-step suspect → suspected_step_error →
Reviewer-арбитраж → 3c; шаг требует API вне TD → clarification_needed → Architect (Phase 2); сценарий
зелёный раньше прод-кода → признак мока → Scenario-Coder убирает мок и перезапускает Red; test_failure в
Phase 4 → Tester чинит свой тест или помечает implementation_error → Developer; MCP/VA недоступен →
fallback `va-visual-check`, при недостаточном сигнале → blocker → эскалация.

**Git-гейты:** ветка на задачу (medium/complex), quick-fix — без ветки. Коммит только после прохождения
review/approval фазы (checkpoint per phase, working tree чист во время BLOCK). Squash-merge оркестратором
автоматически, но ТОЛЬКО при одновременном: cross-provider-review gate=PASS + final-report.md с
`review_id` + все тесты exit_code=0 в финальной итерации + чистое дерево + актуальный rebase на parent.

**Эскалация фильтр (referenced, не в этой выборке дословно):** только admin-операции / изменение
контракта L1-L2 / бизнес-выбор / 3+ BLOCK / расширение scope — технические развилки решаются
делегированием сабагенту, не эскалацией пользователю.

**Ретиринг-архитектура (ключевой факт):** сам `full-cycle/SKILL.md` — НЕ always-on. Дисциплина
оркестрации (delegate-not-execute, routing, gates, bug-routing, cross-provider, escalation-filter) —
durable в профиле `framework/subagents/orchestrator.md` (Слой 2, активна только в full-режиме).
Детальная фазовая механика (Phase 0-4, передача артефактов, обработка ошибок) — read-on-choice, читается
из `full-cycle/SKILL.md` оркестратором по факту входа в конкретную фазу, а не грузится как правило на
каждый запрос. Это объясняет компактность самого full-cycle (108 строк) при большом объёме реальной
дисциплины, живущей вне заданной для этого аудита области.

## Probe Facts

принцип публичен, но точная реализация/цифра/название — уже локальная конвенция.
